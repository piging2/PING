## Section 3: Smallest integration surface (no new persistence)

**The recorder is `ping_events` + `ping_missions`.** Nothing new is stored anywhere. Everything below is instrumentation (new fields on existing writes) + correlation IDs + projection (read-only queries over existing endpoints).

1. **Inject `run_id` / `parent_run_id` into the existing envelope.** `UnifiedEventRuntime.emit()` already accepts arbitrary `metadata`; `POST /events` and `POST /ingest` already accept metadata keys. Change: document and populate `metadata.run_id` (generated by the emitting worker: one execution attempt) and `metadata.parent_run_id` (the delegating run: cron-worker run → meta-pass run → Meta AI ask). `correlation_id` already groups "everything from one originating observation"; `run_id` adds the execution-attempt layer the envelope asks for. Missions stay the parent grouping; no schema migration beyond using JSONB keys that already exist.
2. **Boundary events from existing workers, no new tables.** `meta-pass.sh`, `run_pass.sh`, and the outreach engine already have crisp start/end/exit points. Change: at run start/end they POST to the existing `/events` endpoint with new `event_type`s (e.g. `WORKER_RUN_STARTED` / `WORKER_RUN_COMPLETED`, registered in the existing `generated/event_registry.json`), carrying `run_id`, `parent_run_id`, status/exit code, and `output_refs` (sidecar path, raw artifact name, pack version). This is a client-side change only; the gateway already accepts and indexes these.
3. **Close the worker-file queryability gaps with files, not a store.** Persist `engage.js` result JSONs locally (today they are transient on the Pig); write infra failures to a per-run `.diagnostics` sidecar instead of stdout-only; add `run_id` (+ `mission_id` once the bridge returns it) to `.provenance.json`. Rule: files remain **evidence**, PING remains the **queryable record**; projection reads PING, never the filesystem.
4. **Projection over existing APIs serves all three levels** (read-only; no new backend):
   - L1 Mission (human): `GET /missions` + `GET /events/correlation/:id` → status, progress, last event. Renderable as a static page or even a generated markdown digest hitting the gateway's public/auth'd GETs.
   - L2 Execution trace: `GET /events/:id/descendants` / `/ancestors` already return the causal tree; add `run_id` as a filter dimension (it will be in metadata, already indexed pattern exists for causation/correlation).
   - L3 Evidence: artifacts are already content-addressed (pack sha1; answers by timestamped filename); link them via `output_refs` in the boundary events from step 2. Raw bytes stay in files; hashes + pointers live in events.
5. **Explicitly not built:** no `continuity.db`/`agent_events.db`; no new bus/scheduler/dashboard backend; ORCA untouched (disabled by standing decision); the "Oracle" window is a read-only projection over gateway GETs, not a new system. New `event_type`s go through the existing registry validation.

## Section 4: Open questions and risks

1. **Agent-readable Oracle vs. auth scoping (requirement tension).** The GET APIs are already agent-queryable, but exterior auth is a single Bearer key per agent with coarse levels, and the **L1 over-grant seam is still present in code** (`muse` L1 "Observe" still lists `fs.write`/`fs.patch`; levels are name-only at the HTTP boundary). Least-privilege read keys for Meta/desktop agents are undecided. Risk: widening read access before the capability profile is corrected.
2. **Guardrail — the shadow system risk.** The real duplication hazard is not a new database; it is the worker-file layer (sidecars, logs, engagement markdown) silently becoming a second source of truth. Mitigation is a rule, not code: PING is the queryable record; files are evidence. The `.provenance.json` sidecars should eventually carry the spine's `event_id`/`mission_id` back-pointer so the two layers join explicitly.
3. **Running image ≠ audited source.** The gateway runs `phase4-eventauth6`; the audit read the curious-squid worktree @ bce92787 (documented lineage ends at eventauth4). Deltas in eventauth5/6 are unknown; `/capabilities` 404s live (authority may not have initialized). Byte-verification of image vs. source was out of scope for read-only.
4. **DB is a blind spot.** Postgres is healthy and reachable, but live schema/row counts are unverified (no DB client on the Pig for the SSH user, `docker exec` prohibited, no authorized credential path). Any continuity projection that depends on direct SQL is blocked until a read-only DB path exists; the HTTP APIs are the viable query path today.
5. **Known defects in the read path:** `/ops/status` 500s (root-caused: `fingerprint.generate is not a function`); `/constitution/graph` 500s (pre-existing, not re-verified). A mission-level dashboard built on `/ops/*` must route around these.
6. **The "Why?" layer has no store and needs none new.** Capability-selection rationale (why Meta AI was chosen, why a worker was rejected) fits as `decision`/`reason` keys in the existing `payload`/`result` JSONB of boundary events — instrumentation, not persistence. Nothing records it today.
7. **Retention policy is undecided and currently unbounded.** No TTL on `ping_events`, `ping_missions`, `capability_requests`, or container logs (json-file, no rotation). A continuity plane that records every tool call will accelerate growth; this needs a decision before volume increases.
8. **Two envelope models coexist** (`ping_events` spine vs. TenantOS `canonical_events`); the ledger calls it a documented asymmetry. A continuity projection should pick the spine (`ping_events` + `ping_missions`) as canonical and treat `canonical_events` as out of scope until convergence is decided.
9. **No `run_id` semantics exist** — introducing it touches `emit()`, both POST routes' accepted metadata, and every worker. Small but cross-cutting; needs a single naming decision (`run_id` format, who mints it) before instrumentation starts.
10. **ORCA must stay out.** It is live-but-disabled with its own private event queue and in-memory missions; wiring it into continuity would duplicate the spine and contradict the standing directive. If it is ever converged, that is a separate authorized decision.

**Bottom line:** ~70% of the proposed envelope already exists on the PING spine. The missing layer is genuinely **instrumentation + correlation IDs + projection**, not persistence: mint `run_id`/`parent_run_id`, emit worker boundary events through the existing `/events` API, persist the two transient worker outputs as files, and project the three visibility levels with read-only queries over endpoints that already exist.
