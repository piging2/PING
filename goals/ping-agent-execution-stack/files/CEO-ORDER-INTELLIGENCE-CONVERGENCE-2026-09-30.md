## The research worker must be better than "agent searches web"

The naive implementation would be: `mission → LLM research → summary`. Don't build that.

Make the first real intelligence mission exercise the epistemic machinery already paid for:

`QUESTION → RESEARCH PLAN → SOURCE ACQUISITION → OBSERVATIONS → CLAIM EXTRACTION → SUPPORT/COUNTEREVIDENCE → VERDICT → FINDINGS → UNRESOLVED QUESTIONS → KNOWLEDGE CANDIDATES`

The model performs semantic work — question decomposition, source selection, contradiction discovery, explanation, synthesis — but deterministic PING machinery owns identity, provenance, evidence attachment, mission state, authorization, persistence, and promotion.

The output shouldn't primarily be prose. It should be a structured **Finding Set** from which prose can later be projected.

The scarce object isn't content; it's the **finding**. The useful transformation: `RAW REALITY → ANOMALY → FINDING → PROOF → EXPLANATION → ARTIFACT`, with expected/observed/delta/surprise/consequence/evidence/alternative explanation/confidence/reproducibility as finding dimensions.

## Five reusable semantic products (not five new services)

**Observation** says what was seen.
**Claim** says what may be true.
**Finding** says what survived meaningful examination and why it matters.
**Proposal** says what we might do because of it.
**Learning** says how an observed outcome changes our beliefs.

Those objects power everything: MarketingOS uses a Finding to make a technical post. FYD uses a Finding to decide an acquisition/planning improvement. ORCA uses a Finding to propose work. Mission Control projects the chain. TenantOS could eventually use infrastructure findings as reconciliation-proposal inputs. An engineer uses it to understand why production behaved unexpectedly.

**Repurpose rather than add.**

- FYD CURRENT IMPLEMENTATION: evidence-backed objects, owner corrections, Ask, SiteSpec, capability/approval path, regeneration survival.
- PING EXISTING IMPLEMENTATION: MissionRuntime, scheduler, WorkerRuntime, canonical event ingress, evidence verification, ClaimWorker, knowledge graph/promotion, lineage, authorization, outcome semantics.
- HARVESTABLE CODE: those primitives plus existing research-agent procedures, URL acquisition, replay/witness machinery, Mission Control projection, connector contracts.
- DUPLICATION RISK: very high if we create ResearchAuthority, MarketingAuthority, FindingAuthority, ContentAuthority, AudienceAuthority, ExperimentAuthority, LearningAuthority, or another "agent memory."
- SMALLEST REQUIRED DELTA: one real `INTELLIGENCE_RESEARCH` mission contract + worker routing + existing-event outputs + one Mission Control projection. That's it.

## ORCA becomes the intelligence orchestrator, not the intelligence

ORCA answers: **What needs to be known or done next?**

It must not become the canonical research store, marketing brain, truth engine, or knowledge authority.

For an intelligence mission:
`ORCA → INTELLIGENCE_RESEARCH WorkOrder → WorkerRuntime → execution target(s) → observations/evidence/claims → PING → ORCA sees unresolved state → next bounded mission`

This makes "one brain, many hands" concrete:
`ORCA / MissionRuntime` → chooses bounded work → `WorkerRuntime` → selects `LOCAL / PYTHON / CODEX / HERMES / ORACLE / browser / external model` → receives typed result/evidence → canonical PING machinery decides what that result *means*.

A research agent can disappear tomorrow without taking the company's accumulated intelligence with it.

## Mission Control becomes an epistemic debugger

Not another pretty dashboard. Its killer feature: **Why does the system believe this?**

For any finding: `FINDING → underlying claims → support set → counterevidence → sources → source freshness → direct vs inferred → confidence → competing explanation → mission that produced it → worker/target that observed it → subsequent decisions/artifacts → later outcomes.`

For an action: `PROPOSAL → AUTHORIZATION → ATTEMPT → RESULT → INDEPENDENT EFFECT → OUTCOME`

For deployment: `SOURCE → BUILD → DEPLOYMENT → PROCESS → SERVED BYTES → SERVED BEHAVIOR`

For content: `FINDING → CLAIMS → ARTIFACT → DISCLOSURE PASS → APPROVAL → DISTRIBUTION → OBSERVATIONS → OUTCOME → LEARNING`

Same operating environment. Different projection.

## Collapse "MarketingOS" and "Research OS" internally

Keep MarketingOS as a product/domain name if useful. Architecturally, the lower half is general intelligence infrastructure. The upper half is marketing-specific: `AUDIENCE QUESTION → opportunity → editorial hypothesis → artifact family → distribution experiment → marketing outcome.`

Everything before `AUDIENCE QUESTION` is general-purpose PING intelligence.

- **PING Intelligence Core:** `observe → question → research → claim → evidence → falsify → finding → learn`
- **MarketingOS:** `finding → audience → opportunity → thesis → artifact → approve → distribute → measure`
- **FYD:** `finding/evidence/object → owner experience → proposal → capability → action`

This prevents encoding "marketing" into reusable epistemology.

## Replace content generation with compilation

Don't ask a model to write a post. Give it `Finding + audience question + disclosure policy + format contract + evidence bindings` and compile:
`FINDING → longform technical note → thread → 45-second script → diagram → short post → comment response → follow-up experiment.`
Every derivative carries the same claim IDs/evidence lineage. This gives **idea-level attribution**: we can eventually discover that a concept is powerful across seven derivatives, rather than concluding "Tuesday's X post worked."

## Add a Prediction Test to every finding

After consuming this finding, what can a competent person predict that they could not predict beforehand?

Make it machine-readable: `prediction_before`, `prediction_after`, `decision_changed`, `failure_avoided`, `new_test_enabled`. A finding with no changed prediction, decision, or test may just be trivia. PING can then rank research by expected **decision information gain**, not "interestingness."

## Separate five scores permanently

Never one magic MarketingScore. Maintain orthogonal assessments:

1. **Epistemic quality** — evidence, reproducibility, contradiction, freshness.
2. **Information gain** — how much the finding changes predictions.
3. **Audience value** — who has this problem/question and how intensely.
4. **Editorial leverage** — surprise, clarity, compression, visualizability.
5. **Operational risk** — security, privacy, disclosure, customer/reputation consequences.

Do not average these into fake precision. A finding can be extremely true and terrible to publish. A topic can have massive demand and weak evidence. Those distinctions are valuable state.

## Add a public-proof compiler

Compile `INTERNAL SUPPORT SET → disclosure classification → redact/aggregate/transform → public-safe proof packet → public artifact`, preserving `PUBLIC CLAIM → INTERNAL CLAIM → INTERNAL SUPPORT SET`. A claim can be established internally while deliberately not publicly evidenced — a legitimate `WITHHELD` epistemic state. Technical content with receipts, without reckless disclosure.

## Turn comments into sensors

Treat comments as external adversarial input: `COMMENT → observation → objection/question/counterexample classification → existing finding association → unresolved claim → optionally next research mission.`

The invariant: **COMMENT ≠ KNOWLEDGE.** Comments become observations capable of spawning verification/research — not automatically accepted truth. This closes the flywheel: research → finding → publication → expert criticism → research → stronger finding.

## Reverse-engineer intelligence aggressively

Every model-mediated behavior carries a maturity state:
`MODEL-REQUIRED → MODEL-ASSISTED → DETERMINISTIC DEFAULT / MODEL ESCALATION → potentially DETERMINISTIC.`

But **no model promotes its own heuristic into policy**. That remains: `observations → candidate learning → evidence/support → proposal → human/existing authorization → approved playbook`.

## Harvest external software differently (MarketingOS)

Do not build commodity: crawler, browser automation framework, video editor, generic social scheduler, analytics warehouse, generic vector database, generic workflow engine, generic CMS, generic agent framework, generic observability stack. Harvest them behind boundaries.

Own: **finding semantics, evidence bindings, epistemic state, adversarial review, audience-question matching, content lineage, disclosure policy, qualified-outcome learning, and the deterministic conversion of repeated judgment into software.**

"Harvest everything" continues to mean **understand everything, integrate almost nothing by default**.
