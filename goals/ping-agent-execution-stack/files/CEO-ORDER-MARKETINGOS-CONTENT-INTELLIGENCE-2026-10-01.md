## Nolan's framing

## The directive (crew-facing, verbatim)

> # MARKETINGOS — SENIOR-ENGINEER CONTENT INTELLIGENCE PASS
>
> We are no longer designing a generic marketing automation system.
>
> We are building a system capable of producing technical work that an L6/L7 engineer can inspect, challenge, reproduce, learn from, and feel comfortable forwarding to another strong engineer.
>
> The target is not "AI content."
>
> The target is:
>
> **NOVEL TECHNICAL CLAIM → PRIMARY EVIDENCE → REPRODUCIBLE DEMONSTRATION → SURPRISING CONSEQUENCE → HONEST LIMITATIONS → HIGH-DENSITY ARTIFACT → MEASURED AUDIENCE RESPONSE → LEARNING**
>
> Preserve the existing constitutional architecture. Do not create MarketingAuthority, ViralityAuthority, ContentBrain, ResearchTruthStore, or another database.
>
> ## THE FIRST MAJOR CHANGE: OPTIMIZE FOR INFORMATION GAIN, NOT CONTENT VOLUME
>
> Do not ask:
>
> "What should we post today?"
>
> Ask:
>
> **"What can we prove today that a competent engineer probably does not already know?"**
>
> Every content candidate must earn publication through five dimensions:
>
> **NOVELTY × TECHNICAL DEPTH × EVIDENCE QUALITY × REPRODUCIBILITY × AUDIENCE RELEVANCE**
>
> Then separately estimate:
>
> **SHAREABILITY = SURPRISE × CLARITY × PRACTICAL CONSEQUENCE × IDENTITY VALUE**
>
> Identity value means: *does sharing this make the reader look useful, informed, technically serious, or ahead of an important problem?*
>
> Do not combine those into a fake magic number initially. Preserve the component scores and evidence behind them.
>
> ## 1. BUILD A CLAIM-FIRST CONTENT PIPELINE
>
> Current MarketingOS thinking is too artifact-oriented.
>
> A video is not the unit of intellectual value.
>
> **The claim is.**
>
> Before writing a script, produce a claim inventory:
>
> `CLAIM → TYPE → NOVELTY → SUPPORT SET → COUNTEREVIDENCE → REPRODUCTION → CONFIDENCE → PRACTICAL CONSEQUENCE`
>
> Claim types should include:
>
> `MEASUREMENT / MECHANISM / COMPARISON / FAILURE MODE / ARCHITECTURAL INVARIANT / PERFORMANCE RESULT / SECURITY RESULT / OPERATING LESSON / PREDICTION`
>
> Predictions must remain predictions.
>
> Observations must remain observations.
>
> Mechanistic explanations need evidence beyond correlation.
>
> This maps directly onto the existing ClaimWorker/EvidenceAuthority path rather than inventing a content-truth system.
>
> ## 2. INTRODUCE A TECHNICAL EVIDENCE LADDER
>
> The current proposed `vendor-described / independent / unreplicated` vocabulary is useful but too coarse for senior-engineer material.
>
> Every consequential technical claim should carry an evidence profile:
>
> `SOURCE CODE`
> `LIVE EXECUTION`
> `CONTROLLED REPRODUCTION`
> `PRIMARY DOCUMENTATION`
> `MEASUREMENT`
> `INDEPENDENT CORROBORATION`
> `VENDOR CLAIM`
> `MODEL INFERENCE`
> `UNKNOWN`
>
> And separately:
>
> `REPRODUCED / OBSERVED_ONCE / REPORTED / INFERRED / UNVERIFIED`
>
> Do not collapse source quality and verification state into one label.
>
> **A vendor's documentation can be primary evidence for what the vendor promises, but not independent proof that the behavior occurs.**
>
> That distinction will make the content noticeably more sophisticated.
>
> ## 3. MAKE COUNTEREVIDENCE MANDATORY
>
> Before publishing an important thesis, run a hostile research pass:
>
> "What is the strongest technically credible reason this thesis is wrong?"
>
> Search for:
>
> contradictory benchmarks,
> alternative causal explanations,
> version dependence,
> hardware dependence,
> sample-selection effects,
> warm/cold cache effects,
> hidden configuration differences,
> vendor-specific behavior,
> survivorship bias,
> measurement artifacts,
> confounders.
>
> The system should be rewarded for **downgrading its own thesis**.
>
> A post becoming:
>
> "We thought X. The experiment showed Y."
>
> is not a failed content mission.
>
> It can be substantially better technical content.
>
> ## 4. BUILD A REPRODUCIBILITY CONTRACT
>
> For benchmark/demo/research content, MarketingOS should attempt to produce:
>
> `ENVIRONMENT`
> `VERSION/COMMIT`
> `INPUT`
> `CONFIGURATION`
> `COMMAND/PROCEDURE`
> `RAW RESULT`
> `DERIVED METRIC`
> `KNOWN LIMITATIONS`
> `ARTIFACT DIGEST`
>
> Never publish "37% faster" without making "37% faster under what conditions?" answerable.
>
> The content itself can stay entertaining. The evidence package underneath it should be boringly rigorous.
>
> ## 5. SEPARATE DISCOVERY FROM EXPLANATION
>
> Research that discovers an interesting result and research that explains *why* it happened are different missions.
>
> Use:
>
> `DISCOVERY → FALSIFICATION → MECHANISM → SYNTHESIS`
>
> A benchmark anomaly is discovery.
>
> Re-running it is verification.
>
> Explaining cache locality/compiler behavior/database contention/etc. is mechanism research.
>
> Turning it into a coherent narrative is synthesis.
>
> Never let synthesis manufacture mechanism.
>
> ## 6. ADD A "SURPRISE DELTA"
>
> The best technical content often contains a gap between reasonable expectation and observed reality:
>
> `EXPECTED X → OBSERVED Y → WHY THE GAP EXISTS → CONSEQUENCE`
>
> Mine PING's actual operation for these constantly.
>
> Examples of the *shape*, not claims to publish:
>
> "We blamed X. Measurement showed Y."
>
> "All tests passed. Production was still running older bytes."
>
> "Deleting 40 GB freed essentially nothing until the VHDX was compacted."
>
> "The worker returned success, but that did not establish the external effect."
>
> "The authorization check passed because the request effectively vouched for itself."
>
> These are excellent engineering narratives because the lesson is embedded in a violated expectation.
>
> ## 7. TREAT FAILURES AS FIRST-CLASS CONTENT SOURCES
>
> Build a candidate extractor over real incidents:
>
> `SYMPTOM → INITIAL HYPOTHESIS → OBSERVATION → WRONG ASSUMPTION → ROOT CAUSE → FIX → PROOF → GENERALIZABLE LESSON`
>
> The storage incident is structurally excellent content because measurement falsified the initial voice-memo hypothesis and revealed VHDX behavior.
>
> The tenant self-attestation bug is structurally excellent.
>
> UNKNOWN-after-effect is structurally excellent.
>
> Source/build/deployment divergence is structurally excellent.
>
> The eligibility bypass is structurally excellent.
>
> Do not expose secrets, customer/private data, exploit-enabling detail, or internal information whose disclosure creates unnecessary risk.
>
> ## 8. CONTENT SHOULD HAVE TWO LAYERS
>
> Every serious piece gets:
>
> **Layer A — comprehension**
>
> A technically literate engineer should understand the central result quickly.
>
> **Layer B — inspection**
>
> The skeptical senior engineer gets methodology, evidence, versions, traces, limitations and reproduction details.
>
> This permits an accessible 45-second video without dumbing down the underlying engineering.
>
> Never confuse complexity with sophistication.
>
> **The ideal is simple presentation backed by deep inspectability.**
>
> ## 9. HOOKS MUST BE TECHNICAL PROMISES, NOT MARKETING ADJECTIVES
>
> Ban generic hooks:
>
> "This changes everything."
>
> "Nobody is talking about this."
>
> "This is insane."
>
> Prefer falsifiable tension:
>
> "We deleted 40 GB and Windows gave us almost none of it back."
>
> "Our authorization test passed for exactly the reason it was insecure."
>
> "The code was fixed. Production wasn't."
>
> "A successful worker result still didn't prove the action happened."
>
> The opening should create a technical question whose answer the body actually earns.
>
> ## 10. DO NOT FRONT-LOAD THE ARCHITECTURE
>
> Senior engineers care about architecture when architecture explains something.
>
> Avoid:
>
> "We built a deterministic event-sourced multi-agent orchestration architecture…"
>
> Prefer:
>
> "We had to answer a deceptively difficult question: after an API timeout, did the action happen?"
>
> Then introduce the architectural distinction:
>
> `ATTEMPT ≠ RESULT ≠ EFFECT ≠ VERIFICATION ≠ OUTCOME`
>
> Architecture becomes the explanation, not the advertisement.
>
> ## 11. CREATE AN ABSTRACTION LADDER FOR EVERY PIECE
>
> Strong engineering material should travel:
>
> `INCIDENT → MECHANISM → INVARIANT → GENERAL LESSON`
>
> Example:
>
> storage crisis
> → dynamic VHDX allocation
> → guest deletion ≠ host reclaim
> → logical storage accounting ≠ physical capacity recovery.
>
> That last sentence is the transferable intellectual payload.
>
> If a story cannot produce a transferable lesson, downgrade its priority.
>
> ## 12. BUILD AUDIENCE CLUSTERS FROM QUESTIONS, NOT JOB TITLES
>
> Do not target "senior software engineers."
>
> Discover clusters such as:
>
> distributed-systems engineers worried about retries,
> platform engineers fighting deployment provenance,
> security engineers interested in authority boundaries,
> AI-infra engineers handling agent effects,
> founders operating absurdly complex infrastructure cheaply,
> developers interested in deterministic AI systems.
>
> Cluster on:
>
> `REPEATED QUESTION + TECHNICAL PAIN + VOCABULARY + SOPHISTICATION + OBSERVED RESPONSE`
>
> The existing design already correctly treats AudienceCluster as knowledge/projection rather than a new authority.
>
> ## 13. ADD "AUDIENCE SOPHISTICATION FIT"
>
> A correct post can still fail because it is pitched one abstraction level too low or too high.
>
> Track:
>
> prerequisite concepts,
> unexplained jargon,
> assumed stack knowledge,
> conceptual novelty,
> implementation depth,
> expected reader role.
>
> Generate multiple projections from one canonical technical artifact:
>
> `30s RESULT`
> `90s EXPLANATION`
> `5–10m DEEP DIVE`
> `WRITTEN TECHNICAL NOTE`
> `REPRODUCTION APPENDIX`
>
> One investigation, multiple depths.
>
> ## 14. CONTENT MEMORY MUST REMEMBER CLAIM PERFORMANCE, NOT JUST POST PERFORMANCE
>
> Do not merely learn:
>
> "Video A got 18k views."
>
> Learn:
>
> "The claim about UNKNOWN-after-effect caused saves and senior-engineer comments."
>
> Track performance down the lineage:
>
> `SOURCE INCIDENT → CLAIM → THESIS → HOOK → FORMAT → DISTRIBUTION → AUDIENCE → OUTCOME`
>
> Then MarketingOS can distinguish:
>
> "This topic is good"
>
> from
>
> "This claim was good but the hook was weak"
>
> from
>
> "The hook worked but the technical payoff disappointed."
>
> That is much more valuable.
>
> ## 15. MEASURE DEPTH SIGNALS, NOT JUST REACH
>
> Views are weak evidence.
>
> Capture where platforms permit:
>
> completion,
> retention curve,
> rewatches,
> saves/bookmarks,
> shares,
> profile visits,
> qualified comments,
> link clicks,
> follow conversion,
> long-form continuation,
> technically substantive replies.
>
> Classify comments/questions semantically:
>
> `AGREEMENT`
> `COUNTEREXAMPLE`
> `CLARIFICATION`
> `IMPLEMENTATION QUESTION`
> `REPRODUCTION`
> `CORRECTION`
> `NEW HYPOTHESIS`
>
> A correction from a strong engineer can be more valuable to the intelligence system than 1,000 passive likes.
>
> ## 16. ADD NOVELTY DECAY
>
> A technically excellent idea becomes less valuable after everyone publishes it.
>
> Opportunity evaluation therefore needs:
>
> `FIRST_SEEN`
> `ACCELERATION`
> `SATURATION`
> `OUR_EVIDENCE_ADVANTAGE`
> `OUR_EXPERIENCE_ADVANTAGE`
>
> If a subject is saturated but PING has uniquely strong first-party evidence, it can still be excellent.
>
> Do not chase novelty without defensibility.
>
> ## 17. DISTINGUISH BORROWED INSIGHT FROM OWNED INSIGHT
>
> Label candidate theses:
>
> `ORIGINAL OBSERVATION`
> `ORIGINAL EXPERIMENT`
> `ORIGINAL SYNTHESIS`
> `REPLICATION`
> `COMMENTARY`
> `CURATION`
>
> Favor original observation/experiment when available.
>
> If the insight came from another engineer, paper or vendor, attribution is part of the artifact — not an afterthought.
>
> Competence includes knowing which ideas are yours.
>
> ## 18. BUILD A "DO NOT PUBLISH" GATE
>
> Fail publication when:
>
> central claim unsupported,
> benchmark unreproducible,
> title stronger than evidence,
> mechanism presented as fact when inferred,
> source attribution missing,
> security/privacy risk unresolved,
> confidential information exposed,
> result version-dependent but version omitted,
> contradiction unresolved and material,
> artifact generated from stale evidence,
> human approval absent where required.
>
> "We don't know yet" is a valid result.
>
> ## 19. EXPERIMENT ON PRESENTATION, NEVER ON TRUTH
>
> Test:
>
> hook,
> length,
> diagram,
> pacing,
> title,
> thumbnail,
> CTA,
> posting time,
> format.
>
> Do not A/B test whether to exaggerate the technical conclusion.
>
> The file already has the right constitutional rule: experiment results update confidence and do not directly become policy.
>
> ## 20. BUILD "CONTENT FALSIFICATION" BEFORE CONTENT GENERATION
>
> For the top candidate each day, run:
>
> **Researcher:** strongest case.
>
> **Skeptic:** strongest countercase.
>
> **Reproducer:** can I reproduce it?
>
> **Senior reviewer:** what would embarrass us if published?
>
> **Editor:** what is the smallest accurate statement that remains interesting?
>
> These are roles/worker behaviors, not five new agents with independent memory or authority.
>
> ## 21. CREATE A PUBLIC TECHNICAL TRUST LEDGER
>
> Not a blockchain. Not another store.
>
> A projection from existing evidence.
>
> For published technical pieces, make it possible to expose:
>
> sources,
> environment,
> tested versions,
> corrections,
> updates,
> reproducibility status.
>
> When wrong, append:
>
> `CORRECTED: what changed / why / when / evidence`
>
> Never silently rewrite history.
>
> A visible correction mechanism is a trust feature.
>
> ## 22. VIRALITY MUST BE AN OUTCOME, NOT AN AUTHORITY
>
> Never allow predicted engagement to override:
>
> evidence quality,
> security,
> privacy,
> human approval,
> technical honesty.
>
> OpportunityScore remains recommendation-only. The current design explicitly makes that distinction.
>
> ## 23. MAKE PING'S OWN DEVELOPMENT THE FIRST CONTENT MINE
>
> Before generic trend-chasing, exploit the extraordinary amount of original engineering evidence already being generated.
>
> Every meaningful incident should automatically become a **content candidate**, not a post:
>
> `EVENT/INCIDENT → GENERALIZABLE CLAIM → NOVELTY CHECK → SECURITY REVIEW → EVIDENCE PACKAGE → CONTENT CANDIDATE`
>
> This produces something competitors cannot trivially copy:
>
> **first-party engineering experience.**
>
> ## 24. THE COMPOUNDING UNIT IS NOT THE POST
>
> The durable unit should be:
>
> `QUESTION → CLAIM → EVIDENCE → EXPERIMENT → RESULT → EXPLANATION → ARTIFACT → AUDIENCE RESPONSE → LEARNING → NEXT QUESTION`

> Posts are projections from this graph.
>
> That aligns directly with the current convergence finding that intelligence can compound in `ping_events`, `ping_missions`, `knowledge_nodes/edges`, and Qdrant rather than in a parallel MarketingOS memory system.

## Nolan's three shifts (his own summary, preserved)

First, stop thinking of "viral" as an upstream score. The system should discover the properties correlated with distribution, but those should remain observational. The architecture already has the correct doctrine: opportunity scores are recommendations, not authorities; connectors execute but do not authorize themselves; learning does not become policy automatically. Preserve that separation.

Second, the moat can become technical epistemology as a content engine. Most AI marketing systems optimize wording after choosing a topic. PING can potentially optimize what deserves to be said in the first place: claims, counterclaims, evidence, reproducibility, uncertainty, audience fit, experiments and subsequent corrections. That is considerably harder to copy.

Third, the most interesting content source may already be sitting underneath us. PING has been generating unusually good engineering stories from repeatedly encountering distinctions senior engineers recognize as real: code state versus deployed state, worker result versus world effect, logical bytes versus physical reclamation, authorization versus self-attestation, canonical truth versus projection, and UNKNOWN versus FAILED. Those are not "updates about our startup." They become useful content when converted into general engineering invariants.
