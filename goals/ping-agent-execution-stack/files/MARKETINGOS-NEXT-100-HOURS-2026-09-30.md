## Send this to the coordinator

MARKETINGOS — NEXT 100 HOURS

Switch the center of gravity now.

For the next 100 productive hours, optimize for one outcome:
PING becomes an increasingly intelligent marketing/content machine that can research reality, discover worthwhile ideas, produce technically defensible content, learn from results, and eventually generate a review-ready video every day.

This is not a TenantOS sprint.
Do not spend the sprint expanding cloud placement, generic tenant infrastructure, provider abstraction, constitutional machinery, generic agent frameworks, or speculative autonomy unless a reached MarketingOS arrow is literally blocked by one of them.

ORCA and Jev are concepts/primitives to harvest, not products to rebuild.
ORCA contributes the control-loop idea:
OBJECTIVE → OBSERVE → PLAN → AUTHORIZE → ACT → VERIFY → LEARN → NEXT
Jev contributes useful research/reasoning/execution concepts where they demonstrably improve the content loop.
Neither gets a parallel sovereign runtime.

The MarketingOS product loop is:
QUESTION → RESEARCH → OBSERVATIONS → EVIDENCE → CLAIMS → CONTRADICTIONS → VERDICTS → AUDIENCE/OPPORTUNITY → THESIS → CONTENT BRIEF → SCRIPT → CLAIM CHECK → ASSETS → VIDEO → HUMAN APPROVAL → DISTRIBUTION → METRICS → OUTCOME → LEARNING → NEXT QUESTION
That is the sprint.

Start by proving a DAILY CONTENT LOOP, not by building all the machinery imaginable.
Every day the system should increasingly be capable of answering:
1. What happened that our audience should care about?
Search our approved source universe, current research targets, product ecosystem, GitHub/software developments, experiments, PING/FYD progress, technical incidents worth teaching from, and previously unresolved questions.
2. What is actually new?
Deduplicate against previous observations, content, theses, scripts, and published material. Distinguish genuinely new evidence from recycled discourse.
3. What can we defensibly claim?
Build the support set. Prefer primary evidence. Separate VERIFIED / INFERRED / UNKNOWN. Surface contradictions. A technically impressive script with a false premise is a failed artifact.
4. Why would a senior engineer care?
Do not optimize for generic AI-news engagement. Extract the non-obvious engineering consequence: architecture tradeoff, failure mode, security implication, operational lesson, benchmark caveat, economic consequence, or reusable engineering pattern.
5. What is our thesis?
The system must move beyond summarization. Evidence should produce a defensible point of view—but thesis is an artifact/proposal, never truth authority.
6. What content form best expresses it?
Short technical post, long-form post, diagram, benchmark, code walkthrough, incident retrospective, comparison, demo, short video, or longer video. Do not force every insight into the same format.
7. Can every important factual statement survive hostile review?
Before approval, enumerate script claims and bind each to support. Unsupported factual claims are rewritten, qualified, or removed.
8. What happened after publication?
Capture impressions, watch time, retention, clicks, comments, saves, shares, profile actions, qualified conversations, and other available channel signals as observations—not as truth about causation.
9. What did we learn?
Preserve:
HYPOTHESIS → CONTENT → AUDIENCE → DISTRIBUTION → OBSERVED OUTCOME → INTERPRETATION → CONFIDENCE → NEXT TEST
Never convert one successful post into universal policy.
10. What should tomorrow's mission be?
This is where the system becomes compounding rather than merely automated.

Use existing PING homes. The forensic already identified the durable residue:
ping_events = observations, claims, signals, metric observations, receipts
ping_missions = research briefs, experiments, distribution runs/results
knowledge_nodes/edges = findings, audiences, opportunities, learnings, playbook candidates
Qdrant = semantic retrieval/projection
Do not create MarketingDB, ContentBrain, ResearchTruthStore, GrowthAuthority, AudienceAuthority, ExperimentAuthority, DistributionAuthority, or LearningAuthority. The existing convergence analysis explicitly found no need for them.

The first bounded mission types are enough:
INTELLIGENCE_RESEARCH
CONTENT_PRODUCTION only if an existing mission vocabulary cannot represent it cleanly
EXPERIMENT_RUN
DISTRIBUTION_RUN
Mission type is routing vocabulary, not sovereignty.

First 20 hours: make research excellent.
Run one real INTELLIGENCE_RESEARCH mission on something we might actually publish about.
It must start with explicit questions and claims-to-verify rather than "research X."
Require primary sources where possible. Record contradictory evidence. Generate CONFIRMED / REFUTED / UNCLEAR findings. Produce the unresolved-question set automatically.
The existing forensic says the INTELLIGENCE_RESEARCH label is absent but MissionRuntime and WorkerRuntime already provide the underlying machinery. Treat this as bounded wiring, not architecture.

Hours 20–40: turn intelligence into excellent editorial judgment.
Build/prove the smallest deterministic projection that ranks candidate ideas using things we can actually support:
technical novelty
audience relevance
evidence strength
demonstration potential
disagreement/contradiction
timeliness
uniqueness relative to our own prior content
expected learning value
production cost
Scores recommend. They never authorize.
Make the machine explain why an opportunity scored as it did and what evidence would change the recommendation.
Generate 3–5 competing theses for the strongest opportunity rather than accepting the first model output.
Have a falsifier attack them.
The winner is not "the model's favorite." It is the surviving proposal presented for human judgment.

Hours 40–60: make script generation evidence-native.
Script production must preserve a machine-readable claim ledger.
Every script should have:
HOOK
AUDIENCE PROMISE
THESIS
SUPPORTING CLAIMS
EVIDENCE
DEMONSTRATION/EXAMPLE
COUNTERARGUMENT
LIMITATIONS
CONCLUSION
CTA
Then run a separate accuracy pass.
The MarketingOS forensic already found transcript/script accuracy as a bounded missing behavior, not a missing authority.
Optimize the editorial style for technical credibility:
no fake certainty
no fabricated benchmarks
no "AI changes everything" filler
no fake controversy
no claim stronger than its evidence
distinguish observed behavior from architectural inference
show failure modes
show counterexamples
say UNKNOWN when unknown
cite primary evidence
reproduce important experiments when feasible
We want content a skeptical senior engineer can disagree with while still concluding: these people did the work.

Hours 60–80: build the first VIDEO COMPILER path.
Do not start by building a giant generative-video platform.
Treat video exactly like FYD treats a website:
structured truth + intent → deterministic presentation specification → renderer.
Define a minimal VideoSpec using existing artifact/projection conventions wherever possible:
narrative beats
spoken script
claim/support references
shot/scene requirements
code/demo captures
diagrams
screenshots
B-roll requirements
on-screen text
citations
timing
transitions
music/audio intent
voice track
captions
Then compile:
VERIFIED RESEARCH → THESIS → SCRIPT → VIDEO SPEC → ASSET PLAN → VOICE → TIMELINE → RENDER → TRANSCRIPT RECHECK → HUMAN REVIEW
The first target is deliberately boring:
one automatically assembled technically accurate video that Nolan can review.
Not cinematic autonomy.
If existing FFmpeg/video/voice primitives can render it, harvest them. If not, identify the smallest missing renderer behavior. Do not create VideoAuthority.
The long-term target is:
every morning, one genuinely worthwhile review-ready video candidate exists because yesterday's evidence and outcomes informed today's research.
Not one mandatory publish per day. If evidence is weak, the correct daily output can be:
NO DEFENSIBLE VIDEO TODAY — HERE IS WHAT WE NEED TO LEARN.
That restraint is part of the product.

Hours 80–100: close the learning loop.
Wire observed distribution metrics through the existing ingestion seam.
The forensic already says /ingest is the canonical observation door and currently lacks a live production producer. Do not build a metrics subsystem; walk through the door that exists.
Evaluate content as experiments, but preserve:
CORRELATION ≠ CAUSATION.
A post followed by follower growth does not prove the post caused it.
Store what happened, competing explanations, confidence, and next test.
Learning must generate candidate playbook rules, never silently rewrite policy.
Repeated supported findings may gradually move:
MODEL-REQUIRED → MODEL-ASSISTED → DETERMINISTIC DEFAULT + MODEL ESCALATION
That is how MarketingOS becomes cheaper, faster, and more reliable instead of merely accumulating prompts.

If a segment cannot be reached, mark the first broken arrow.

One final product law:
MarketingOS is not an automated posting machine.
Posting is commodity.
The valuable machine is:
OBSERVE BETTER → KNOW BETTER → CHOOSE BETTER → EXPLAIN BETTER → CREATE BETTER → MEASURE HONESTLY → LEARN → REPEAT.
ORCA supplies control-loop discipline. Jev supplies useful intelligence/execution concepts. PING supplies memory, evidence, missions, and accountability. Models supply judgment where deterministic software cannot yet do it.
The product is the compounding marketing intelligence loop.
Keep the existing storage guardrails. Keep the current infrastructure stable. No TenantOS expansion unless this loop proves it needs one. No new sovereign authority without proof that existing ownership cannot express the requirement.
And preserve Muse commit law on every writer:
STATUS → OWNERSHIP → IMPLEMENT → TEST → DIFF → STAGE OWNED FILES ONLY → COMMIT → REPORT SHA
No push without explicit authorization.

There is a particularly strong architectural analogy here: the video generator should eventually become a compiler, not an agent wandering around an editor. FYD already demonstrates why that model is powerful: its core value comes from compiling evidence plus owner intent into a deterministic representation, rather than starting from a blank canvas. MarketingOS can do the same thing with video.

And I would make the daily objective slightly harder than "generate a video every day": generate the best defensible next artifact every day. Most days that may become a video. Some days the intelligence system should conclude that the evidence is not strong enough yet and automatically create tomorrow's research mission instead. That behavior is what separates a sophisticated marketing intelligence system from a content spam machine.
