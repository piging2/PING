## 0. Verdict up front

**No new object type is required.** The `MarketingOpportunity` semantics decompose exactly onto five existing PING/FYD primitives. What is needed is two small vocabulary additions (a claim kind and a grant event family), both of which ride existing spines and create no new authority, scheduler, queue, or store.

| Seam stage | Existing primitive | Location | Status |
|---|---|---|---|
| OPPORTUNITY | PING **Claim** (`CLAIM_CREATED`, kind `OPPORTUNITY`) | `ping_events` spine; `ping-runtime/analysis/claim_chaining.js` pattern | needs typed kind only |
| PROPOSAL | **PROPOSED_ACTION** approval event | `ping-runtime/approval/approval_events.js` | exists, P0-gated |
| DECISION | **ACTION_APPROVED / REJECTED** | same module | exists |
| ACTION PLAN + EXECUTION | **Mission** (`ping_missions`, MissionRuntime) | `ping-runtime/orchestration/mission_runtime.js` | exists |
| RECEIPT | **MISSION_COMPLETED** `{missionId, result, duration_ms}` | same module, line 225 | exists |
| OUTCOME | **OBSERVATION_CREATED** → new claims | event spine | exists |

Candidates evaluated and rejected as carriers:
- **Mission as opportunity**: rejected. Missions are durable *work to be done* with lease/retry/execution semantics. An opportunity is *candidate value not yet authorized*; stuffing it into `ping_missions` would confuse "proposed" with "scheduled" and bypass the approval boundary the P0 exists to protect.
- **MarketingOS `opportunity` node_type**: evaluated. It exists only as a placeholder (`mc-marketingos.ts`: state UNKNOWN, reason `NO_VERIFIED_DEMAND_OBSERVATIONS`). It is a projection label, not a truth carrier; the claim spine is the truth carrier.
- **FYD OwnerProposal as opportunity**: partially reused, not as carrier. `OwnerProposal` (`src/fyd/customize/owner-proposal.ts`) is the owner-facing, digest-bound, preview → approve → apply → replay record for *site changes*. It is the right shape for Proposal kinds A/B/E (site prominence, metadata, structured data). But opportunities also produce non-site proposals (social post, creator collaboration), which live on the PING side as PROPOSED_ACTION. OwnerProposal stays the site-change proposal type; it does not generalize to the seam.

## 1. The typed opportunity model (as a Claim kind)

An opportunity is a PING claim: derived truth, evidence-bound, with a verdict lifecycle. New claim *kind* `OPPORTUNITY` (kinds are free-form in the claim payload; this is a vocabulary addition, not a schema migration).

```yaml
# CLAIM_CREATED payload, kind: OPPORTUNITY
subject_object_ids: ["ping:object:<emergency-plumbing>", "ping:object:<coppersmith>"]
objective: "increase qualified emergency calls"
audience_query:            # deterministic filter spec, evaluated not guessed
  geographic: { within: "Grand Junction service area", source: "evidence" }
  relationship: ["existing customers", "follows business"]
  declared_interest: "only where legitimately available"
reason: |                  # the WHY, human-readable, evidence-anchored
  - source confirms 24/7 availability (evidence ref e1)
  - service exists as canonical object (object ref o2)
  - service is below the fold on homepage (observation ob3)
  - emergency-intent traffic is relevant (observation ob4)
  - owner objective is qualified calls (owner statement s5)
evidence_refs: ["e1", "o2", "ob3", "ob4", "s5"]   # CLAIM→SUPPORTED_BY→EVIDENCE edges
candidate_channels: ["site_prominence", "social_post", "creator_collab", "structured_metadata"]
proposed_actions:             # sketches only; each becomes a PROPOSED_ACTION if pursued
  - { sketch: "move emergency section above fold", channel: "site_prominence" }
  - { sketch: "evidence-backed post about 24/7 dispatch", channel: "social_post" }
estimated_cost: { currency: "USD", amount: 0, basis: "internal surface, no spend" }
required_capabilities: ["site.edit", "social.publish", "creator.contact"]
expires_at: "2026-10-14T00:00:00Z"
```

Field-by-field grounding against `recordProposedAction()` (`approval_events.js`):
- `subject_object` → `target_identity` on the derived PROPOSED_ACTION.
- `objective`, `reason` → `reason` (WHY preserved verbatim into the approval request).
- `audience_query` → new claim-payload field; evaluated deterministically before ranking.
- `evidence_refs` → `evidence_refs` (already a first-class field).
- `candidate_channels`, `proposed_actions`, `estimated_cost` → new claim-payload fields; each concrete action fans out to its own PROPOSED_ACTION.
- `required_capabilities` → `capability` on PROPOSED_ACTION (today singular; extend to list in payload, no authority change).
- `required_approval` → the PROPOSED_ACTION construct itself *is* the approval request; nothing executes without ACTION_APPROVED.
- `expiration` → `expires_at` (already a first-class field).

The existing `claim_chaining.js` pattern already proves the mechanism: a claim emits → bounded worker behavior proposes next work with correlation/causation lineage, idempotent on (tenant, type, event_id). Opportunity claims reuse this: unsettled OPPORTUNITY claims may propose *drafting* PROPOSED_ACTION events, never executing.

## 2. Coppersmith proof sequence mapped to primitives

Nolan's required loop, each step bound to an existing primitive:

1. **Coppersmith object** → PING objects (`PingObject`: business, services, location, person, website, external identities) + relationships. Exists (`src/fyd/sitespec/types.ts`, `@/lib/ping/types`).
2. **FYD understands business** → evidence-bound Ask retrieval. Exists; evidence-boundary is the open product step.
3. **FYD generates site** → SiteSpec compiler + renderer. Exists (just closed: SOURCE → EVIDENCE → OBJECTS → SITE SPEC → RENDERER → BROWSER).
4. **Visitor asks question** → Ask FYD. Exists.
5. **FYD answers from evidence** → ask composer with citations + explicit unknowns. Exists.
6. **FYD identifies improvement opportunity** → NEW (small): an intelligence worker emits an OPPORTUNITY-kind claim with WHY + evidence_refs. This is the only new *behavior*; it uses the existing emit choke point.
7. **Owner sees WHY** → Mission Control projection reads the claim + its SUPPORTED_BY edges. Projection work only; no new tab (standing correction).
8. **Owner approves** → PROPOSED_ACTION → ACTION_APPROVED, under the P0 invariants (valid principal, required capability, exact proposal digest, tenant/owner match). Exists; boundary already hardened (commit 50983ded).
9. **Site changes** → Mission (`SITE_PATCH` type) → FYD OwnerProposal apply → regeneration. Exists.
10. **Action is recorded** → MISSION_COMPLETED + spine events. Exists.
11. **Future observation does not destroy it** → owner-override semantics: source stays evidence, owner correction is the governed current fact, regeneration preserves it. Exists (`owner-mode/`).

Rejection is first-class: REJECTED on a PROPOSED_ACTION is outcome evidence that feeds the next opportunity ranking (the order's "rejection is useful outcome evidence").

## 3. The candidate → outcome chain with PING authority insertion points

```
CANDIDATE                    (external data: Modash/Upfluence/HypeAuditor/public protocol.
                              NEVER truth. NEVER permission. NEVER automatic outreach.)
  ↓ [A] identity resolution
PING IDENTITY/OBJECT RESOLUTION  (dedupe, resolve to canonical objects; IdentityAuthority)
  ↓ [B] opportunity formation
OPPORTUNITY                  (OPPORTUNITY-kind claim, evidence-bound, ranked; §1)
  ↓ [C] action planning (only after approval)
ACTION PLAN                  (Mission row; causation → ACTION_APPROVED event)
  ↓ [D] capability check
CAPABILITY                   (does the actor/system hold required capability?
                              CapabilityAuthority; deny-by-default)
  ↓ [E] policy evaluation
POLICY                       (human policy governs; GovernanceAuthority)
  ↓ [F] human approval
APPROVAL                     (P0 invariants: principal, capability, exact digest,
                              tenant/owner match; operator is the authority)
  ↓ [G] bounded execution
PROVIDER ADAPTER             (typed tool, NOT YET BUILT — explicit non-goal of this lane;
                              when built: narrow, receipt-returning, swappable)
  ↓
RECEIPT                      (MISSION_COMPLETED + provider receipt payload)
  ↓
OUTCOME                      (OBSERVATION_CREATED measuring effect:
                              CTA moved → quote requests changed;
                              collab → visits/conversions;
                              recommendation → owner accepted/rejected)
  ↓
LEARN                        (new claims; opportunity ranking improves from REAL RESULTS)
```

This is the Upfluence pattern with PING inserted: Upfluence does natural language → typed tool → authorized action. FYD does intelligence → OPPORTUNITY claim → PROPOSED_ACTION → CAPABILITY → POLICY → APPROVAL → typed adapter → RECEIPT → OUTCOME. The adapter boundary is what lets Modash / Upfluence / HypeAuditor / open-protocol data / PING's own index be swapped without changing PING truth.

## 4. Progressive permission as a PING design principle

ATProto's lesson (granular resource/collection/action scopes + progressive requests) becomes standing PING principle:

> **Connect cheaply and read-only first. Request stronger capabilities only when the user asks FYD to do something requiring them.** Never "give FYD your entire account."

Gap proven (2026-09-30, read-only search): no `grant` vocabulary exists anywhere in `ping-runtime/approval/`, `ping-runtime/authorities/`, or `capabilities/`. The capability registry maps capability → intent → authority, and FYD `owner-mode/capability.ts` has typed verbs, but neither records a *scoped grant*.

Small vocabulary addition (no new authority; the human/tenant is the grantor, PING only records):

```
GRANT_ISSUED   { connection_id, principal, resource, collection, action,
                 expires_at, granted_by, causation_id }
GRANT_SCOPE_CHANGED  { connection_id, added: [...], removed: [...], reason }
GRANT_REVOKED  { connection_id, reason }
```

Progression example: `connection:read` (observation plane) → later, on user request, `follow:create` → later, on user request, `post:create`. Each step is a separate grant event; the adapter refuses any action outside the current grant set. This also bounds the observation plane: targeted subscriptions, filters, demand-driven backfill, rebuildable indexes — opportunity discovery, not surveillance.

## 7. Sequencing (design view; execution needs Nolan's word per item)

1. P0s first (separate lanes, already ordered).
2. OPPORTUNITY claim kind + emission behavior (smallest delta: one worker behavior + payload convention, riding `emit()`).
3. GRANT_* vocabulary (small: event types + adapter-side enforcement point).
4. Mission Control projection reads OPPORTUNITY claims with evidence (feed wiring; the stuck-missions wiring dependency — MC missions feed must read the PING journal — is the same class of work).
5. Coppersmith internal proof: three proposals from objects+evidence+relationships+capabilities only, no execution, owner chooses.
6. Only then: the same pipeline against external candidate sources, behind the (future) adapter boundary.
