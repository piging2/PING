## Verdict

**In scope, and largely already buildable without new inventions.** Claim-evidence *support* (the binding between a claim and stored evidence) is replayable today by composition: the lower half (stored bytes to evidence records) already has a single deterministic replay entry point, and the upper half (evidence records plus graph snapshot to claim-support verdicts) exists as pure, deterministic validators with typed fail-closed outcomes. What does not exist is the *combined* replay harness: one callable procedure that takes pinned inputs (graph snapshot, evidence corpus, claim set, supersession marks, viewer) and returns a support verdict per claim. That harness is a thin composition of existing functions, not a new subsystem.

The line that must not be crossed: **prose is not re-derivable**. Answer fragments (generated text bound to claim ids) can be re-validated against stored inputs, never re-generated byte-identically. Replay is *re-verification on pinned inputs*, not *re-generation*. Any replay procedure that claims to reproduce generated prose deterministically would be false.

## The actual machinery (all file:line citations)

### Half 1: stored bytes to evidence records (replay entry point already exists)

`~/workspace/fyd-build/src/fyd/acquisition/validate-chain.ts` implements `resolveAcquisitionChain` (line 375), a full mechanical walk:

- Hop 1, `verifyAcquisitionBytes` (line 210): `sha256(stored bytes) == acquisition.contentDigest` and byte-length match against the acquisition record loaded from `evidence/acquisition-<slug>-2026-09-22.json` (`loadAcquisitionRecord`, line 138; `loadSourceBytes`, line 188). Fail closed on `digest_mismatch`, `byte_length_mismatch`, `missing_source_bytes`.
- Hop 2, `bindObservationsToAcquisition` (line 309): every observation in `evidence/observations-<slug>-2026-09-22.json` (`loadObservations`, line 241) must have `sourcePointer == "web:" + acquisition.contentDigest` and a matching `sourceUrl`; otherwise `dangling_source_pointer`.
- Hop 3, `observationsToEvidenceEntries` (line 349): maps parsed observations into the ask lane's `ResolvedEvidence` record shape. The stored corpus at `~/workspace/fyd-build/evidence/` confirms the record layout (acquisition record: contentBytes/contentDigest/contentType/method/methodVersion/retrievedAt/sourceUrl/storedAt; 6 observations per site with observationId/name/value/observationType/sourceUrl/sourcePointer/observedAt/extractor).

The module header states the replay-relevant contract plainly: "No generated prose is ever treated as acquisition here: bytes that do not hash to the acquisition's contentDigest cannot back any evidence."

The ask lane's evidence record shape is `ResolvedEvidence` at `~/workspace/fyd-build/src/fyd/ask/types.ts` (line 29): ref, kind (`observation` | `acquisition`), observationId, sourceUrl, sourcePointer (`"web:sha256:<digest>"`), observedAt, extractor, summary, plus FYD-013 versioning fields: `evidenceVersion`, `supersededBy`, `supersededAt`, `supersedingVersion`.

## The replay procedure (sketch)

Given a stored graph snapshot G, a stored evidence corpus E, a stored claim set C, a stored supersession-mark set M, and a pinned viewer V, replay claim-evidence support as follows:

**Step 0. Pin the snapshot.** Re-run `graphSnapshotPin(G)` (ask/snapshot.ts:73) and require equality with the snapshot pin recorded at composition time. If the pin mismatches, stop: the replay is not against the graph the claims were made on, and any verdict would be ungrounded. This is the deterministic identity of "the graph snapshot."

**Step 1. Re-derive the evidence records from stored bytes.** Run `resolveAcquisitionChain(slug)` (acquisition/validate-chain.ts:375) over the stored corpus files. This re-verifies sha256 of stored bytes against the acquisition record, binds every observation's sourcePointer to the acquisition digest, and emits `ResolvedEvidence[]`. Any typed error (`digest_mismatch`, `dangling_source_pointer`, missing hop) fails the whole replay closed. Note the corpus currently on disk is the committed V1 set; the site slug and corpus version must be pinned inputs, because evidenceVersion semantics (FYD-013) distinguish the V1 corpus from regen-emitted versions.

**Step 2. Re-apply supersession.** Run `applySupersededMarks(records, M)` (evidence/refs.ts:161) with the stored mark set M (the regen result's `supersededObservations`; regenerate.ts:244). Marks are metadata input, not mutation of observations. First mark wins on duplicates; record ordering must be preserved because index construction is first-wins on duplicate ids.

**Step 3. Rebuild the evidence index.** Run `buildEvidenceIndex(records, graph)` (evidence/refs.ts:92). Loader "acquisition" placeholders must never back a citation; the index excludes them by construction, and the replay must fail any claim whose only resolution is a placeholder (circular evidence).

**Step 4. Re-run claim validation.** Run `validateClaims(C, evidenceLookup)` (claims/claims.ts:265). This re-checks text non-empty, vocabulary membership, evidence-ref presence for DIRECT/DERIVED, ref resolution, non-supersession, and the DIRECT admission rule. The result is a typed verdict per claim set; any failure is recorded as a gap, never downgraded.

**Step 5. Re-run citation binding against the graph.** For every citation ref in C, run `validateEvidenceRef(ref, {index, graph, viewer: V})` (evidence/refs.ts:192). This adds what `validateClaims` cannot see: the digest match between the record's `sourcePointer` and the citing object's `fields.source_digest` (wrong_snapshot), the visibility gate (hidden_evidence), and the graph anchoring (the record must actually be cited by an object in G).

**Step 6. Re-run presentation bindings.** For every presented field binding, run `verifyPresentationBinding(binding, G)` (sitespec/graph.ts:146). Omit on failure; the replay records the omission as a gap rather than treating the value as supported.

**Step 7. Compare verdicts.** The replay's support verdict for each claim is the conjunction of steps 4 and 5 (plus step 6 for presented values). Compare against the verdict recorded at composition time. A mismatch is a replay failure with a typed reason, not a silent pass.

## What is deterministic

- Everything in steps 0-7 is a pure function over pinned inputs: sha256 over bytes, canonicalization with sorted keys, map construction with first-wins rules, verbatim-then-tail ref resolution (refs.ts:127 `resolveRecord` mirrors the composer's findEvidence order), and typed fail-closed validators. The three modules each declare purity in their headers: claims.ts "No LLM calls, no network, no semantic truth judgment"; refs.ts "pure and deterministic: no network, no clocks, no randomness"; graph.ts `verifyPresentationBinding` "Pure and deterministic: no clock, no randomness, no I/O."
- The failure taxonomy is typed and deterministic: `digest_mismatch`, `dangling_source_pointer`, `wrong_snapshot`, `dangling_evidence_ref`, `superseded_evidence`, `hidden_evidence`, `direct_admission_failed`, and the claim-validation reasons. Replay failures are therefore diagnosable, not mysterious.

## What is NOT replayable (treat as pinned-input regression)

1. **Generated prose is not re-derivable.** `bindAnswerFragment` binds prose to validated claim ids, but the prose itself is the output of a non-deterministic generator. Replay must re-validate the stored prose's bindings against stored evidence; it must never re-generate prose and expect identical text. Do not claim LLM generation is deterministically replayable.
2. **Acquisition is not replayable from evidence alone.** Step 1 re-verifies *stored* bytes against *stored* digests; it does not re-fetch the source. If the stored bytes are absent, the chain fails closed (`missing_source_bytes`), which is the honest outcome, not a retry trigger.
3. **Viewer dependence is by design.** `validateEvidenceRef` takes an AskViewer; a replay pinned to a different viewer legitimately yields different verdicts under the FYD-010 visibility policy. The viewer must be a pinned replay input, and the verdict must record which viewer it is valid for.
4. **Supersession marks are inputs, not derivations.** Replay re-verifies that marked records fail closed; it cannot re-derive which records *should* be marked without re-running the regen lane on a new acquisition. M must be stored alongside the regen result that produced it.
5. **Claim text is validated, not re-derived.** `validateClaims` checks the stored claim's text and classification; the composer's choice of claim text (currently `object.title`) is not canonically re-derivable from the graph if object titles change between corpus versions. Replay is re-verification, not re-composition.
6. **Insertion-order dependence is real but pinned.** First-wins rules (buildEvidenceIndex, applySupersededMarks, evidenceLookup, findEvidence) depend on record order. The replay pins the `inOrder` sequence; re-sorting records would change verdicts, so the corpus file ordering is part of the pinned input.

## Gaps

1. **No combined replay entry point.** `resolveAcquisitionChain` replays bytes-to-evidence; the claim-support validators are wired into the composer (`answer.ts:214`) and visitor (`visitor.ts:78`) paths, but there is no single callable that takes (graph snapshot, evidence corpus, claim set, marks, viewer) and returns per-claim support verdicts. The harness is a composition exercise, but it does not exist yet.
2. **Supersession marks have no canonical stored home on the ask path.** `applySupersededMarks` (evidence/refs.ts:161) is exported and pure, but has no callers in `src/fyd/ask/`; the regen lane's marks live in `RegenerateResult.supersededObservations` (regenerate.ts:290). A replay needs the mark set stored and versioned alongside the corpus it applies to; that storage contract is unwritten. This matches the known OPEN item `evidence-freshness-supersession` (binding against superseded evidence still OPEN, see FYD-013).
3. **Claims are not persisted as stored evidence.** `validateCitations` validates at compose time; there is no durable claim store keyed to a snapshot pin. A replay today would need claims captured from the composition run (or re-run through the composer, which re-enters generation nondeterminism for the prose). Related but separate: `askfyd-outcome-history` (P3 OPEN) is the contract that would give claims a durable home.
4. **Corpus versioning is convention, not enforced.** `evidenceVersion: 1` is assigned by `observationsToEvidenceEntries` (validate-chain.ts:349) for the committed V1 corpus; regen bumps the version. Nothing pins which corpus version a given graph snapshot's claims were made against except the object's `fields.source_digest`. A replay harness must carry the corpus-version pin explicitly.
5. **Envelope location vs backlog wording.** `evidence-observation-envelope` is recorded DONE_VERIFIED with the envelope "in the evidence module," but `src/fyd/evidence/` contains only `refs.ts`; the source-bytes-hash plus digest binding actually lives in the acquisition chain (`validate-chain.ts`) and the digest convention in `refs.ts`/`ask/types.ts`. The capability is proven; its documented home is not where the backlog says. Minor, but a replay-harness author should look in the acquisition module, not the evidence dir. (Cited as location only; no identity-semantics analysis undertaken.)
6. **Two index-building paths with subtle differences.** The composer's `findEvidence` (answer.ts:87) and the validator's `resolveRecord` (refs.ts:127) implement the same verbatim-then-tail resolution order, but the composer has its own null-guard for the business object while the validator uses `BUSINESS_CITATION_REF` (refs.ts:55). A replay that only re-runs one path could diverge from the other. The replay harness should run both the composer-resolution and the validator-resolution over the same inputs and require agreement (the refs.ts header documents that the resolver "mirrors the composer's findEvidence resolution order," which is a claim worth testing rather than assuming).

## Recommendation

Answer the scope question as **IN SCOPE**: evidence replay (given a graph snapshot, re-derive the evidence chain deterministically) is feasible and mostly already implemented in separable, proven pieces. The correct scoping is narrow:

- In scope: a deterministic replay harness composing steps 0-7 above, returning typed per-claim support verdicts over pinned inputs. It verifies, never regenerates.
- Out of scope (by construction): re-derivation of generated prose, re-acquisition of source bytes, re-derivation of supersession marks, and any touching of canonical-byte or identity semantics (frozen, crew-adjacent).

The natural sequencing: first close gap 2 (stored, versioned mark set on the ask path; owned by the FYD-013/freshness work) and gap 3 (durable claim records keyed to snapshot pins; related to `askfyd-outcome-history`), then the replay harness is a composition task with no new subsystems. Gap 6 (dual resolution-path agreement) should be asserted by a test before the harness trusts it.
