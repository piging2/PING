## 2. Smallest closed-loop design (existing capabilities only)

Loop: **SIGNAL → OPPORTUNITY → RECOMMENDED MISSION → AUTHORIZATION → EXECUTION → RECEIPT → OUTCOME → NEW EVIDENCE → LEARNING**

Design law: Opportunity is a **derived, evidence-backed projection computed server-side at read time** — never a stored object, never an authority. React holds view-state only (tab, expanded, filter, pending draft input). All truth lives behind API routes; mutations are commands returning `eventId`s; the UI refetches projections after every command. No optimistic canonical state.

| Stage | Existing capability it maps to | What it is (no new backend) |
|---|---|---|
| SIGNAL | Journal overlay events; technology probes; Ask answer states | `GET /events/FYD_SITE_OVERLAY` (what changed), `/api/mc/technology` (risks/incidents: e.g. no DB backup UNWIRED, unhealthy healthchecks OBSERVED), `POST /api/fyd/ask` returning `answerState: UNKNOWN/CONFLICTED` (knowledge gaps as signals) |
| OPPORTUNITY | Technology-route DERIVED risks (template) + competitive-signal-pass discipline ("LLM generates candidates; deterministic machinery decides"; terminal states PASS/NO_VALUE/BLOCKED/FAILURE; never writes to PING) | Server-side composer: signals in → deterministic gates (evidence refs present, claim grade ≥ DERIVED, not a duplicate of a live journal resolution) → opportunity cards `{ title, whyItMatters, evidenceRefs[], claimGrade, freshness }`. Recomputed per request. NO_VALUE/BLOCKED terminal states render honestly. |
| RECOMMENDED MISSION | Ask pipeline `suggestedActions` + draft `AskProposal` (already returned by `POST /api/fyd/ask`); staging `today` "Needs your authority" card (GRILLING-BRIEF.md questions) | Mission = recommended action attached to an opportunity: `{ action, target, draftProposal?, suggestedActions[], rationale }`. Drafts generated by the existing ask-pipeline machinery; the draft is local until submitted. |
| AUTHORIZATION | `POST /api/ping/proposal` + `/o/[objectId]/manage` approve/reject pattern | Proposal card reusing the exact governed path: digest re-verified, owner-gated, 409 STALE_PROPOSAL semantics. Approve → `{ eventId }`; reject → "nothing changed". Cross-object queue is a read-model over the journal tail (see gaps). |
| EXECUTION | `submitSignedEvent` → `emitOverlayEvent` → journal append | The approved proposal executes through the one governed write. For non-FYD actions (outreach passes, fleet work): execution stays in its existing machinery (cron/intent ledgers); MC **reads** its ledgers, never duplicates execution. |
| RECEIPT | `{ eventId }` + journal GET | Receipt card: `GET /events/FYD_SITE_OVERLAY` filtered to the returned `eventId` → renders the journal envelope (event_id, timestamp, ops, tenant). |
| OUTCOME | Truth-display rule (staging agents route): timeouts never render FAILED; proven-fail vs unknown-outcome distinguished | Read-back: re-run the probe that produced the signal (technology probe, overlay tail, ask re-query) → outcome graded PROVEN/OBSERVED/DERIVED/UNKNOWN with the existing claim vocabulary. |
| NEW EVIDENCE | The journal event itself | Overlay ops carry before/after; citations attach. The receipt *is* the new evidence; it feeds the next SIGNAL pass automatically. |
| LEARNING | Outreach `angle-performance.md` (signal→angle→channel→response→outcome, per-prospect) as the established pattern | Read-model over the journal tail: per-tenant, per-action-type counts of approved / rejected / stale proposals and post-approval outcome grades. Derived projection; no store. Answers "which recommendations were worth authorizing" without a new authority. |

### Why this is the smallest

Every stage reuses a capability that was observed working this session (or recorded verified 2026-09-24 with a restoration spec in staging). The only new code is two read-side routes and one tab; the authorization write path is untouched and reused verbatim. The loop closes because EXECUTION's output (journal event) is SIGNAL's input (overlay tail) — the journal is the single integration point, and it already exists.

## 4. Open questions and candidate gaps (with evidence)

- **Q1. Where does "needs authority" queue durably?** The staging `today` route read active questions from `GRILLING-BRIEF.md` (a markdown file, verified present on the Pig). A markdown file is not a queue. `proposal_decision` (owner-signed approval variant) is a recorded BACKLOG OBJECT (STATE.md 2026-09-24), not built. Candidate gap: a durable pending-authorization list has no backend; do not fake it with a JSON file that two writers can corrupt.
- **Q2. Cross-tenant proposal enumeration is missing.** `POST /api/ping/proposal` writes; `/o/[objectId]/manage` reads per-object. There is no list endpoint, and the journal gateway only serves `FYD_SITE_OVERLAY` event GETs. An MC-wide "pending approvals" view cannot be built on reads that do not exist — it needs a journal query capability, not a new store.
- **Q3. Non-FYD mission execution has no authorization seam.** Outreach/fleet work executes via workspace crons and intent ledgers (`action-intent-ledger.jsonl`), outside any governed approval path. If MC is to authorize those missions, the authority boundary is undefined. Until defined, MC must stay read-only over them (projection, not control).
- **Q4. ORCA reconciler contract still open.** Per-operation fields (idempotencyKey, reconciliationState, retryEligibility, criticality, authorityRequirement) were null pending the port lane; controls (hold/resume/cancel/retry) are withheld by law until witnessed mutation exists. The AGENTS tab cannot show reconciliation truth until that contract lands — it must keep showing PROTOTYPE badges, not guesses.
- **Q5. SiteSpec forward trace is backend-blocked.** `registerSiteSpecProvider` has zero callers (STATE.md backend survey 2026-09-24); digest-bound SiteSpec verification 400s. Mission evidence for site changes stops at the graph digest — acceptable for the loop, but the forward-trace leg is capped until the factory calls the provider.
- **Q6. `OBSERVATION_CREATED` does not exist.** Outcomes are observable only by re-probing. If the loop needs typed outcome events (for learning beyond re-reads), that event type is a backend addition — flagged, not designed here.
- **Q7. Which `/mission-control` is canonical?** Live = technology surface; staging = operations surface. Restoring staging routes without resolving this creates two competing definitions of Mission Control (duplication hazard). This needs the adjudication call before any writer touches the page.
- **Q8. Learning labels are thin.** The learning read-model counts approvals/rejections/staleness, but "did the authorized action actually help" requires outcome re-probes that may not exist for every action type (e.g. owner corrections have owner feedback; infra fixes have probes; marketing actions have none in-repo). Learning quality is bounded by probe coverage — record the bound in the UI, do not smooth over it.
