## 3. Proposed ONE HOLD semantic

> **UNKNOWN-PARK:** a dispatch transition whose consequence classification includes the possibility that a side effect occurred (anything at or past the pre/post side-effect boundary per `classifyDispatchOutcome`) → the unit of work is PARKED in a durable, scheduler-invisible, reaper-honoring hold; no automatic path may make it dispatchable again. The ONLY exits are (a) a recorded operator decision (append-only audit trail; `release`-family → re-enter only via the conditional-claim path, never direct dispatch; `fail`-family → terminal), or (b) an idempotent-keyed reconcile against newly recovered durable evidence (same op_key; can only execute-or-recover, never duplicate). Pre-boundary failures (dispatcher never ran, boundary never crossed) are NOT holds: bounded re-plan stays valid.

Rationale:
- Every live implementation agrees on the invariant: "no automatic path turns UNKNOWN dispatchable" (H1: timeout never FAILED, no auto retry; H2: reaper/claim/reclaim all exclude held; H3: blocked never auto-claimed; H4: held invisible to pending/reaper). The convergence is naming the one invariant and making it row-visible and reaper-honored, which only H2 does end to end at the mission layer.
- The pre/post-boundary distinction (H3's `classifyDispatchOutcome`, gauntlet-accepted) is the classification the canonical path lacks (H1 treats every timeout as one UNKNOWN_EXECUTION). Without it, pre-boundary transport failures are needlessly parked and post-boundary timeouts are indistinguishable.
- The release path must be a recorded decision with an audit trail (H2 `decisions` JSONB, H3 `decisions` log) because operator toil is the cost of the semantic, and the toil must be evidence, not state mutation.
- The crash-ordering discipline (block/hold-record BEFORE the state claim) must be part of the semantic, not an implementation detail: H2's `setHeld`-before-emit and H3's block-before-state are the same law at different layers.

Representation recommendation (for coordinator adjudication): adopt H2's shape — `held` boolean flag + `hold_reason` + `decisions` JSONB on `ping_missions` — over H4's `status='held'`, because (i) the flag survives a manual/errant status reset (harvested test #5; a `status='held'` row silently un-holds if anyone writes `created`), (ii) `reapExpiredLeases`/`assign`/`reclaimRetryPending`/`findStuckRunning` all honor it explicitly with recorded skips, and (iii) terminal states stay in the status column, so 'held' is never confused with a lifecycle state. H4's `EFFECT_HELD` event, `escalateHold()`, op-key idempotency gate, and `sweepUnknown` feed into this semantic at the effect layer; H4's `hold()`/`resumeHeld()`/`getHeld()` row API is retired as an authority (superseded), its tests absorbed as the effect-level acceptance suite. H3's `orca_unknown_block.js` is retired as an authority candidate and kept only as ORCA's consumer-side guard until ORCA work orders flow through MissionRuntime (per the prior harvest recommendation) — it must not define competing HOLD truth, and no ORCA code takes over scheduler/reaper authority. H5 is renamed (not a HOLD). H6 is out of scope.
