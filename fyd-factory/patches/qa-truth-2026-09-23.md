## P-1: Footer provenance must read spec.provenance, never a hardcoded string
File: src/app/sites/_shared/site-client.tsx (around line 169)
Problem (F-001): the footer hardcodes "(acceptance sequences 65-83)" for every
site. It is false on /sites/coppersmith-plumbing (eventSequences is undefined).
The generator already emits the true provenance at spec.provenance
(source, claimKind, eventSequences, note); the renderer ignores it.
Proposal:
- Replace the hardcoded sentence with a render of spec.provenance:
  "Generated by FYD Social from a {source} object graph{eventSequences ? ` (acceptance sequences ${a}-${b})` : ""}. {note}"
- Fail closed on the display: when eventSequences is absent, omit the
  parenthetical entirely rather than printing a placeholder.
- Add a unit test asserting the footer contains no acceptance-sequence numbers
  when spec.provenance.eventSequences is undefined, and the exact pair when
  present.
- Optional hardening: a CI grep that fails if the literal "acceptance sequences"
  appears anywhere outside the generator/provenance types.

## P-2: Rights-basis wording must not claim authorization; label it inferred
Files: src/fyd/media/discover.ts (classifyRights), src/fyd/components/renderer.tsx:1673
Problem (F-002): classifyRights emits "authorized for acquisition and derivative
generation for this demo" from a URL heuristic (same origin, not a logo of
another brand). The renderer then labels that step state "observed", so the
page presents a policy inference as a seen-in-the-source fact, and the word
"authorized" asserts a legal permission no evidence supports.
Proposal:
- Change the public-demo-source basis sentence to a policy statement, e.g.:
  "Same-origin imagery from the business site. FYD's demo policy treats this as
  acquisition-eligible for this demo; this is not a legal determination and FYD
  claims no copyright. Caching or deriving this asset does not transfer rights;
  the business (or its site licensor) retains all rights."
- In renderer.tsx GalleryMediaWhyThis (and the hero equivalent), push the
  rights-basis step with state "inferred", not "observed". The URL and the
  observedAt/digest stay "observed"; only the rights call is inferred.
- Consider adding a RightsCall.reason field naming the heuristic rule that
  fired (same-origin / off-site / logo-like), so the drill-down shows its
  work instead of a bare conclusion.

## P-3: Stop rendering evidence state "observed" as "Verified"
File: src/fyd/components/contact-link.tsx (compactProvenanceLine, lines 56-78)
Problem (F-003a/b): state "observed" renders as "Verified from X", which
contradicts the same page's footer ("never verified fact") and overclaims:
being seen on the source site is not independent verification.
Proposal:
- Map "observed" to "Seen on {receipt}{count}" (e.g. "Seen on
  coppersmithplumbing.com, 1 source").
- Reserve the word "Verified" for a future evidence state that actually means
  independently confirmed (none exists today; the verification seam's only
  implemented method is operator attestation).
- Keep "Inferred from", "Unverified", etc. as-is; they are honest.

## P-4: Route the /sites demo path through the verification seam (architectural)
Files: src/app/sites/coppersmith-plumbing/page.tsx,
src/app/sites/happy-place/page.tsx, src/fyd/builder/planner.ts
Problem (R-A): buildVerifiedRenderModel / assertSpecBindingsVerified are invoked
only from planSite (used by /build/[siteId]). The /sites demo pages call
generateSiteSpec directly, so the BindingVerifier's verdicts are unavailable
for every claim on the audited pages. The fail-closed emission gate the
architecture promises does not cover the pages users actually see in the demo.
Proposal (pick one):
- (a) Have the /sites pages call planSite (or a shared buildVerifiedSpec
  helper) instead of generateSiteSpec, so every emitted spec passes through
  the verifier; or
- (b) Add an explicit, documented exemption: if /sites stays on the direct
  path, the page must render a visible "unverified render path" marker and the
  decision must be recorded in FYD-DECISIONS, because the current code comments
  ("The spec is validated before render. An invalid spec never renders.")
  imply a guarantee the verifier does not actually provide on this path.
- Either way, extend the binding model (or a parallel renderer-string audit)
  to cover renderer-injected factual strings (R-B): footer provenance,
  rights-basis steps, and provenance wording. A verifier that cannot see a
  claim cannot fail closed on it.
