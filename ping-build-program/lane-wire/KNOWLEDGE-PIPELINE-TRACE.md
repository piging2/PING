## Hop 0: POST /ingest -> 201 (contract in ingest-route.js + canon-svc.js + emit)

For each envelope the gateway returns:
`201 {status: "ok", eventId, objectId, canonicalHash, canonicalVersion, namespace: "core::owner"}`

- `eventId = sha256(JSON.stringify({eventType, source, namespace, logical_id}))`
  — content-deterministic; the same logical observation always hashes to the
  same eventId (the duplicate-delivery safety proven in ingest-sim.mjs).
- `objectId` = the canonical object's id from `createCanonicalObject`
  (kind = eventType, authority = source).
- The journal row lands in `ping_events(event_id, event_type, source, timestamp,
  payload, metadata, namespace)` where `metadata` carries `confidence`,
  `lifecycle_stage`, `evidence[]`, `canonical_hash`.

Both envelopes use registry-validated types (OBJECT_CREATED x 2,503 envelopes
checked against the 233-type registry; negative probe NOT_A_REAL_TYPE -> 422).

## Hop 1: lane J RunRecord (observability) — by run_id + observation_ids

Join contract (lane-j OBSERVABILITY-DESIGN.md §5, proposed to N/BCQ):
- observations carry `run_id` (the connector run lease that emitted them);
- the RunRecord carries `observation_ids` (the logicalIds/eventIds it produced);
- `before_event_id` / `after_event_id` are the canonical spine eventIds when mapped.

Reachability for the two envelopes:
- Git: run_id `run-git-ingestor-<cursor-range>`; the RunRecord for the
  OLD HEAD -> NEW HEAD sweep records discovered/accepted counts; the git commit
  envelope's eventId appears in `observation_ids` and as `after_event_id` of the
  ref's previous head state.
- GitHub: run_id `run-github-connector-<attempt>`; RunRecord carries
  discovered/accepted/rejected, bytes, cost, rate-limit hits; the issue
  envelope's eventId in `observation_ids`.
- Queries answered: `runs(source, time)` ("what has github-connector done this
  week?"), `changes(run_id)` (temporal diff with before/after eventIds),
  `whyDidThisChange` entry point hands the (entity, field) to lane O's index.
- By which IDs: `run_id` (correlation), `observation_ids[]` (logicalIds/eventIds),
  `source` ("git-ingestor:lane-a" / "connector:github-connector:lane-conn").

## Hop 2: lane N lineage (tracer.ts) — by sourceKey + causedByEventId

Chain (lane-n LINEAGE-DESIGN.md): SOURCE -> ACQUISITION -> OBSERVATION ->
EVIDENCE -> OBJECT -> SITE SECTION -> ANSWER -> ACTION. Every edge carries
`causedByEventId` = the canonical event id from the 201 response (never forged).

- Git envelope: SOURCE node `sourceKey = "git:<remote>#<path>"` (the PING repo);
  ACQUISITION node = {connectorId: "git-ingestor:lane-a", runId, contentDigest:
  packet evidence sha256}; OBSERVATION node id = logicalId
  `git:commit:<sha>`; EXTRACTED edge causedByEventId = the 201 eventId.
  The commit_parent envelope (`git:parent:<sha>:<parent>`, RELATIONSHIP_CREATED)
  becomes the RESOLVED edge between the two commit OBJECT nodes.
- GitHub envelope: SOURCE node `sourceKey = "github:<owner>/<repo>"`;
  OBSERVATION node id = `obs_github-connector_<32hex>`; causedByEventId = eventId.
- Queries answered: `traceClaim` 7-stage machine trace (source bytes ->
  observation -> evidence -> object field -> sitespec binding -> rendered claim
  -> Ask FYD answer), `whyDidThisChange(objectId, field)` walks MATERIALIZED
  edges with `eventId` + `causedBy`, `whatBreaksIfSourceDisappears(sourceKey)`
  reverse-walks to impacted objects/sections/answers.
- By which IDs: `sourceKey`, observation `logicalId`, `causedByEventId` (= eventId),
  `objectId` (the canonical object from the 201).

## Hop 3: lane F object search — by id tier + sourceIdentity

Deterministic tiers (lane-f OBJECT-SEARCH-DESIGN.md), ordered id > url > phone >
source > name:

- Tier 0 exact-id: the envelope `logicalId` is the id-tier key.
  Git: `git:commit:<sha>` / `git:ref:<refname>`; GitHub: `obs_github-connector_<32hex>`.
- `exact-source` rule: provider + providerId equality over connector observations.
  GitHub: {provider: "github-connector", providerId: source_record_id (the issue id)};
  git: {provider: "git-ingestor", providerId: repo_slug + ref}.
- Source/URL/name tiers: `source` field ("git-ingestor:lane-a",
  "connector:github-connector:lane-conn"), payload text (commit message, issue
  title), `event_type` + `namespace` filters over the journal.
- By which IDs: `logicalId` (id tier), `{provider, providerId}` (exact-source),
  `eventId`, `source`, `event_type`.

## Hop 4: lane G Ask FYD context compiler — by objectId + evidenceRefs

(lane-g CONTEXT-COMPILER-DESIGN.md): question + viewer + target object ->
ContextPacket {relevant objects, relationships, evidence, capabilities,
visibility} -> model; `toAskFydAnswer` emits [n] markers aligned with evidenceRefs.

- The compiler's evidence-source adapter reads objects whose evidence chains
  include the two envelopes' `evidence[]` sha256 refs and the `eventId`s.
- A question like "what changed in the repo this week?" resolves the git
  commit OBJECTs by objectId (from the 201s), pulls their evidence items
  (provenance-carrying, newest first), and cites them as [n] markers.
- A question like "what issues are open on the repo?" resolves the GitHub
  issue objects the same way; confidence grades (DIRECT 1.0 vs INFERRED 0.5)
  flow through AskEvidenceRef classification.
- By which IDs: `objectId` (201 response), `evidenceRefs[]` (envelope evidence
  sha256s + eventIds), `sourceExcerpts` bounded raw text behind the evidence.
