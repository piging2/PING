## Defects (actionable)

**D1. Non-conforming ledger line (schema).** Line 116 of `fleet/ledger.jsonl` uses a different schema (`ts`/`results`/`notes`, no `missions`/`verdicts`/`at`) than the other 205 lines. Content is valid (fleet-be-1, backend 0351-0400, results PROVEN 17/ADAPT 16/REJECTED 17) but any parser expecting the canonical schema will misread it. Path: `fleet/ledger.jsonl` line 116.

**D2. Missing result + verdict mismatch, acquisition 0051-0100.** `fleet/results/acquisition/ACQ-0100.json` does not exist; the final drain (line 5, fleet-acq-2, ledger claims PROVEN 50) therefore only has 49 files on disk and its count cannot reconcile. Either the result was never written or the file was lost. Paths: `fleet/results/acquisition/ACQ-0100.json` (absent), `fleet/ledger.jsonl` line 5.

**D3. Double-drains with conflicting verdicts (3).** Same (category, matrix, range) drained twice with different results:
- `oracle/oracle-v2/2951-3000`: line 109 fleet-ora-2 ADAPT 50 (at 05:00 UTC) vs line 115 fleet-acq-2 PROVEN 50 (at 03:48 UTC). On-disk JSONs are PROVEN 100 for 2951-3000+3051-3100 with fleet-ora-2 evidence files, i.e. disk agrees with acq-2's verdicts but carries ora-2's evidence. The ledger's append order and timestamps disagree here (ora-2's lines were appended earlier but carry later, future timestamps), so which drain is authoritative is ambiguous and needs reconciliation.
- `oracle/oracle-v2/3051-3100`: line 114 fleet-ora-2 ADAPT 50 vs line 121 fleet-acq-2 PROVEN 50. Same situation.
- `oracle/default/1651-1700`: line 70 fleet-ora-1 NEEDS-FOLLOWUP 50 vs line 102 fleet-ora-1 PROVEN 50, same worker, note says "RE-DRAIN per coordinator directive 2". Legitimate re-drain, but the ledger has no supersession marker; a reader sees two conflicting drains.
- Benign (confirmed, not a defect): `oracle/default/0551-0600` double-append, lines 39-40, fleet-ora-2, identical verdicts both times.

**D4. v3 redrain incomplete: 12 ranges (600 missions) with no `matrix=oracle-v3` ledger entry.**
- `1301-1350, 1351-1400, 1401-1450, 1451-1500, 1501-1550, 1551-1600, 1601-1650, 1651-1700, 1701-1750` (450 missions): drained only under the default matrix (v1/v2 era); redrain claim files exist in `fleet/inprogress/` (fleet-ora-2 holds 1301-1350, 1401-1450, 1451-1500, 1501-1550, 1551-1600, 1601-1650, 1701-1750; fleet-ora-1 holds 1651-1700; fleet-po-1 holds 1351-1400) but no v3 ledger lines yet. In-flight or stalled.
- `2701-2750, 2751-2800, 2801-2850` (150 missions): drained by fleet-ora-1 with notes explicitly describing oracle-v3 content ("oracle-v3 resource-exhaustion..."), and on-disk verdicts match those ledger lines, but the ledger entries lack `matrix: oracle-v3`, so they are invisible to a matrix-filtered coverage query. Cosmetic tag defect; the work itself verifies.
- Stale claim files for the redrain sit unclaimed: `fleet/claims/oracle-v3-redrain/oracle-v3-redrain-2701-2750.claim`, `-2751-2800.claim`, `-2801-2850.claim`.

## Warnings (hygiene, no data loss)

**W1. Evidence path typo in 18 oracle results.** Files `ORA-0974, ORA-0986, ORA-0988, ORA-1964, ORA-1974, ORA-1988, ORA-1998, ORA-2073, ORA-2079, ORA-2095, ORA-2098, ORA-2109, ORA-2114, ORA-2140, ORA-2145, ORA-2858, ORA-2890, ORA-2897` (in `fleet/results/oracle/`) cite `fleet/work/fleet-ora-2/sandbox/store-loss-drill.sh`, which does not exist; the real file is `fleet/work/fleet-ora-2/sandbox/tree/store-loss-drill.sh` (missing `tree/` segment). Evidence exists, paths are wrong.

**W2. URLs cited as evidence files (24 samples).** Connector results cite `https://...` documentation URLs inside `evidence_files` (e.g. `fleet/results/connector/CON-0001.json` cites a HubSpot docs URL). A URL is a citation, not a file; harmless but the field is named for files.

**W3. Stale unclaimed claim files overlapping ledgered ranges (30).**
- `fleet/claims/oracle-v2/oracle-3101-3150.claim` through `oracle-3701-3750.claim` (13 files): the oracle-v2 matrix was superseded by the v3 redrain; ranges were drained under v2/v3 ledger entries but the claim files were never claimed or moved to `fleet/claims/oracle-superseded/`.
- `fleet/claims/acquisition/2151-2200.claim`, `2201-2250.claim`, `2251-2300.claim`, `2301-2350.claim` (4 files, all 0 bytes): same ranges were drained by fleet-acq-2 (ledger lines, PROVEN 50 each) and duplicate claim copies sit in `fleet/inprogress/fleet-acq-2/`. The claims-dir copies are empty; the protocol's atomic `mv` was evidently not used (copied, not moved).

**W4. In-progress claims overlapping ranges already ledgered by a different worker (3).** `fleet/inprogress/fleet-acq-2/0401-0450.claim` overlaps acquisition 0401-0450 ledgered by fleet-acq-1 (duplicate-work risk); `fleet/inprogress/fleet-ora-1/v2-2851-2900.claim` overlaps 2851-2900 already ledgered under both oracle-v2 and oracle-v3. The other 292 inprogress-vs-ledger overlaps are same-worker leftovers (workers do not clean up claim files after draining), which is noisy but expected.

**W5. 70 ledger lines carry future timestamps** (max `2026-09-24T12:10:00Z`, ~8h ahead of the audit). Rounded values (e.g. `05:22:00Z`) suggest batch-written or clock-skewed entries. Consequence: ledger append order and `at` timestamps disagree (see D3), so "latest drain" is ambiguous without a documented tiebreak.
