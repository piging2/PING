# Resource-exhaustion cases 5/6/7 designs (fleet-ora-1, 2026-09-24 UTC)

## case 5: journald cap (SystemMaxUse) design — REVIEWED
Current state (read-only, ping-core-01): journald 440MB, no SystemMaxUse cap.
Reviewed design (applies at next provision / staging clone; editing live journald.conf
is host mutation and is NOT done here):
  /etc/systemd/journald.conf: SystemMaxUse=200M, SystemKeepFree=500M,
  MaxRetentionSec=30d, MaxFileSec=7d
Rationale: 200M cap bounds the 432MB slow fill; KeepFree protects the 45GB disk;
30d retention keeps forensics for incident review without unbounded growth.
Review checklist: cap < 1% of disk; retention covers incident window; change is
config-as-code (checked in), not hand-edited.

## case 6: log rotation 10m x 5 (proposed compose) bounds log growth — DEMONSTRATED
Design: docker json-file log driver options per service:
  logging: {driver: json-file, options: {max-size: "10m", max-file: "5"}}
Bound math: 10m x 5 = 50MB retained + 1 active file = <= 60MB per container, hard bound
regardless of log rate. Mechanics demonstrated sandbox-local with Python's
RotatingFileHandler (1MB x 5 analog): after 20000 log lines, 5 files, 4.3MB total,
bound (6MB) held. Same rotation mechanics as the json-file driver (size-triggered
rotation with fixed backup count).
