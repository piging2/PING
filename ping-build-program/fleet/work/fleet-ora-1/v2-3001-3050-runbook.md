# Slow-queries staging runbook (fleet-ora-1, 2026-09-24 UTC)

For oracle v3 missions ORA-3001..3050 (slow-queries, cases 5-9). This worker host has no
docker and no postgres (installs forbidden by coordinator capacity directive), so these
missions are delivered as a concrete staging runbook: exact commands, pass criteria, and
evidence to capture. Run on a docker-capable staging host; never against the live Oracle host.

## Staging setup (once)

```bash
docker network create sq-scratch
docker run -d --name sq-pg --network sq-scratch -e POSTGRES_PASSWORD=scratch \
  postgres:17-alpine
docker run -d --name sq-qdrant --network sq-scratch -p 6333:6333 \
  qdrant/qdrant:v1.7.0
# seed crx_runtime analog:
psql -h localhost -U postgres -c "CREATE DATABASE crx_runtime;"
psql -h localhost -U postgres -d crx_runtime -c \
  "CREATE TABLE events(id serial primary key, payload jsonb, created_at timestamptz default now());"
psql -h localhost -U postgres -d crx_runtime -c \
  "INSERT INTO events(payload) SELECT jsonb_build_object('i', g) FROM generate_series(1,200000) g;"
```

## case 5: client kill does not wedge the server
```bash
psql -h localhost -U postgres -d crx_runtime -c "SET statement_timeout='30s'; SELECT count(*) FROM events WHERE payload::text LIKE '%1%';"
# in a second session, kill the client (SIGKILL the psql process), then:
psql -h localhost -U postgres -d crx_runtime -c "SELECT count(*) FROM pg_stat_activity;"  # server responsive
```
PASS: server accepts new connections and answers within 2s after the client kill;
no stuck backends (pg_stat_activity shows no orphaned active query).

## case 6: design-spec — deadline propagation end to end
Application-level: every service sets a deadline at ingress (e.g. gateway
`ctx.WithTimeout(30s)` / `AbortController.timeout(30000)`) and passes it to postgres
(`SET LOCAL statement_timeout`) and qdrant (timeout param). Document the chain:
ingress deadline -> db statement_timeout -> driver timeout -> client timeout, each
strictly decreasing. Deliverable: the deadline table in the service runbook.
PASS: table exists and every hop has a configured, decreasing timeout.

## case 7: regression — a query that was fast stays fast (plan stability)
```bash
psql -h localhost -U postgres -d crx_runtime -c "EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE id = 42;"
# record plan hash; after ANALYZE / data growth, re-run and compare
```
PASS: plan shape identical across runs (index scan retained); execution time within
2x of baseline; evidence = both EXPLAIN outputs.

## case 8: slow path degrades to a bounded queue, not thread explosion
Configure a bounded worker pool (e.g. pgbouncer pool_size=20, or app semaphore=20) and
fire 100 concurrent slow queries; observe max concurrent backends:
```bash
seq 1 100 | xargs -P100 -I{} psql -h localhost -U postgres -d crx_runtime -c "SELECT pg_sleep(2);" &
sleep 3; psql -h localhost -U postgres -d crx_runtime -t -c \
  "SELECT count(*) FROM pg_stat_activity WHERE state='active';"
```
PASS: active backends <= pool bound (20); the rest queue or fail fast with a typed
timeout; no unbounded backend/thread growth.

## case 9: timeout budget documented in the runbook
Deliverable: a timeout-budget table (per operation: p50/p99 observed, budget, typed
error on breach) for: event-table scan, vector search, snapshot POST, pg_dump, restore,
healthcheck fan-out, index build. Budgets must be <= the ingress deadline (case 6).
PASS: table exists with measured numbers from the staging runs above.
