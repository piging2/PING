# FAIL-4 FALSIFICATION (PROVISIONAL): adversarial attacks on the four survivors

**Date:** 2026-09-23. **Mode:** research only. No implementation code.
**Status: PROVISIONAL.** Every verdict in this file is labeled PROVISIONAL-PENDING the
dedicated F4 falsification worker, which is still running. This pass exists so the
mapper is not blocked. It must be superseded, not cited, once the dedicated run lands.

**Method:** analytical dry-run, same as the other lanes. Each survivor's own falsifiable
test (from FAIL-4-fixture-drift.md section (b)) was traced against adversarial
fixtures. For each attack: does the test *as written* catch it? Where it does not, a
strengthened test is proposed. No code was built; the "runs" are careful simulations
grounded in documented platform behavior (Node sort stability guarantees, ICU
collation behavior, process isolation semantics).

**Survivor numbering and naming** follow FAIL-4-fixture-drift.md, not the task brief's
approximate labels. Mapping: task "S1 pinned fixtures / replay determinism" is file S1
(declared-input purity + golden byte-compare); task "S2 declared-input purity" and
"readdir-order nondeterminism" are aspects of file S1's test; task "S3 fixture-aware
projection contracts" is file S3 (typed semantic render model gate); task "S4 fixture
oracle during regeneration" is file S2 (replay-mismatch tripwire) in function. File S4
(content-derived identity) has no separate task label.

**Standing rule for verdicts:** WITHSTANDS (claim holds against the attacks),
WEAKENED (claim holds for a sub-shape but fails for a real, in-scope shape), FALLS
(the claimed class is no longer prevented; the class name is given). Every verdict here

## Survivor 1: Declared-input purity (pure render contract + canonical serialization + content hashing + golden byte-compare in CI)

Claimed: #4 fixture-drift, #8 correction-loss, #7 clone-sitespecs.

### Attack A1: bug-contemporary blessing (blessing-laundering)

The golden fixtures are generated *by the pipeline itself*. If the pipeline contained a
bug at golden-blessing time (a sort that is stable but wrong, an evidence binding
systematically misclassified, a canonical serializer that drops a field), the golden
bytes pin the bug forever. Every later run byte-compares against the poisoned golden
and passes. The mechanism detects *change*; it has no oracle for *correctness*.

**Does the test as written catch it?** No. The test runs the pipeline 5 times with
environment variation and byte-compares. That proves stability, never correctness. A
bug-contemporary golden is stable by construction, so the test passes on a poisoned
baseline. The "proves it DOESN'T work" clause only covers cross-run byte differences
and ignored declared inputs; it never asks whether the golden itself is right.

**Strengthened test:** golden blessing becomes a two-key ceremony. (1) The golden
bytes are generated by the pipeline; (2) an *independent* checker (a second,
minimal implementation of canonical serialization and the semantic render walk,
written from the contract text rather than the pipeline code, or the Meta AI tandem
acting as an outside reader) re-derives the semantic content and asserts the golden
encodes what the contract says. Blessing requires a named human sign-off on a
semantic diff, not just byte equality. This directly answers FAIL-4 open question 6
(who approves golden updates; what stops a rubber-stamp).

### Attack A2: cross-environment serialization drift outside the tested matrix

The test varies key order, Date.now, Math.random seed, and TZ. The realistic
serialization drift sources it does *not* vary: Node.js version (V8/ICU changes alter
`String.prototype.localeCompare` collation and thus any sort keyed on locale-aware
comparison), tzdata version on the host (offset rules change; a canonical `asOf`
formatted with zone abbreviations can serialize differently), and Unicode
normalization (NFC vs NFD in owner-supplied strings; byte-compare sees different
bytes for canonically equal text). A pipeline that sorts with localeCompare, or
serializes a date through a zone abbreviation, passes the 5-run matrix on one host and
drifts on another host, with an identical declared input tuple.

**Does the test as written catch it?** No. The matrix fixes the platform; the attack
varies the platform. The test also never includes a pathological serialization fixture
(-0 vs 0, lone surrogates, mixed-normalization strings, equal sort keys exercising
tiebreak paths).

**Strengthened test:** (1) extend the matrix to at least two Node/ICU versions and a
pinned-vs-unpinned tzdata host pair; (2) add a hostile canonicalization fixture
(mixed NFC/NFD strings, -0, duplicate-ish sort keys, zone-abbreviation dates) and
assert byte-identical canonical output; (3) ban locale-aware comparison from the
canonical path by lint (code-order sort on UTF-16 code units only) so the attack
surface is closed by construction, not by matrix luck.

### Attack A3: version-bump laundering (declare-and-bless in one motion)

rendererVersion is a declared input, so every renderer deploy changes the inputHash and
*legitimately* invalidates the golden fixtures. The standard workflow then re-blesses
new goldens. If the code change and the golden re-bless land in the same change with
no independent review, any silent behavior change (a reordered section, a dropped
binding class, a subtly different URL rewrite) is laundered through the declared
channel: the byte-compare never fires because the baseline was moved at the same time
as the behavior. This is the same hole as FAIL-4 open question 3 (rendererVersion
granularity) and open question 6 (rubber-stamp updates).

**Does the test as written catch it?** No. The test varies the environment and flips
one declared input (ownerOverrides); it never exercises the version-bump path, which
is the path real drift takes in production (renderer code changes between runs is
listed in FAIL-4 section (a) as an open drift source).

**Strengthened test:** a CI rule that the golden re-bless for a rendererVersion bump
must be a *separate* change from the code change, carrying a machine-generated
semantic diff (which sections changed, which binding classes changed, confined to
the declared feature) plus human sign-off. Additionally, pin rendererVersion to the
content hash of the renderer bundle (open question 3's candidate) so the version
cannot be bumped cosmetically to justify a re-bless.

### PROVISIONAL verdict S1: WEAKENED (PROVISIONAL-PENDING dedicated F4 falsification)

The pure determinism shape holds: the 5-run env-varied matrix, as specified, is a
genuine test of undeclared-input leakage, and the inputHash/outputHash closure is the
right construction. What weakens the survivor is that its prevention claim for #4 is
about *detecting change*, while production drift most often arrives *declared*:
bug-contemporary goldens (A1) and version-bump re-blessing (A3) both move the baseline
through legitimate-looking channels, and cross-platform serialization (A2) evades the
tested matrix. The mechanism as written is a same-host change detector, not a
drift-proof pipeline.

**Pruned honest class claims (PROVISIONAL):**
- #4 fixture-drift: PREVENTED only for the sub-shape "undeclared ambient input leaks
  into the render path on a fixed platform and fixed renderer version." NOT prevented
  for baseline poisoning at blessing time, version-bump laundering, or
  cross-platform serialization drift. Full claim requires the golden-governance
  protocol (two-key blessing, separate re-bless change, content-hashed
  rendererVersion) and the extended platform matrix.
- #8 correction-loss: see the dedicated verification section below; the claim as
  written in FAIL-4 is overstated and must be narrowed to the same-input-tuple
  sub-shape.
- #7 clone-sitespecs: HOLDS in the narrow sense (divergent inputHashes mapping to
  convergent outputs are observable in the pairing log), but note the pairing log
  itself is not specified as a built artifact with an alert; without a specified
  consumer it is observability, not a tripwire. Prune to "makes convergence
  observable in the (inputHash, outputHash) log" until the alert is specified.

## Survivor 2: Replay-mismatch tripwire (regen re-derives and byte-compares against the recorded output; divergence is a hard failure)

Claimed: #4 fixture-drift, #8 correction-loss, #9 conflict-collapse.

### Attack B1: baseline laundering (deploy regenerates and re-records in one motion)

The tripwire compares regen output against the *recorded* output from the last good
generation. Nothing in the mechanism as specified constrains *how a record becomes the
record*. If the deploy pipeline regenerates all sites after a renderer deploy and
writes the new outputs as the new recorded baselines (the natural implementation of
"update the goldens"), the tripwire compares new behavior against new behavior and
never fires. The three mutation trials in the test all attack the *pipeline* while
holding the baseline fixed; none attacks the baseline's provenance.

**Does the test as written catch it?** No. The test's input is "recorded output from
a clean generation" taken as given; the procedure never probes who may write the
record or whether a code deploy can rewrite it.

**Strengthened test:** baseline promotion is a separate named event with a different
actor than the code deploy (mirrors the S1 A3 fix). Test: run a renderer-behavior
change through the full deploy pipeline in a trial where the pipeline attempts to
re-record baselines automatically; the expected outcome is that the tripwire halts
the *re-record* itself (the re-record is an unexplained divergence until blessed),
and publish proceeds only after a distinct baseline-bless event naming the code
change. What proves failure: a single deploy step that both changes renderer behavior
and updates recorded outputs with no intervening named event.

### Attack B2: benign platform drift with no resolution path

A tzdata or ICU update on the production host changes output bytes with inputHash
unchanged. The tripwire correctly fires (unexplained divergence), but the mechanism
specifies no resolution path other than "halt." Every host patch becomes a
publish-blocking incident, and the only escape is re-blessing the baseline, which is
exactly the laundering channel of B1/A3. The mechanism is fail-closed without a
fail-*operational* path, so in practice operators will build an ad-hoc re-bless
shortcut, and that shortcut becomes the drift hole.

**Does the test as written catch it?** Partially. Its own "proves it DOESN'T work"
clause demands the tripwire distinguish explained vs unexplained divergence, but the
test never injects a benign-platform-change trial, so the resolution path is never
exercised.

**Strengthened test:** add trial (d): upgrade tzdata/ICU on the regen host with no
input change, run regen through the gate. Expected: halt with a named divergence
error *plus* a named resolution workflow (platform-change attestation: re-run on the
old platform to confirm the diff is platform-caused, then bless with the platform
change named as the cause). What proves failure: the only way past the halt is an
unattributed re-bless.

### Attack B3: non-atomic record update (the halt that becomes the baseline)

"Serves outputBytes0" and "halts with a named divergence error" are only as good as
the write ordering. Attack: regen writes outputBytes1 to the record, *then* the gate
compares and halts. The halt fired correctly, but the record now holds the diverged
bytes. The next regen compares against poisoned outputBytes1 and passes. A crash
between output write and record commit has the same shape. The mechanism specifies
the comparison but not the atomicity of the record update relative to the halt
decision.

**Does the test as written catch it?** No. It asserts the halt and the served bytes
but never inspects the record's bytes after a halt, and never crash-tests
mid-regen.

**Strengthened test:** (1) after each of the three mutation trials, assert the
recorded (inputHash0, outputBytes0, outputHash0) is byte-identical to before the
trial; (2) crash-mid-regen test: kill the regen process between output derivation
and record commit, then run the gate and assert it still halts against outputBytes0
and serves outputBytes0; (3) specify the invariant: the record is updated *only* on
an explicit baseline-bless event, never as a side effect of a regen run.

### PROVISIONAL verdict S2: WEAKENED (PROVISIONAL-PENDING dedicated F4 falsification)

The core detection shape holds against the tested attacks: pipeline mutations that
drop overrides, collapse conflicts, or reorder sections are genuinely caught by a
byte-compare against a trusted baseline, and "never silently merge" is the right
production posture. What weakens it is that every one of its #4/#8/#9 claims rests on
the baseline's integrity, and the baseline's provenance (B1), its update atomicity
(B3), and the operational resolution path for benign drift (B2) are all unspecified
and untested. A tripwire whose baseline can be rewritten by the same deploy it
polices is a tripwire with the wires cut at the post.

**Pruned honest class claims (PROVISIONAL):**
- #4 fixture-drift: DETECTED at regen time against a *trusted, separately-blessed,
  atomically-updated* baseline. The qualifiers are load-bearing; without the
  baseline-bless protocol and the atomic-commit invariant, the honest claim is
  "detects pipeline mutations under a fixed baseline," not "prevents silent drift
  from reaching production."
- #8 correction-loss: holds for the tested sub-shape (render-path drops of the
  overlay are caught as unexplained divergence). Inherits the baseline qualifiers
  above.
- #9 conflict-collapse: holds for the tested sub-shape (silent conflict resolution
  diverges from the recorded conflict-preserving output). Same baseline qualifiers.

## Survivor 3: Typed semantic render model with fail-closed gate (evidence, visibility, URL-safety axes; GENERATED quarantine with seed pinning)

Claimed: #5 claim-binding, #6 visibility-error, #2 unsafe-url; #4 fixture-drift supporting.

### Attack C1: contract-shape-vs-content (the classifier launders the claim)

The gate checks that every node *carries* a binding class; it does not verify that
the class is *correct*. Attack: the binding classifier labels an unevidenced
marketing claim DIRECT_EVIDENCE (wrong class, right shape), or a binding cites a
source object ID that exists but contains different text than the claim asserts.
The gate walks the model, sees a well-formed DIRECT_EVIDENCE binding, and passes.
The test's fixture (a) poisons the *graph* with an unevidenced claim, which only
tests the classifier when the classifier is honest. The attack poisons the
*classification step itself*.

**Does the test as written catch it?** No. Procedure (1) runs the render through
the gate and expects the unevidenced claim absent, but the fixture's unevidenced
claim arrives *untyped*; the gate's real-world input arrives *pre-typed* by the
classifier, and nothing in the test exercises a mis-typed node.

**Strengthened test:** adversarial typing trial. (1) Mutate the classifier to
mislabel one unevidenced claim as DIRECT_EVIDENCE and one private fact as public;
run the gate. Expected: the verifier re-resolves each DIRECT_EVIDENCE binding
against the source layer (coordinates resolve, text matches the claim's predicate)
and fails closed on the laundered node, logging CLASSIFICATION_MISMATCH. (2)
Binding-pointer trial: a claim bound to a real source ID whose text contradicts
the claim. If the verifier only checks "binding class is populated," this passes
and the mechanism is falsified; the honest contract must include binding
re-resolution, which is currently unspecified.

### Attack C2: the GENERATED quarantine is a smuggling compartment

Two sub-attacks. (i) The *segmentation* into GENERATED_PRESENTATION vs evidential
nodes is itself a model decision (the ask-composer path is in the pipeline). If an
LLM decides node boundaries, an unevidenced claim can be segmented *inside* a
GENERATED paragraph, where it is exempt from binding checks *and* exempt from the
canonical byte-compare. The gate trusts the segmentation it was supposed to police.
(ii) Even with honest segmentation, the mechanism says GENERATED nodes are "excluded
from the canonical byte-compare surface" but does not say whether the
visibility and URL-safety axes still walk *inside* GENERATED nodes. A `javascript:`
URL or a private fact smuggled inside LLM copy would then be invisible to both the
drift machinery and the safety gate.

**Does the test as written catch it?** No. The fixture's GENERATED paragraph (seed
42) is a cooperating paragraph; the test never poisons the segmentation, never
embeds a blocked URL or private fact inside GENERATED copy, and never asserts which
axes walk GENERATED nodes.

**Strengthened test:** (1) hostile segmentation fixture: an LLM-typed boundary that
places an unevidenced factual claim inside a GENERATED paragraph; expected: the
gate either re-segments factual sentences out of GENERATED regions or fails the
node closed. (2) Smuggled-payload fixture: GENERATED paragraph containing a
`javascript:` URL and a private fact; expected: URL_BLOCKED and VISIBILITY_BLOCKED
log entries even though the node is GENERATED, proving the safety axes walk all
nodes while only the *byte-compare* excludes GENERATED. If the exclusion covers the
whole gate walk, the quarantine is a hole and the #2/#6 claims fall for
LLM-generated regions.

### Attack C3: the second emit surface (the gate nobody walks through)

The test inspects "the emitted markup." Real sites emit more than markup: the
serialized client graph, JSON-LD, sitemap, search-index payload, feed. Attack: a
consumer reads the *untyped projection* (pre-gate) instead of the gated semantic
model. This is not hypothetical: FAIL-8's STEP-06 defect was exactly a presentation
boundary hole where one consumer never received the overlay. A private fact blocked
from markup but present in the serialized client graph is a #6 failure the gate
never sees.

**Does the test as written catch it?** No. It names one emit surface.

**Strengthened test:** enumerate every emit surface and every graph consumer in a
registry test; assert each surface is derived from the gated semantic model (or
passes the gate itself). The STEP-06 lesson becomes a standing test: any consumer
added without gate wiring fails the build. What proves failure: any surface
emitting an (a)/(b)/(c) fixture payload that the gated markup correctly blocks.

### PROVISIONAL verdict S3: WEAKENED (PROVISIONAL-PENDING dedicated F4 falsification)

The fail-closed gate over a correctly-typed model is a sound construction, and the
per-node (not per-page) failure scope is the right call. What weakens the survivor is
the trust boundary: the gate trusts the *typing* (C1), trusts the *segmentation*
(C2), and is only proven on one emit surface (C3). The test as written verifies the
gate against cooperating fixtures; it never attacks the classifier, the segmenter,
or the second surface. A gate that cannot be lied to by its own inputs is not yet
proven.

**Pruned honest class claims (PROVISIONAL):**
- #5 claim-binding: holds for nodes whose binding classification is correct and
  whose binding coordinates re-resolve. The re-resolution step is currently
  unspecified; until it is specified and tested, prune to "untyped or unbound
  claims cannot reach markup through the gated path."
- #6 visibility-error: holds for the gated markup surface. Prune the multi-surface
  claim until the consumer-registry test (C3) exists and passes.
- #2 unsafe-url: same surface qualification as #6; plus the GENERATED-interior
  question (C2-ii) must be answered (safety axes walk all nodes) before the claim
  covers LLM-generated regions.
- #4 fixture-drift (supporting): the GENERATED quarantine with seed pinning is
  sound *within one model version on one platform* (see FAIL-4 open question 1);
  prune any byte-stability claim across model versions or providers.

## Survivor 4: Content-derived identity (every generated ID is a hash of canonical coordinates, never a random UUID)

Claimed: #4 fixture-drift, #8 correction-loss.

### Attack D1: oracle-independence collapse (the coordinates are pipeline-derived)

The claim "same logical entity gets the same ID" holds only if the *coordinates* are
independent of pipeline nondeterminism. Attack: `id = hash(siteSpecHash, objectPath,
index)` where `index` comes from an iteration order that is sorted today by a
comparator that is not a total order (equal keys), or from readdir/extraction order
that the current code happens to sort but a future extractor change stops sorting.
The IDs are then a pure function of coordinates that are themselves unstable: the
oracle (hash) is deterministic, but its *inputs* are not independent of the
environment. Two runs in different filesystem states silently reshuffle every ID,
and correction bindings keyed by ID orphan en masse.

**Does the test as written catch it?** No. Procedure (1) runs generation twice and
compares ID lists, but unlike S1's test it specifies *no environment variation*
between the runs. Two runs on the same host with the same filesystem state prove
nothing about coordinate independence.

**Strengthened test:** port S1's adversarial matrix into S4: shuffle extraction /
readdir order, vary filesystem state, run the two generations in *separate
processes*; assert byte-identical ID lists. Add a static invariant: ID-derivation
inputs must be provably totally ordered (lint the derivation call sites; any
positional index must come from a sort with a total comparator, or positional
indices are banned from coordinates entirely).

### Attack D2: insert/delete index shift (the re-observation the test never runs)

Procedure (2) changes field *values* without changing object identity: the easy
case. Attack: the source re-dump *deletes* one service and *adds* another. If any
coordinate is positional (index in a list), every object after the deletion gets a
new index, a new ID, and its owner corrections orphan in a single re-observation.
The survivor's #8 claim ("stable derived IDs keep the correction binding alive
across re-dumps") fails exactly in the routine business event of dropping or adding
a service. The STEP-01 sample IDs (`website-service-51de038c1defe8bd`) show a hash
suffix but do not reveal whether a positional index feeds the hash.

**Does the test as written catch it?** No. Re-observation in the test is
value-only; insert/delete is never exercised. The grep for random UUIDs (procedure
3) is orthogonal: this attack uses no randomness at all.

**Strengthened test:** adversarial re-observation: delete one service, add one
service, rename one service; re-run; assert every *surviving* object keeps its ID
byte-identical. This forces coordinates to be anchored in stable source keys (or a
re-anchoring protocol), never in sibling order. Note this is the same open problem
as FAIL-8 open question 1 (stable identity under entity merge/split); S4's #8
claim currently assumes it solved.

### Attack D3: rename-driven coordinate churn (owner renames orphan their own corrections)

If `objectPath` incorporates a human-readable slug derived from the service name,
then an owner rename (a legitimate, common event) changes the coordinates, changes
the ID, and orphans the owner's own earlier corrections keyed by the old ID. The
correction that renamed the service destroys the anchor of every other correction
on that service. This is #8 arriving through the identity layer rather than the
source layer.

**Does the test as written catch it?** No. Renames are not in the procedure.

**Strengthened test:** rename one service via the owner-override path (not the
source), re-run generation, assert the object's ID is unchanged and all its
corrections still resolve. Coordinates must be derived from immutable source keys
(where they exist) or from the first-observed identity record, never from mutable
display names. Where no stable source key exists, the honest claim must say so.

### PROVISIONAL verdict S4: WEAKENED (PROVISIONAL-PENDING dedicated F4 falsification)

The anti-randomness shape is solid: no-UUID-in-the-generation-path plus the
double-run ID-list comparison genuinely kills the "random UUIDs are the purest
drift source" case, and the STEP-01 sample IDs are consistent with content-derived
coordinates. What weakens the survivor is that its #8 claim depends on coordinate
stability under *reorganization* (insert/delete/rename/merge/split), and the test
only exercises value-only re-observation on a fixed host. D2 is the load-bearing
untested case: if any coordinate is positional, the #8 claim fails on the most
routine business event (adding or dropping a service). The honest status of D2/D3
cannot be settled without reading the actual derivation inputs, which is work for
the dedicated falsification run.

**Pruned honest class claims (PROVISIONAL):**
- #4 fixture-drift: WITHHOLDS provisionally for the randomness sub-shape (no random
  IDs in the generation path; double-run ID stability). The coordinate-independence
  sub-shape (D1) is unproven until the env-varied ID test runs.
- #8 correction-loss: holds only for value-only re-observation with stable entity
  sets. Prune the general "correction binding alive across re-dumps" claim until
  the insert/delete/rename trials pass or a re-anchoring protocol is specified.
  Explicitly out of scope until then: entity merge/split (shared open problem with
  FAIL-8).

## Verification: the F4-S1 correction-loss claim flagged by the gate-checker

The claim as written in FAIL-4-fixture-drift.md S1: "A regen that drops a correction
produces different output bytes under an identical input tuple, which is drift by
definition, so the golden byte-compare trips. Step 7 already proves the separation
(owner store untouched by re-dump); this mechanism turns that separation into a
checked invariant."

**Verdict on the explanation: PRUNE, do not keep as written.** The logic is valid
only for a narrow sub-shape and misleading about the general shape:

1. **It conflates two different regen shapes.** The claim's "identical input tuple"
   scenario is: same source, same ownerOverrides, and the render path regresses so
   the overlay is not applied. There, output differs under an identical inputHash,
   and the golden byte-compare genuinely trips. That is real and worth keeping.
   But the *common* correction-loss shape is: the source changed (new graphDigest,
   so the input tuple is NOT identical), and the correction orphans because its
   anchor churned or the merge dropped it. In that shape there is no golden for the
   new inputHash yet, the byte-compare has nothing to trip against, and S1 says
   nothing. The explanation presents the narrow shape as if it covered
   correction-loss generally.

2. **It assumes the golden baseline contains the correction.** The trip only fires
   if the recorded golden output was generated with the correction applied. If the
   golden was blessed before the correction existed (the normal ordering: goldens
   blessed at build time, corrections recorded at owner time), then a regen that
   drops the correction reproduces the *pre-correction* golden bytes exactly, and
   the byte-compare *passes*. The mechanism as specified has no story for
   correction-time golden updates; without one, S1 is blind to exactly the loss it
   claims to catch. This is attack A1 wearing a correction-loss mask.

3. **Step 7 does not prove what the sentence claims it proves.** STEP-07 proves the
   owner store is untouched by re-dump (separation of layers). It does not prove
   that the render path consults the store on every regen; that direction is what
   S1's own falsifiable test probes ("identical output bytes after the
   ownerOverrides change" = declared input silently ignored). Citing Step 7 as the
   proof of the invariant is citing the wrong half of the invariant.

**Pruned replacement claim (PROVISIONAL):** S1's golden byte-compare catches
correction loss *only* in the same-input-tuple sub-shape (render-path regression
dropping the overlay while source and overrides are unchanged), *and* only when
the golden baseline postdates the correction. Correction loss across
source-changing regens (anchor churn, merge drops, pre-correction baselines) is
outside S1's boundary; it belongs to S2 (tripwire against the last corrected
recorded output), S4 (stable identity keeping the anchor alive), and FAIL-8's own
survivors. The FAIL-4 S1 "Prevents #8" line should read: "same-input-tuple overlay
regressions only; see pruned claim."
