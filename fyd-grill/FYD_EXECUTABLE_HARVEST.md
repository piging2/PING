## (1) Top 15 reuse candidates, ranked by FYD hot-path leverage

1. **FYD canonical envelope kit** (`src/fyd/ask/envelope.ts`): Ed25519 sign/verify with payload-hash binding and the pinned single serializer; the trust root every proposal builds on.
2. **Proceduralizer 9-stage pipeline** (`src/fyd/proceduralize/proceduralizer.ts`): the entire sources to object-graph compiler as pure tested functions; the FYD onboarding engine's deterministic half.
3. **SiteSpec generator** (`src/fyd/proceduralize/generator.ts`): pure ObjectGraph to FYDSiteSpec; byte-deterministic; the declarative site compiler core.
4. **SiteSpec validator + render gate** (`src/fyd/sitespec/validator.ts`): two-layer findings validation with `isRenderable`; "never render an invalid spec" enforced in code.
5. **Component registry** (`src/fyd/components/registry.ts`): one schema to component mapping consumed by generator, validator, and renderer; unknown schemas fall back to GenericObjectCard, never fail.
6. **Renderer + deterministic query resolution** (`src/fyd/components/renderer.tsx`): (SiteSpec + ObjectGraph + ViewerContext) to UI with total-order query resolution; no hand-layout per company.
7. **Proof schemas codegen chain** (`src/fyd/sitespec/schemas.ts`): 3 schemas driving validator, component eligibility, relationship rules, capability options, and agent tool descriptions from one definition.
8. **Ask FYD site-patch drafting** (`src/fyd/ask/site-patch.ts`): deterministic keyword-anchored intent to digest-bound proposal with honest refusals; the agent drafts, never mutates.
9. **Proposal approval route** (`src/app/api/ping/proposal/route.ts`): server-side digest re-verification, siteSpecDigest binding, stale-draft rejection; the human-approval enforcement point.
10. **Grant authority + agent capability boundary** (`src/lib/ping/grants.ts`, `src/fyd/ask/capabilities.ts`): user-facing grants plus fail-closed agent grant stripping; the permission model already built.
11. **Refresh lane** (`src/fyd/refresh/`): temporal observation, claim grading, snapshot diff, cross-source conflict detection with keep-both-claims resolution, and dependency-index invalidation; 21/21 tests green.
12. **PingObjectReader BFF** (`src/lib/ping/ping-object-reader.ts`): the single server-side gateway adapter with sanitization and typed errors; the read/projection boundary FYD already uses.
13. **Ask composer digest law** (`src/lib/ping/ask-composer.ts`): deterministic evidence-backed answers plus the shared `canonicalize`/`proposalDigest` the envelope kit pins.
14. **Action planner + Circle actions** (`src/lib/ping/action-planner.ts`, `src/fyd/ask/circle-actions.ts`): pure (viewer, target, grants) to UI actions; unplannable actions never render.
15. **Embedding + retrieval services** (`ping-runtime/embeddings/embedding_service.js`, `runtime/retrieval/retrieval_service.py`): the only working semantic search in the estate (Ollama nomic-embed-text, Qdrant 768-d cosine, deterministic fallback vectors); FYD's discovery stage needs this behind the BFF, not reimplemented.

## (3) Gaps: FYD pipeline stages with NO executable implementation

**G0. Schema-id drift (live breakage, not just a gap).** The Happy Place fixture carries the real journal schemas (`ping.knowledge.business@1`, `ping.knowledge.service@1`, `ping.knowledge.location@1`, `ping.knowledge.person@1`, `ping.knowledge.website@1`) but the generator, validator, and registry hardcode `ping.social.*@1`. Result, verified by running the suites read-only just now: the generator emits only the `explore` page (no owner found), and `generator.test.ts`, `patch.test.ts`, `validator.test.ts`, `render.test.ts` fail (11 tests across 4 suites). The demo route at `src/app/sites/happy-place` renders explore-only. Fix shape: a schema map/alias layer (`ping.knowledge.*` to `ping.social.*`) or generator acceptance of both namespaces. Until this lands, the "procedural clone of HPP" proof is red in the worktree. Everything else in the Top 15 is green.

**G1. Resolution (entity resolution).** `proceduralize.resolve()` resolves field-level conflicts by source priority, and `refresh/conflict.ts` detects cross-source value disagreements, but NOTHING links the same real-world entity across sources (website business vs Facebook page vs Drive doc). No dedupe, no merge, no identity stitching anywhere in the estate. The refresh lane's synthetic fixture even notes entity matching is assumed. FYD stage affected: resolution, object graph.

**G2. RSS/Atom/sitemap parsing.** `discover()` enumerates `sitemap`, `rss`, `atom` source records, but `parse()` only understands JSON-LD, OpenGraph, meta tags, and `<title>`. Feed and sitemap XML are acquired and then silently yield nothing. FYD stage affected: acquisition.

**G3. Semantic search in the FYD hot path.** Embeddings and retrieval work PING-side only, behind Python/Node services with their own credentials. The BFF (`ping-object-reader.ts`) exposes no search endpoint, so FYD's discovery surface cannot do semantic search without new plumbing. FYD stage affected: discovery.

**G4. Social provider adapters.** No executable ActivityPub, ATProto, Nostr, or Farcaster code exists in either repo. The `facebook-source.ts` real path (`fromFacebookCliJson`) is wired but unfed; everything else is pattern harvest. FYD stages affected: sources, acquisition, social/agent actions (projection).

**G5. Regeneration executor.** `dependency-index.ts` computes exactly which sections/pages invalidate on a change, but nothing re-runs generator plus renderer for those pages, and conflict resolution does not yet draft a governed `site_patch` (the refresh README names this as the next improvement). **G6. RELATE stage output is dropped.** `relate()` emits `links_to` relationship pairs, but `project()` never consumes them; only `located_at` relationships reach the graph. Either wire it or delete the stage. FYD stage affected: object graph.

**G7. AI extraction stage.** The proceduralizer header says "Deterministic first, AI second" but no LLM call is wired anywhere in the FYD lanes; the provider adapters that could serve it live PING-side. FYD stage affected: acquisition (enrichment).
