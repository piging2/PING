## Differentiation thesis

The ecosystem (OpenPage typed JSON source of truth; SiteSpec deterministic specs + controlled section composition; VoxelSite structural page graphs + transactional reviewed AI changes; Elementor September beta exposing editable site structure to external AI via MCP) is converging on: structured JSON/specs shared by humans and agents, transactional/reviewable AI edits, deterministic rendering, agent-native CMS interfaces. FYD's differentiation sits ONE LAYER BELOW: evidence-backed objects, owner decisions, relationships, capabilities, outcomes, and multiple projections. FYD owns semantics, not commodities.

Durable core: OBSERVATION → EVIDENCE → CLAIM/FACT → OBJECT → RELATIONSHIP → OWNER DECISION → CAPABILITY → PROPOSAL → AUTHORIZED TRANSITION → OUTCOME.
Everything else replaceable where practical: HTTP crawler, browser, LLM, React, site renderer, social provider are replaceable; MCP/ ActivityPub / ATProto are adapters; CRDT is optional collaboration implementation. THE CUSTOMER'S SEMANTIC OBJECT + HISTORY MUST SURVIVE ALL OF THEM.
Replacement test for every major implementation: IF WE REPLACE THIS IN TWO YEARS, DOES THE CUSTOMER LOSE THEIR FYD? If replacement destroys identity, evidence, objects, relationships, owner corrections, authorized transitions, or outcome history, canonical value was put in the wrong layer. FIX IT.

## Five design questions — answered

1. **Who owns "no invented claims"?** The shared evidence/object projection contract owns factual eligibility — not the renderer, and no new ClaimAuthority. The renderer receives a renderable projection in which every factual binding carries object/fact → evidence identity → visibility/status. The binding verifier is the enforcement point: factual content without a valid binding FAILS CLOSED. Generated marketing copy is allowed but must stay typed as generated presentation, never silently promoted into factual claim. Ask FYD uses exactly the same evidence identity. Renderer and concierge are two consumers of one evidence contract, not two truth systems.
2. **Who decides whether the street address appears?** The owner, subject to hard privacy/security policy. Extraction says "we observed address X"; it never constitutionally says "publish X" or "hide X." Store source-derived fact separately from an owner-controlled visibility decision (PUBLIC / PING_ONLY / PRIVATE) using the existing visibility mechanism. Default conservatively for person/home-address-like data; business addresses may have schema-aware defaults, owner-overridable. FYD KNOWS X does not imply FYD PUBLISHES X. Do not let acquisition own publication policy. Do not create SiteAuthority for this. BUILD IT SMALL.
3. **Is WHY THIS for the owner or us?** Primarily a trust/correction primitive, not a dashboard feature. Normal UI simply works; "why this?" appears when the owner sees something surprising, wants to correct it, or Ask makes an assertion. Architectural role underneath: correction, conflict resolution, debugging, safe regeneration, evidence-grounded agents. Hierarchy: value first → correction when needed → provenance on demand.
4. **Render determinism?** Make the semantic render model deterministic, not every browser byte. ObjectGraph + SiteSpec + ViewerContext + owner overrides + renderer version → canonical render model must be stable. Wall-clock timestamps, random IDs, unstable iteration ordering, process-local counters cannot participate. Browser-generated implementation details are not constitutional. Persist/test a canonical semantic digest. Do NOT constitutionalize incidental browser DOM bytes.
5. **Generic planner failure?** Keep the deterministic planner small: schema presence, cardinality, relationship topology, capabilities, owner overrides determine eligible/required sections. Intelligence may propose composition beyond that baseline, but SiteSpec remains typed and reviewable. Don't turn the planner into an autonomous designer until real users demonstrate deterministic composition is inadequate.

## Four builder-lane product questions — answered

1. **Media:** Don't assume "publicly visible" = "authorized for FYD to permanently copy." PING/FYD-owned or explicitly authorized demo assets: download → hash → preserve original source/provenance → derive normalized thumbnails/variants → serve derivatives. Arbitrary third-party sites: default to source references/hotlinks until rights/owner authorization established. Owner-connected site with explicit asset import → promote into owner-authorized FYD media. Keep source asset, authorization basis, and derivative distinct. The four ambiguous manifests must be classified SOURCE-DERIVED or OWNER/GENERATED by what they mean, not filename/history; split semantic ownership without duplicating the asset if both.
2. **Owner mode:** Don't fake authentication as real. Immediate demo: clearly marked DEV OWNER SESSION acceptable if unmistakably non-production and unable to cross the production boundary. But SiteSpec/visibility/correction operations must already require an owner capability at the backend contract — real authentication plugs into the same boundary later without rewriting product semantics.
3. **Ask FYD visitors:** Full evidence-backed Q&A now (proven at c02b9ecc). The contract is not "answer everything"; it is answer what evidence supports, separate known from unknown, cite the graph, refuse unsupported factual assertions.
4. **Comparison must-wins:** Keep mobile UX, service discoverability, contact discoverability; replace raw "performance" as the fourth product criterion with trustworthy editability. Performance is a release gate, not the differentiation. Four wins: understands me accurately; customers can find what matters; I can change it by talking; it stays correct afterward. Measure performance/accessibility/SEO/security underneath those.

## Ecosystem harvest posture (Nolan's research, 2026-09-29)

- Crawl4AI 0.9.4 (Sept 23): SSRF + env-var trust-boundary patches. WARNING as much as opportunity: customer URL ingestion is hostile input; acquisition belongs behind egress restrictions, not inside a trusted application process. Eventual acquisition-worker posture: network egress policy, no cloud metadata access, no internal network access, resource limits, timeouts, bounded redirects, sanitized output.
- Lightpanda: acquisition worker candidate only; recent open issues (OOMs, unauthenticated CDP control, Playwright compatibility). Not foundational truth infrastructure.
- Automerge 3.x: attractive LATER for concurrent/offline SiteSpec editing or multi-device owner customization — never for canonical evidence or events. PING already has event authority; don't let a CRDT become a competing truth system.
- MCP July spec (stateless core, cacheable capability/resource listings, formal extensions, hardened authorization): increasingly sensible for exposing object/capability operations to external agents rather than inventing an agent transport. PING still decides authorization and records outcomes.
- Renderer security: OWASP javascript: sink guidance — canonicalize and allowlist safe URL schemes for untrusted href/src; encoding alone insufficient. Already-proven URL neutralization stays regression-gated: allowlisted URL schemes, escaped text, no arbitrary source HTML execution, no untrusted script/style injection.
- Harvest rule for any candidate: require PROBLEM / CURRENT COST / HARVEST CANDIDATE / LICENSE / DEPENDENCY COST / MEASURED BENEFIT / EXIT STRATEGY. Do not adopt because fashionable. For structured builders (OpenPage, SiteSpec, VoxelSite, Elementor MCP/Atomic Editor) READ ONLY FIRST; extract spec representation, component contracts, design tokens, transactional edits, preview, undo, agent editing, impact analysis, renderer separation, responsive primitives; for each: ADOPT / ADAPT / REJECT. Do not import an entire builder. ONE design system, not customer-specific CSS. SiteSpec controls semantic composition, design tokens, variant selection, media references, presentation preferences. Components own responsive correctness, accessibility, safe rendering. AI may PROPOSE tokens/composition/copy/media selection. Renderer executes deterministically.
