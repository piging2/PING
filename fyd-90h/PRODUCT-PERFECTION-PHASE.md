## DO NOT EXPAND

STOP NEW-BUSINESS EXPANSION. No Monument View. No additional customer/business fixtures. No prospecting. No generalized onboarding campaign. No proving that we can make a fourth mediocre website. We have enough fixtures.

## THE LOOP BEING GREEN DOES NOT MEAN THE PRODUCT IS DONE

We have now demonstrated an extremely important thing:
SOURCE → EVIDENCE → OBJECT GRAPH → SITE SPEC → RENDER → ASK → OWNER INTENT → APPROVAL → REGENERATION → SOURCE REFRESH → INTENT SURVIVAL → LAST GOOD.
Preserve that proof. But distinguish: MECHANISM WORKS from: PRODUCT IS EXCELLENT. We are still much closer to the first.

The next phase is therefore: PERFECT THE MACHINE USING ONLY PING + HPP + COPPERSMITH. Every backend improvement must make one or more of those three sites measurably better, safer, more faithful, easier to change, or easier to regenerate.

## PRIMARY QUESTION

Stop asking: "Can FYD generate a site?"
Ask: "Can FYD understand three very different businesses deeply enough to repeatedly produce sites that feel intentionally designed for each one?"
And: "Can it regenerate those sites after reality changes without destroying the owner's design intent?"
That is now the product frontier.

## THE THREE-SITE COURTROOM

Treat these three as a permanent adversarial corpus. They should deliberately exercise different product characteristics.

**PING** — Dogfood the system itself. It should stress: technical/product information; complex concepts; documentation; evidence provenance; changing product state; deep Ask questions; many relationships; structured feature descriptions; architecture/technical terminology; frequent regeneration.

**HPP** — Stress: personality; visual warmth; human/business story; services; location/contact information; owner corrections; photographs/media; conversational changes; mobile experience; clear calls to action.

**COPPERSMITH** — Stress: service-business conversion; emergency intent; trust; service-area semantics; phone/contact prominence; local information; multiple services; structured business facts; practical mobile use; strong hierarchy.

Do not force these three through identical page compositions merely because they share one renderer. Shared semantics. Shared primitives. Shared correctness. Different experiences.

## BACKEND FIRST

The next work should overwhelmingly attack the backend architecture that determines product quality. Focus on:

### 1. ACQUISITION QUALITY
Can PING actually understand the source? Perfect: URL/SOURCE → FETCH → OBSERVATION → EXTRACTION → EVIDENCE. Measure what was discovered and what was missed. Compare the generated understanding against the actual HPP, Coppersmith and PING source realities. Browser escalation remains a bounded acquisition adapter, not a second truth authority. Fix: missing content; dynamic content; metadata; structured data; navigation; contact information; service extraction; image/media acquisition; duplicate facts; stale facts; conflicting facts; source provenance. Do not beautify downstream garbage.

### 2. EVIDENCE QUALITY
Every important generated assertion should have an answer to: WHY DOES FYD BELIEVE THIS? Improve: OBSERVATION → CLAIM → EVIDENCE → VERIFICATION → OBJECT. Find: unsupported objects; weakly supported fields; duplicated evidence; stale evidence; conflicting evidence; lost source URLs; fabricated confidence; provenance gaps. Ask FYD being green is useful because it becomes a diagnostic instrument for the underlying knowledge model. Use it aggressively.

### 3. OBJECT GRAPH QUALITY
This is one of the deepest product assets. For all three fixtures inspect what FYD believes exists: Business, Person, Service, Location, Contact method, Media, Offer, Hours, Relationship, Evidence, Owner correction, Owner intent. Determine: what objects are missing; what objects are falsely duplicated; what relationships are wrong; what information is flattened that should remain structured; what presentation concepts leaked backward into canonical business semantics. Do not solve graph defects with renderer conditionals.

### 4. SITESPEC QUALITY
SiteSpec should be the point where BUSINESS REALITY BECOMES COMMUNICATION INTENT. It must decide: what matters; hierarchy; page structure; section selection; section order; content density; CTA strategy; media use; emphasis; visibility; responsive priorities; design tokens; component variants. SiteSpec must not merely serialize the object graph into rectangles. Compare the three SiteSpecs side-by-side. If they look structurally identical despite radically different businesses, the compiler is underthinking.

### 5. DESIGN SYSTEM / TEMPLATE INTELLIGENCE
Do not create hundreds of templates. Also do not create one giant template with business-name substitutions. Build a small, excellent compositional vocabulary: page archetypes; hero variants; navigation variants; service presentations; evidence/trust treatments; media treatments; CTA patterns; contact patterns; location treatments; testimonial/social-proof patterns when supported; FAQ/Ask integration; footer patterns; typography systems; spacing/density systems; responsive behaviors. The generator chooses among proven primitives according to SiteSpec. The target is: FINITE COMPONENT VOCABULARY + HIGH COMPOSITIONAL RANGE. Not: ONE TEMPLATE PER INDUSTRY. Not: UNBOUNDED AI-GENERATED HTML.

### 6. GENERATOR DETERMINISM
Given the same OBJECT GRAPH + OWNER INTENT + GENERATOR VERSION we should be able to explain and reproduce the semantic SiteSpec. If intelligence participates in planning, capture its bounded decision artifact. Regeneration must not randomly redesign the customer's business. Variation should be intentional and versioned.

### 7. OWNER INTENT AS A FIRST-CLASS LAYER
Source truth and owner presentation preference are different things. Preserve: SOURCE REALITY + OWNER CORRECTIONS + OWNER PRESENTATION INTENT → GENERATED EXPERIENCE. Examples: "Hide Locations." "Put Services first." "Make emergency service more prominent." "Use this photo." "Don't mention X." "Make this feel less corporate." "Make the phone number easier to find." These should survive regeneration without turning the generated HTML itself into canonical truth.

### 8. REGENERATION
Now attack regeneration much harder. Repeatedly mutate the fixture reality. For example: SOURCE V1 → SITE V1 → OWNER INTENT → SITE V2 → SOURCE V2 → REOBSERVE → SITE V3. Assert: source changes appear; irrelevant sections do not churn; owner intent survives; stale proposals fail; dependencies invalidate correctly; incremental rebuild equals clean full rebuild semantically; broken regeneration keeps last-good; publication is atomic. The selected projection relationship remains: journal = authority, object graph = projection, file dump = disposable projection serialization, SiteSpec = generated/owner-influenced presentation specification, rendered HTML = disposable projection.

### 9. ASK FYD AS A PRODUCT QUALITY PROBE
Don't treat Ask as a finished feature because 11/11 passed. Use it to interrogate the entire backend. Ask hundreds of useful questions against the three fixtures. Categorize failures: acquisition failure; evidence failure; graph failure; retrieval failure; projection failure; reasoning failure; privacy failure; unsupported-answer honesty failure. Then fix the earliest broken semantic layer. Do not patch individual answers.

### 10. SOURCE / BUILD / SERVED PROVENANCE
Close this properly. Earlier reconnaissance found no mechanical binding from served bytes back to source SHA, build identity, SiteSpec digest, object-graph version, or projection version. Make every proof able to identify: SOURCE, OBJECT GRAPH, PROJECTION, SITESPEC, GENERATOR, BUILD, SERVED ARTIFACT. We should never again have to ask: "Which code produced the page I'm looking at?" Do this without turning provenance into a new truth store.

### 11. IDENTITY / OWNER BOUNDARY
Demo-owner is acceptable for the bounded proof. It is not product completion. The earlier reconnaissance explicitly found the demo actor path unverified and no cryptographic identity mechanism on that HEAD. Perfect the semantic seam before expansion: AUTHENTICATED PERSON → OWNER/TENANT BINDING → CAPABILITY → PROPOSAL → APPROVAL → EXACT AUTHORIZED EFFECT. Do not invent one giant identity architecture merely to close this. Search and converge existing implementations first.

### 12. APPROVAL / ASK GAP
Keep the Ask-drafted-proposal gap visible. Do not immediately unify incompatible vocabularies. Determine the actual desired product experience first. The important user experience is: owner talks naturally → FYD understands requested presentation change → preview/proposal is understandable → owner approves → exact change occurs. If the proven F1 conversational path already gives us this, Ask does not need to become a second mutation engine simply for architectural symmetry. Decide whether Ask should: remain informational; hand conversational customization to the existing F1 intent compiler; or gain mutation capabilities through the same canonical intent boundary. It must not create a parallel mutation vocabulary.

## TEMPLATE PERFECTION PROGRAM

Stop asking whether a template "renders." For PING, HPP and Coppersmith, evaluate every important page at: mobile, small tablet, tablet, desktop, wide desktop. Evaluate: first impression; visual hierarchy; typography; whitespace; responsive composition; navigation; CTA clarity; media quality; cropping; image loading; trust; evidence visibility; service discovery; contact path; accessibility; touch targets; layout stability; broken assets; empty states; long content; short content; missing media; unusually long names; unusual service counts. 43px means RED if our invariant is 44px. A missing derivative 404 means RED until fixed or explicitly demonstrated irrelevant. Do not normalize small defects because the architecture is exciting.

## CREATE A THREE-SITE DIFFERENTIAL

This should become one of the most valuable tools in the sprint. For each semantic input, compare what each site does. Example: HAS EMERGENCY SERVICE → PING irrelevant, HPP irrelevant, Coppersmith high-priority CTA. HAS STRONG PHOTOGRAPHY → PING secondary, HPP major design material, Coppersmith trust/supporting. HAS COMPLEX TECHNICAL KNOWLEDGE → PING deep Ask/evidence experience, HPP low importance, Coppersmith service explanation. We want to discover the small number of semantic signals that produce large experience differences. Encode stable discoveries into deterministic generator behavior after they survive falsification.

## PERFECT BEFORE GENERALIZE

Any proposed abstraction now must answer: WHICH DEFECT IN PING, HPP OR COPPERSMITH REQUIRES THIS? If the answer is "future customers might need it": DO NOT BUILD IT. If all three sites need the same behavior: candidate shared primitive. If two need it: candidate compositional primitive. If one needs it: first determine whether it reflects a real semantic distinction or a one-off hack. Three examples are enough to discover useful structure. They are not enough to justify universal business ontology.

## HARVEST POLICY CHANGES

Harvest only when it removes commodity implementation from the current three-site loop. Good: robust HTML extraction; image processing; responsive primitives; accessibility; safe URL handling; deterministic hashing; schema validation; browser acquisition; established layout primitives. Bad right now: generalized CRM; campaign systems; multi-network social publishing; arbitrary commerce; giant plugin ecosystems; new agent frameworks; generalized multi-business orchestration. We are not collecting optionality implementations. We are preserving architectural optionality while perfecting one product.
