# CRX Runtime Assessment — Harvest Spec for the PING MVP
**From Nolan, 2026-09-29 ~09:10 MDT. Verbatim. This is the CRX-side harvest specification: harvest surgically, do not adopt wholesale.**

- The repository claims far more completeness than the runtime supports. ARCHITECTURE_INVENTORY.md says infrastructure is 100%, deployment 100%, monitoring 100%, canonical IR 100%, while runtime is only 20%, execution engine 10%, normalization 15%. That means the repo is structurally inverted: lots of surrounding architecture, little reached execution core. This is exactly the kind of imbalance that creates "impressive system, weak product loop."
- There are multiple competing authority systems. The repo's own audit says there are three authority schemes with no mapping: declared 10-level classes, file-path-derived 3-level authority, and integer SQL authority. That is not a documentation problem; it means the same artifact can be classified differently depending on which path evaluates it.
- Runtime code defines law that supposedly belongs to constitutional specs. RUNTIME_AUTHORITY_VIOLATIONS.md identifies six such cases: authority_search.py, authority_classification.ts, authority_registry.ts, constitutional_projection_worker.py, constitutional_law_manifest.ts, and Mission Control's app.py. That violates the repo's own principle that runtime consumes law but does not define it.
- The constitutional repository is internally contradictory and poorly discoverable. The audit found divergent replay laws, ambiguous vault copies, superseded documents that still appear authoritative, missing laws referenced by code, zero cross-references between hundreds of governance documents, and no reliable active/frozen/superseded metadata.
- The repo contains a lot of architectural documentation that describes intended systems rather than reached systems. There are many design reports, freeze specs, amendment specs, verification designs, witness designs, archive designs, constitutional compiler specs, etc. The problem is not that those documents exist; the problem is that they can create a false sense that architectural questions are solved when the runtime path still has unresolved competing implementations and missing wiring.
- The README is essentially empty. README.md is just # crx-runtime. For a repository this complex, that is a major operational flaw. There is no authoritative "start here, this is what actually runs, these are the canonical paths, these are obsolete paths" entry point.
- The repo mixes multiple languages, workspace models, and architectural eras without a clearly enforced canonical runtime boundary. There is a JS/TS monorepo root, a Python pyproject.toml, older extracted code, comparison labs, archive copies, runtime modules, constitutional-integration-lab material, CascadeProjects, brainos, workers, vault, workspace, and assorted top-level scripts. That makes semantic reachability extremely hard to infer from the tree alone.
- The "constitutional" layer has become partly self-referential. The repo created documents governing agent authority, law, replay, mutation, witness, authority taxonomy, frozen state, amendment rules, and compiler generation—while audits repeatedly found those very authorities duplicated or contradicted in runtime. In other words, the constitution is trying to regulate a substrate that is not yet fully converged.
- The repository has a bloat problem acknowledged by its own audit. ARCHITECTURAL_BLOAT_REPORT.md lists 23 items and criticizes security-event spam, governance bureaucracy, trigger duplication, wrapper classes, duplicate audit logging, amendment pipelines, witness validation, and hash verification. That is a strong signal that design accretion outpaced simplification.
- Some of the bloat report's proposed remedies are themselves too absolute. For example, "remove all security events" and "eliminate cross-environment validation" are overcorrections. Structural prevention is good, but observability and independent replay across environments can still be valuable evidence. The repo tends to swing between abstraction-heavy design and absolutist simplification rather than applying measured, reached-path discipline.
- The authority model has especially deep flaws. AGENT_CONSTITUTION.md defines agent classes, model assignments, tool permissions, boot sequences, memory tiers, event permissions, constitutional proposal flows, and governance constraints. That looks rigorous, but several elements are not actually enforced by one canonical authority path. The document says agents cannot self-authorize, cannot emit claims without verification, and must boot through a specified sequence, yet the runtime has historically contained separate authority definitions, scattered literal authority strings, and unrelated enforcement mechanisms. That creates a dangerous condition: policy describes one coherent system, but the code may execute another.
- There is also a conceptual flaw in the agent constitution: it couples some semantic claims too tightly to specific implementation choices. For example, it says OBSERVATION_CREATED may be emitted only from the "7B model, never 14B." That is not a constitutional invariant; that is an implementation policy frozen into constitutional language. Model size should not define epistemic authority. The durable rule should be about what qualifies as an observation, what evidence is required, and which authority can promote it, not which model happened to emit it.
- Likewise, the memory tier model mixes storage implementation with semantics. "Tier 1 = Postgres + Qdrant," "Tier 3 = Qdrant only," etc. are deployment choices embedded in governance. The stronger architecture would define semantic roles—canonical history, derived retrieval projection, ephemeral working state—and let storage implementations vary.
- The event/truth model also has a serious risk of circularity. The system repeatedly uses language like "truth = immutable verified event." That is useful as a storage invariant, but it can become epistemically misleading. An immutable verified event proves that the system recorded a statement or occurrence under a valid protocol. It does not necessarily prove that the external-world content of that event is true. The stronger law is closer to: event integrity != world truth and verified recording != verified proposition. The PING principles already reflect this better: EVENT != EVIDENCE, WITNESS != ORIGIN, METRIC != TRUTH, RESULT != VERIFIED OUTCOME. CRX should adopt that distinction consistently.
- The repository also has a major authority-vs-verification conflation history. The audit itself records that authority search once weighted verification into authority scoring, then later removed it. That shows the architecture has repeatedly mixed "this thing is authoritative" with "this thing passed mechanical verification." Those should remain orthogonal forever: authority answers who/what is allowed to define or decide; verification answers whether a particular artifact/event satisfies evidence/integrity rules. Any system that computes authority from verification scores risks promoting well-formed nonsense.
- There are also concrete code-quality concerns visible from search results. throw new Error(...) still appears in canonical runtime-adjacent TypeScript such as dag_validator.ts, despite the later convergence law banning raw generic errors in sovereign paths. Searches also show many extracted/archive copies using recursive validators and ad hoc assertion logic. That suggests the repo has not fully converged on one deterministic failure representation.
- The repository appears to have multiple canonicalization and fingerprinting lineages. Search results show canonical_engine, canonical_fingerprint_service, identity-engine hashing, hashing comparisons, canonical comparisons, and archived/extracted variants. Even though certification docs claim convergence, the number of surviving implementations means you still need reachability proof before declaring one authority. The dangerous pattern is not merely duplicate code—it is duplicate code with slightly different semantics around nulls, ordering, domain separation, recursion, or serialization.
- The same problem exists for replay and witness logic. There are multiple replay documents, witness laws, replay comparison reports, witness workers, constitutional replay modules, and extracted versions. The repo's own audit says constitution/replay_law.md and vault/laws/REPLAY_LAW.md diverge. That means "replay" is conceptually central but historically forked.
- Persistence semantics are another likely weak point. The repository has event sourcing ambitions, but the audit history mentions schema mismatches, wrong event columns, orphaned queries to nonexistent tables, supersession field mismatches, and Qdrant/Postgres verification discrepancies. Those are not small bugs; they mean the data model has drifted under the architecture. A constitutional runtime cannot tolerate "same concept, several schemas" without explicit adapters and versioning.
- Qdrant is also overrepresented in the architecture relative to its trust role. The repo correctly says Qdrant is projection, not authority, but many retrieval paths and older designs still depend heavily on it. The fact that earlier runtime fixes were needed to verify Qdrant results back against Postgres shows the projection layer had been allowed too close to authority semantics.
- The repo's fallback philosophy is inconsistent. Some code paths fail closed; other audit findings explicitly mention flat-file fallbacks that silently mask database failures. Silent fallback is dangerous in a constitutional system because it makes "authority unavailable" look like "authority resolved from alternate source." Every fallback should declare reduced assurance, not silently pretend equivalence.
- The constitutional document lifecycle is also broken. The audit found active documents, frozen documents, superseded documents, vault copies, amendment patches, and phase-labeled laws with ambiguous status. There is no reliable single machine-readable state transition model. That means the repo can't answer the simplest governance question deterministically: Which exact document currently owns this semantic decision? Until that is mechanically answerable, the constitution is advisory.
- The repository has a proliferation of preservation copies. constitutional-integration-lab, CascadeProjects, archive materials, extracted versions, vault copies, and comparison copies are useful for archaeology but hazardous inside the same searchable namespace. They pollute code search and make it too easy to accidentally inspect or import stale implementations.
- There is also a top-level hygiene problem. The branch includes things like webui.db, token.json, .tmp.driveupload, temp, generated snapshots/filelists, and many audit artifacts at root. Even when non-sensitive, runtime DBs and transient artifacts committed beside source increase reproducibility and security risk. In particular, a file literally named token.json in a public repo is a red flag that should be audited immediately for secret exposure or stale credentials, even if it turns out sanitized.
- Similarly, .env.base committed to the repo deserves scrutiny. It may be harmless configuration, but any checked-in env-style file in a public repo should be assumed sensitive until proven otherwise.
- The AGENTS.md session log is another smell. It contains a large chronological operational history mixed with current norms and "gate status." That makes a mutable log look like canonical architecture. Logs belong in logs. Current laws and current runtime state should have separate, machine-checkable representations. Otherwise future agents inherit stale conclusions as present truth.
- There is a big mismatch between documentation confidence and runtime evidence confidence. Phrases like "100% complete," "certified," "all verified," and "migration complete" appear in docs, yet later audits discover broken networks, unreachable containers, wrong schemas, missing tables, conflicting authority schemes, and stale runtime assumptions. This suggests "complete" has often meant "this phase's tests/doc checklist passed," not "reached, restart-proven, integrated system behavior."
- That is one of the most important flaws: the definition of done has historically been too local. The repository should treat: documented / implemented / tested / wired / reached / runtime-proven / restart-proven / certified as separate states.
- There is also a recurring anti-pattern of inventing new named authorities for concerns that may just need functions or contracts. ReplayAuthority, WitnessAuthority, CertificateAuthority, HashAuthority, GovernanceAgent, constitutional compiler, etc. Some may be justified, but the repository tends to elevate mechanisms into authorities. That increases the number of semantic rulers in the system. The newer "desired new authorities = 0" discipline is a good corrective.
- The AGENT_CONSTITUTION.md boot sequence also looks over-prescriptive. Requiring every agent to emit boot events, verify Postgres/Qdrant, check constitutional docs, register with a supervisor, and emit ready events may be appropriate for some long-lived workers, but not every deterministic function or isolated task worker. The document conflates agent semantics with service lifecycle semantics.
- The model assignment section is similarly brittle. It constitutionalizes qwen 7B vs 14B responsibilities. That will age badly. The rule should be capability-based and evidence-based, not tied to model SKU.
- The repo also appears to treat the constitutional compiler as a remedy for too many problems. Generating registries from specs can help, but if the source specs are contradictory, a compiler merely formalizes ambiguity. Before generating code, you need one authority graph that passes uniqueness and ownership constraints.
- Another flaw is missing clear separation between product runtime and constitutional experimentation. The branch contains production-like runtime, design labs, certification, extracted copies, experiments, and governance materials all in one tree. That makes deployment reachability hard to prove and increases accidental coupling.
- The infrastructure story is likely overstated too. ARCHITECTURE_INVENTORY.md says infrastructure is 100% complete, but AGENTS history records broken Docker networks, unreachable containers, stopped services, Qdrant schema mismatches, and mission-control import failures. A static directory of compose files is not "100% infrastructure complete." Infrastructure completeness needs running, restart-proven, health-checked service graphs.
- Likewise, the monitoring "100% complete" claim is dubious if the runtime itself is only 20% complete. You cannot fully observe a system whose execution semantics are incomplete.
- The execution engine at 10% is actually the most important line in the whole inventory. The repo spent enormous effort on laws, audits, governance, authority, constitutional snapshots, witness semantics, and monitoring while the actual execution engine remained barely implemented. This is architectural inversion. The next work should be ruthless about moving value toward the reached mission/execution loop.
- The repository's own commit history reinforces this. The latest listed commits on the branch are dominated by phrases like "freeze constitutional object model," "constitutional boundary sweep," "deployment readiness," and "replay kernel hardening." That shows a strong bias toward freezing/certifying architecture before enough product execution existed to falsify it.
- The "7 constitutional object definitions frozen" decision is challenged: freezing Identity, Object, Placement, Host, Owner, Revocation, Witness at that stage risks locking vocabulary before enough product pressure. "Frozen" should follow long-lived semantic proof, not precede it.
- Another flaw is that owner/tenant/business semantics are not obviously first-class enough in CRX itself. The repo is heavy on constitutional primitives, but for PING's current MVP the vital chain is caller → tenant → authority → mission → evidence → worker → effect → outcome. CRX should be judged by whether it can support that reached chain, not by how internally elegant its constitutional ontology is.
- The repository also lacks a clear answer to unknown external effect at the constitutional level. The newer PING law—UNKNOWN → HOLD → RECONCILE → never blind redispatch—is stronger than much of the older CRX constitutional material. That should become a foundational execution invariant.
- Result verification appears underdeveloped compared with artifact verification. The repo has extensive witness/hash/lineage verification, but a worker can still plausibly return a structurally valid result that is semantically wrong. The critical distinction is: artifact integrity vs effect correctness vs objective fulfillment. CRX historically focused more on the first.
- There is also too much trust in hash-based identity. Hashes are excellent for content identity, but not for semantic equivalence. Two semantically identical artifacts can hash differently, and two valid hashes do not prove a valid business transition. The architecture sometimes gives hashing an aura of authority that it does not deserve.
- The archive strategy has similar overreach. "Archive instead of delete" is useful for preservation, but if every superseded implementation remains inside the same repository forever, search noise becomes systemic. Preservation should be reachable only through explicit archive paths and excluded from normal build/search/runtime authority.
- The branch likely needs a serious repo hygiene pass: move historical labs under a clearly excluded archive subtree; ensure build tooling cannot import archived code; remove generated DBs/transient artifacts from source control; add one authoritative architecture index; mark every governance doc machine-readably as ACTIVE/SUPERSEDED/FROZEN/DRAFT; designate one reached runtime root.
- The strongest positive thing in the repo is that it already knows many of these flaws. The internal audits are often quite good. The problem is execution: the repository repeatedly discovers architectural contradictions, writes a report/spec about them, then accumulates another layer rather than collapsing the old one.
- So the deepest flaw is: CRX has been better at auditing itself than converging itself. That is why it feels sophisticated but still leaves uncertainty about what is actually authoritative and live.

## Convergence order (forcing this branch toward the PING MVP)

1. One reached runtime root. Identify exactly which code executes PING's path. Everything else is archive/reference until proven reached.
2. One authority graph. Eliminate the three competing authority schemes. No file-path authority. No inline authority literals. One generated/read-only registry if generation is still justified.
3. One canonicalization/hash authority. One byte encoding, one domain separation scheme, one hash implementation.
4. One event schema. Remove legacy CQRS/event-column ambiguity. Version adapters explicitly if old data must remain readable.
5. One identity/tenant chain. Actor identity, tenant binding, capability, agent identity remain distinct but connected.
6. One WorkOrder / ResultEnvelope. Objective-bound, tenant-bound, capability-bound, attempt-bound.
7. UNKNOWN/HOLD/reconciliation as first-class runtime semantics. Not just docs.
8. Independent result/effect verification. Stop equating structurally valid artifacts with successful outcomes.
9. Qdrant fully demoted to rebuildable retrieval projection. No silent fallback, no authority influence.
10. Mission Control consumes truth; it does not invent it. Every displayed state needs a reached source.
11. Archive old implementations aggressively from the runtime namespace. Preserve history without letting it compete in code search/imports.
12. Shrink the constitution. Keep only laws that protect real reached invariants. Move model SKU choices, service topology, boot choreography, and implementation specifics out of constitutional authority.
13. Stop "certifying" unreached architecture. Require integrated + reached + restart-proven before certification.
14. Make PING the first adversarial tenant. CRX should prove itself by safely running PING, not by generating more constitutional documents.

## Overall assessment

constitutional-trunk contains a lot of valuable hardening work, but it should be harvested surgically, not adopted wholesale as PING's runtime architecture. The best pieces are the deterministic replay, canonicalization discipline, evidence/authority separation, mutation constraints, witness thinking, and adversarial audit culture. The worst pieces are authority proliferation, constitutional overreach, archival duplication, status ambiguity, and repeated "spec instead of convergence."
The right goal is not "make CRX more constitutional." It is: extract the smallest set of proven invariants from CRX that make PING safer, more deterministic, more replayable, and harder to lie about — then delete or archive the rest from the reached path.
