## The seven questions — answers with file:line evidence

### Q1. Can a mission be traced BACK to its source event(s)? — YES, via correlation_id, with one documented seam

The back-trace chain is code-complete on the bridge path:

1. **Bridge threads the root correlation_id into the mission row.** `EventToMissionBridge._handleEvent` (event_to_mission_bridge.js:118-146) resolves `correlationId = event.metadata?.correlation_id || event.correlation_id || event.event_id` (:124-127) and stores it in the mission payload along with `event_id`, `event_type`, `source`, `namespace` (:128-135), with `createdBy: 'event-to-mission-bridge'` (:135).
2. **Scheduler preserves it onto the dispatch event.** mission_scheduler.js:248-270 builds the dispatch event with `metadata.correlation_id = payload.correlation_id || payload.event_id || mission.mission_id` (:266) and `metadata.causation_id = payload.event_id` (:267).
3. **Workers preserve it on re-emission.** `BaseWorker._emit` (canonical_workers.js:31-87) sets `correlation_id = options.correlation_id || this._event?.metadata?.correlation_id || this._event?.event_id || options.causation_id` (:44-48) and `causation_id = options.causation_id || this._event?.event_id` (:52). `WorkerRuntime.dispatch` sets `entry.worker._event = event` (worker_runtime.js:106) so the inheritance works.
4. **The spine defaults it when absent.** unified_event_runtime.js:136: `correlation_id: options.correlation_id || eventId`; :135: `causation_id: options.causation_id || null`.
5. **Canonical back-trace entry point.** `MissionRuntime.getTrace(missionId)` (mission_runtime.js:410-462): reads `payload.event_id`, resolves the triggering event's `metadata->>'correlation_id'` (:437-445), returns `{mission, correlation_id, events}` for all events sharing that correlation_id (:455-461). Exposed at `GET /mc/missions/:id/trace` (mission_control.js:412-425).

Join keys: `ping_missions.payload->>'event_id'` → `ping_events.event_id` → `ping_events.metadata->>'correlation_id'`. Indexed: `idx_ping_events_correlation`, `idx_ping_events_causation` (unified_event_runtime.js:61-62).

**Seams:** (a) `getTrace` has a silent fallback — if the triggering event is not in `ping_events`, it uses `payload.event_id` itself as the correlation_id (:445-450), which can return an empty or misleading chain with no degraded flag. (b) For direct `POST /missions` (no bridge), `payload.event_id` is absent; the chain is then correlatable only via `mission_id`-as-`correlation_id` (scheduler :266 falls back to it; worker `_emit` preserves it). (c) The bridge's `_handleEvent` failure path (:142-145) logs only — an event whose mission insert fails leaves no mission and no durable failure record (OBS3's bridge gap, confirmed).

### Q2. Can a mission be traced FORWARD to its effects? — YES at event level; and the forward loop is UNBOUNDED (echo CONFIRMED via a new mechanism)

Forward trace surfaces exist: `GET /events/:eventId/children|/descendants|/ancestors` and `GET /events/correlation/:correlationId` (gateway/routes/events.js:158-183), `GET /mc/replay/trace/:correlationId` (mission_control.js:591-629). Causation links are intact on the bridge path because the scheduler deliberately reuses `payload.event_id` as the dispatch event's `event_id` (mission_scheduler.js:253), so each worker output's `causation_id` points at a real persisted event row.

**The echo is CONFIRMED — but OBS3-F1's cited mechanism is REFUTED.** OBS3-F1 claimed "RecommendationWorker and ProjectionWorker subscribe to their OWN output event types" citing registration lines that **do not exist** at `cc6856c` (file last changed 2026-08-28, verified via `git log`): recommendation is registered on `['CLASSIFICATION_CREATED', 'RECOMMENDATION_CREATE']` and projection on `['KNOWLEDGE_INDEX', 'PROJECTION_CREATE', 'RECOMMENDATION_CREATED', 'LINEAGE_CREATED']` (canonical_workers.js:708-709). The self-subscription is gone; the echo survives through the **dispatch-on-original-event-type** contract (documented in the `[DOC-CONTRACT]` at mission_scheduler.js:24-32):

1. Bridge: `PROJECTION_CREATED` → `REPLAY_VERIFY` mission, `payload.event_type='PROJECTION_CREATED'` (EVENT_MISSION_MAP, event_to_mission_bridge.js:52).
2. Scheduler dispatches on `payload.event_type` → `event_type='PROJECTION_CREATED'` (mission_scheduler.js:255).
3. `WorkerRuntime.dispatch` matches **every** worker whose `eventTypes` include it (worker_runtime.js:97) → **projection AND replay both run**.
4. `ProjectionWorker.handle` emits `PROJECTION_CREATED` unconditionally (canonical_workers.js:182), with a fresh `timestamp` inside the payload (:175-179) → fresh content-hash `event_id` (unified_event_runtime.js:80-83 hashes `{eventType, source, namespace?, payload}`; the fresh timestamp defeats the `ON CONFLICT DO NOTHING` dedupe, :153).
5. Bridge sees the new `PROJECTION_CREATED` → new `REPLAY_VERIFY` mission (`mission_id = sha256('REPLAY_VERIFY:' + new_event_id)`, mission_runtime.js:78-84 — distinct every echo) → goto 2.

**This is truly unbounded, not merely latent-bounded:** each cycle also runs the replay worker (emits `REPLAY_COMPLETED` → `WITNESS_CREATE` → `WITNESS_CREATED` → `LINEAGE_CREATE` → `LINEAGE_CREATED`, terminal) and writes a Qdrant point per projection run. Throttled only by scheduler `maxConcurrent=3` and per-worker `maxConcurrent=2` — rate limits, not termination. The trigger is any `PROJECTION_CREATED` reaching the bridge, including a **single direct `POST /missions {missionType:'PROJECTION_CREATE'}`** (dispatch on `'PROJECTION_CREATE'` → projection emits `PROJECTION_CREATED` → loop ignites), which combined with S5-F1's unauthenticated POST is remotely triggerable. Currently latent only because no business events are flowing (REACHABILITY). It also **poisons observability**: the echo inflates `/mc/missions/stats` completed counts and `ping_events` row counts so they read as healthy throughput; the only early signal is abnormal correlation-group growth per chain.

### Q3. Mission lifecycle traceability — durable states, writers, and what the table alone can(not) reconstruct

Durable states in `ping_missions` (mission_runtime.js:35-63) and their writers, all with conditional guards:

| State | Writer | Guard |
|---|---|---|
| `created` | `MissionRuntime.create` (:76-104); `reapExpiredLeases` (:319-347) resets here | INSERT … `ON CONFLICT DO NOTHING` (idempotent on `mission_id = sha256(missionType:event_id)`) |
| `assigned` | `MissionRuntime.assign` (:119-136) | only from `created`; sets `claimed_at`, `lease_until = NOW()+60s` |
| `running` | `MissionRuntime.start` (:147-158) | only from `assigned` |
| `completed` | `MissionRuntime.complete` (:167-189) | only from `running`; writes `result` (+`duration_ms`), `completed_at` |
| `failed` | `MissionRuntime.fail` (:196-205); `failWithRetry` exhaustion (:238-248) | from `running`/`assigned`/`retry_pending` |
| `retry_pending` | `MissionRuntime.failWithRetry` (:225-273) | from `running`/`assigned`; sets `retries`, `retry_at`, `error` |

Each transition also emits a `MISSION_*` event into `ping_events` (`MISSION_CREATED/ASSIGNED/STARTED/COMPLETED/FAILED/LEASE_EXPIRED`), which is the dual-persistence S5-F13 calls designed duality.

**Reconstruction from the table alone is PARTIAL.** You get current state, coarse timing (`created_at`, `claimed_at`, `started_at`, `completed_at`), attempt count (`retries`), last error (`error`, overwritten each attempt — only the LAST attempt's error survives), and the assigned worker label. You do NOT get: per-transition history (no audit rows), per-attempt errors (attempt history exists only as `MISSION_FAILED` events in `ping_events`, queryable by `payload->>'missionId'` — not by correlation_id, see Q7), or the reaper's uncounted retries (`reapExpiredLeases` resets to `created` **without incrementing `retries`**, so the retry budget is bypassed on the lease-reclaim path). Doc drift: the class docstring still says lifecycle `created → assigned → running → completed/failed → archived`, but **no `archived` state is implemented** and `retry_pending` is missing from the docstring.

### Q4. Attribution — is there ANY verifiable identity→mission binding? — NO

- `POST /missions` (gateway/routes/missions.js:22-30) reads `createdBy` from the request body with **no auth middleware** (S5-F1) and `MissionRuntime.create` stores it verbatim (`options.createdBy || null`, mission_runtime.js:79-82).
- The bridge hardcodes `createdBy: 'event-to-mission-bridge'` (event_to_mission_bridge.js:135) — a literal string, not a verified principal.
- **`created_by` is write-only on the live path:** no live consumer SELECTs `ping_missions.created_by` (grep over `gateway/` + `ping-runtime/` finds only the INSERT and test writers). The `MISSION_CREATED` event payload (`{missionId, missionType, payload, priority}`, mission_runtime.js:97-100) does **not** include `created_by` or any identity, and the scheduler's dispatch event metadata (`mission_type, priority, assigned_to, canonical_hash, confidence, correlation_id, causation_id`, mission_scheduler.js:260-268) carries no identity either.
- Extends S5-F1: the unauthenticated injection path is also an **unattributed-action** path — missions in `ping_missions` cannot be attributed to a real principal, and nothing downstream even reads the claimed value.

### Q6. Retry/poison traceability — complete on the mission path, with two seams

Worker throw → `MissionScheduler._failMission` → `failWithRetry` (3 attempts, 5s backoff; durable in `ping_missions`: `retries`, `error` (last wins), `retry_at`, `retry_pending`) → exhaustion → `DeadLetterAuthority.recordDeadLetter` (mission_scheduler.js:297-333) with `{job_id, job_type, mission_id, correlation_id, causation_id, authority:'MissionScheduler', retry_count, payload}` → `repository_dead_letters` row (schema dead_letter_authority.js:63-91; indexes on `job_type`, `mission_id`, `replayable`, `dead_lettered_at`) + `MISSION_FAILED` journaled in `ping_events` (no subscriber).

**Trace-back path works:** `repository_dead_letters.mission_id` → `ping_missions` row → `payload.event_id` → source event → correlation chain (Q1). DLQ rows also carry `correlation_id`, `causation_id`, `original_job_id`, `failure_reason` (classified by `RetryPolicy`), `replayable`, and a witness.

**Seams:** (a) `error` is overwritten per attempt — attempt-level history survives only in the `MISSION_FAILED` event stream (query by `payload->>'missionId'`). (b) `dead_letter_id = generateId('dl', {original_job_id})` (runtime/kernel/authorities/identity_authority.js:289-291) is deterministic per mission — a second record for the same mission would hit the PK with no `ON CONFLICT` and fail (logged only); the live path records once per mission (failed is terminal; the reaper never touches `failed`), so this is latent. (c) `replayDeadLetter` exists (dead_letter_authority.js) but has **no live caller** — the replay arrow in the module docstring (DeadLetterAuthority → Witness → Replay) is unwired. (d) Bridge-path failures (OBS3-F3/F4) never reach the DLQ at all.

### Q7. What is untraceable

1. **All session-scoped counters** — scheduler (`dispatched/completed/failed/skipped/renewals`), bridge (`listened/missionsCreated/skipped/failed`), per-worker totals, event-runtime stats: in-memory, `scope:'session'`, restart wipes them. A restart erases the entire operational history except the durable tables.
2. **In-flight set** — `MissionScheduler._processing` (mission_scheduler.js:140) is a memory-only Set; only its size is exposed.
3. **Silent dispatch() saturation** (OBS3-F2): the `entry.running < entry.maxConcurrent` gate (worker_runtime.js:98) has no else branch — no counter, no log; the scheduler mislabels it `no worker matched event_type=…` (mission_scheduler.js:280-283) and **burns one of the 3 retries** with a wrong diagnosis. Capacity backpressure is indistinguishable from a routing failure in every durable record.
4. **`MISSION_*` lifecycle events are correlation-orphans** — emitted without `correlation_id` (mission_runtime.js:97-100 etc.), so `getTrace` / `/mc/missions/:id/trace` never include them; the mission lifecycle stream and the business causal stream cannot be joined by correlation.
5. **`ping_events.processed` is a dead column** on the live path (set only for `canonical_events`/`mission_events`; confirmed OBS3) — event-level consumption is journaled at mission granularity only.
6. **Reaper retries are uncounted** — `reapExpiredLeases` resets to `created` without incrementing `retries`; a crash-looping worker can cycle a mission indefinitely outside the 3-attempt budget, visible only via repeated `MISSION_LEASE_EXPIRED` events.
7. **Phantom `causation_id` on the direct-POST path** — without `payload.event_id`, the scheduler sets `event_id = mission.mission_id`, which matches no `ping_events` row; downstream `causation_id`s dangle.
8. **Bridge insert failures** — logged only, event not requeued, no durable record (OBS3, confirmed at event_to_mission_bridge.js:142-145).

## Proposed diffs (WHY → EVIDENCE → MINIMUM CHANGE → TEST → RESULT) — propose only, none applied

### P-T1: Break the dispatch re-match echo
- WHY: Every `REPLAY_VERIFY` mission re-runs the projection worker via event_type re-matching, and the projection worker's output re-mints the mission. Unbounded mission/event/Qdrant growth from a single trigger; also inflates backlog/throughput metrics so the system looks healthily busy while looping.
- EVIDENCE: T1 above (mission_scheduler.js:24-32, :255; worker_runtime.js:97; canonical_workers.js:182, :708-709; event_to_mission_bridge.js:52; unified_event_runtime.js:80-83).
- MINIMUM CHANGE: In `MissionScheduler._dispatch`, dispatch the built event **only to the assigned worker** (`workerName` from `MISSION_WORKER_MAP`) instead of broadcasting to all workers matching `event_type`. Keep the registered-worker guard (phantom-complete prevention) and the `payload.event_type`-based event construction. Update the `[DOC-CONTRACT]` comment to record the new invariant: *a mission executes exactly its assigned worker; event_type on the dispatch event is data, not a routing broadcast.* (Alternative considered and rejected: removing `PROJECTION_CREATED` from projection's eventTypes — that would break the legitimate initial `PROJECTION_CREATE` mission path and the replay worker's need to see it.)
- TEST: unit test — dispatch a synthetic `REPLAY_VERIFY` mission with `payload.event_type='PROJECTION_CREATED'`, assert only the replay worker ran and no `PROJECTION_CREATED` was emitted; then the chain test OBS3 proposed: one `RECOMMENDATION_CREATED` through the bridge → assert `ping_missions` grows by a bounded finite chain and returns to quiescent.
- RESULT: not tested (propose-only).

### P-T5: Verifiable mission attribution
- WHY: `created_by` is an arbitrary unauthenticated string that nothing reads — worse than absent, it invites false trust (same class as S5-F2's capabilities field).
- EVIDENCE: T5 above.
- MINIMUM CHANGE: (a) bind `createdBy` server-side: for `POST /missions`, set `created_by` from the authenticated principal (or `'anonymous'`/reject when no auth exists — do not accept a client-supplied value); keep the bridge's literal as the system principal. (b) include `created_by` in the `MISSION_CREATED` event payload so attribution survives in the event journal. (c) add one reader: an audit query/endpoint filtering missions by `created_by`.
- TEST: unauthenticated POST → 401/403 or `created_by='anonymous'` (per the auth decision); authenticated POST → stored principal matches the caller and appears in the `MISSION_CREATED` event.
- RESULT: not tested (propose-only).

### P-T3/T4/T8: Close the traceability gaps (small, additive)
