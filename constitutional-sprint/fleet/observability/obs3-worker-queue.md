## Hunt results

### Queues with no consumers
- **Q1: /events/unprocessed protocol** (routes + event_processing table + migrations). Zero consumers: JS WorkerRuntime._poll is disabled in code (comment: "disabled to prevent dual input paths"); the Python worker_runtime.py that spoke this protocol is dormant (dev-profile compose, no container). CONFIDENCE: HIGH (code + docker ps).
- **Q2: repository_events as an input table.** EventBridge polls it, but there are NO live writers (agent_memory_authority, distributed_desktop_agents, automatic_mission_generator, continuous_replay_authority, append_orchestrator are not constructed in gateway_runtime.js). The bridge leg polls an unwritten table. CONFIDENCE: HIGH.

### Workers with no liveness signal
- **L1: MissionScheduler** has no heartbeat timestamp and no health-authority check; /scheduler exposes session stats only. If its 5s timer dies silently, nothing in /health changes. CONFIDENCE: HIGH.
- **L2: /health** (gateway/health_authority.js) registers checks for gateway/artifacts/integrations/governance/event_runtime/canonicalization/qdrant/embedding, but NOT for MissionScheduler, WorkerRuntime, EventBridge, EventToMissionBridge, or DeadLetterAuthority. **The gateway can report "healthy" while the entire worker pipeline is stopped or dropping work.** This is the FAKE-health finding. CONFIDENCE: HIGH (bootstrap lines 726-759 enumerated).

### Workers that silently drop items
- **F1 (CRITICAL, latent infinite echo): RecommendationWorker and ProjectionWorker subscribe to their OWN output event types.** RecommendationWorker eventTypes include RECOMMENDATION_CREATED (canonical_workers.js register list); ProjectionWorker eventTypes include PROJECTION_CREATED. MissionScheduler dispatches on the ORIGINAL business event type, and WorkerRuntime.dispatch matches every worker whose eventTypes include it. So a PROJECTION_CREATE mission dispatches event_type=RECOMMENDATION_CREATED to BOTH projection and recommendation; recommendation emits a NEW RECOMMENDATION_CREATED (fresh timestamp -> fresh content-hash event_id -> dedupe does not catch it) -> bridge creates another PROJECTION_CREATE mission -> repeat. Same for projection on PROJECTION_CREATED (REPLAY_VERIFY mission dispatches PROJECTION_CREATED to projection AND replay; projection re-emits PROJECTION_CREATED...). Each echo spawns downstream replay/witness/lineage missions and Qdrant points. Unbounded mission-table growth, throttled only by scheduler maxConcurrent=3. Currently latent: REACHABILITY observed EventBridge "0 unprocessed" and no business events flowing, so the loop has no fuel. The first live RECOMMENDATION_CREATED lights it. CONFIDENCE: HIGH (mechanism fully code-traced; trigger condition not yet observed live).
- **F2: concurrency saturation misclassified as routing failure.** WorkerRuntime.dispatch skips (silently, no counter) when entry.running >= maxConcurrent; returns null; MissionScheduler treats null as "no worker matched event_type=..." -> _failMission -> burns one of 3 retries with a misleading error. A transient capacity spike becomes a DLQ candidate with a wrong diagnosis. CONFIDENCE: HIGH.
- **F3: EventBridge cursor advances past failures.** In both _bridgeRepositoryEvents and _bridgeCanonicalEvents, per-row emit failures are caught (errors++ in-memory only) and the cursor is set to the LAST row of the batch unconditionally. Failed rows are never retried and leave no durable failure record. For canonical_events, a rejected emit also leaves processed=FALSE but the cursor has moved past -> row is stranded (WHERE processed=FALSE still matches it, but `event_id > cursor` excludes it forever). CONFIDENCE: HIGH.
- **F4: repository_events bridge cursor is not a valid watermark.** Cursor comparison is lexicographic `event_id > last_event_id`, but repository_events event_ids are content hashes (identityAuthority.generateEventId -> generateId('evt', {event_type, aggregate_id}) -> canonical-bytes hash), NOT insertion-ordered. New rows whose hash sorts below the cursor are never bridged; no signal. (Moot while Q2 holds, live the moment any writer is re-enabled.) CONFIDENCE: HIGH on mechanism, MEDIUM on impact (no live writers today).

### Duplicate consumption of the same item
- **D1 = F1**: the same RECOMMENDATION_CREATED / PROJECTION_CREATED event is consumed by two workers (projection+recommendation, projection+replay respectively) BY DESIGN of overlapping eventTypes, and the echo makes it unbounded. Distinguish from legitimate fan-out (embedding subscriber + bridge on the same event = different stages, fine).
- **D2 (checked, clear)**: UnifiedEventRuntime.emit dedupes by content-hash event_id with ON CONFLICT DO NOTHING and suppresses handlers/integrations on duplicate delivery (unified_event_runtime.js:147-164). Redelivery does not double-fire in-process subscribers. The echo in F1 escapes this ONLY because each echo carries a fresh timestamp -> fresh hash. CONFIDENCE: HIGH.

### Backlog metric
Exists and is real for the mission pipeline: /missions/pending, /missions/stats, /queues, /queues/:eventType, /scheduler, /workers, /bridge, /event-mission-bridge, /dead-letters/stats (gateway/routes/mission_control.js). Gaps: /queues reads the vestigial protocol (not the live mission queue); event_processing failures have no read endpoint; all worker/bridge stats are session-scoped (restart wipes them); ping_missions is the only durable backlog record. CONFIDENCE: HIGH.

### Poison-message path
Complete on the JS mission pipeline: worker throw -> failWithRetry (3 attempts, 5s backoff, durable in ping_missions with error text) -> exhaustion -> DeadLetterAuthority.recordDeadLetter -> repository_dead_letters (durable, indexed, readable via /dead-letters*) + MISSION_FAILED event journaled in ping_events (no subscriber; journal-only). Bootstrap now injects the authority (previously accepted-but-never-injected per code comment). On the bridge path (F3) and the vestigial queue protocol, the poison path is broken/absent. CONFIDENCE: HIGH.

### Journaling of consumed items
- Mission layer: every consumption journaled in ping_missions (assigned/started/completed/failed + retries + error). COMPLETE.
- Event layer: ping_events has a `processed` BOOLEAN column (created in UnifiedEventRuntime.initialize) that NOTHING sets on the live path. DEAD COLUMN. The event_processing table serves only the vestigial protocol. Bridge stats are session-scoped. So: item-level consumption is journaled at mission granularity, not event granularity. CONFIDENCE: HIGH.

## Proposed diffs (WHY -> EVIDENCE -> MINIMUM CHANGE -> TEST -> RESULT)

### P1: Break the worker echo loops (F1/D1)
- WHY: RecommendationWorker and ProjectionWorker list their own output event types, so every downstream mission re-triggers them with fresh timestamps; the bridge converts each echo into new missions. Unbounded.
- EVIDENCE: ping-runtime/workers/canonical_workers.js registerCanonicalWorkers: recommendation eventTypes [..., 'RECOMMENDATION_CREATED'] (line ~716), projection eventTypes [..., 'PROJECTION_CREATED'] (line ~711); WorkerRuntime.dispatch matches all workers by event_type; _emit includes fresh constitutionalTimeAuthority.nowAsISOString() -> fresh content-hash event_id; EVENT_MISSION_MAP turns each echo into a mission.
- MINIMUM CHANGE: remove 'RECOMMENDATION_CREATED' from the recommendation worker's eventTypes and 'PROJECTION_CREATED' from the projection worker's eventTypes (one line each). Keep the *_CREATE trigger types. Rationale: a worker must never be registered on an event type it emits.
- TEST: gateway/test_dormant_worker_gate.js exists as the pattern; add a static assertion test that no registered worker's eventTypes intersect the set of event types it emits (parse _emit call sites vs registration list). Then a live test: emit one RECOMMENDATION_CREATED, assert ping_missions grows by exactly the expected finite chain (<= 8 missions), not unboundedly.
- RESULT: chain terminates; per business event exactly 8 missions (observation, claim, classification, recommendation, projection, replay, witness, lineage).

### P2: Count (don't drop) concurrency-saturated dispatches (F2)
- WHY: dispatch() silently skips when running >= maxConcurrent and the scheduler misdiagnoses it as a routing failure, burning retries.
- EVIDENCE: ping-runtime/workers/worker_runtime.js dispatch(): the `if (entry.running < entry.maxConcurrent)` gate has no else branch; MissionScheduler._dispatch treats null dispatchResult as "no worker matched event_type=...".
- MINIMUM CHANGE: add `this._stats.saturated++` + per-worker `entry.totalSaturated++` in an else branch; return a sentinel `{ status: 'saturated' }` instead of null; in MissionScheduler._dispatch, treat 'saturated' as retryable-backoff (requeue without burning a full retry: set retry_at, keep status retry_pending, do not increment retries).
- TEST: unit test with maxConcurrent=1 dispatching two events concurrently; assert saturated counter increments and the mission is requeued (status retry_pending, retries unchanged).
- RESULT: backpressure becomes visible and non-destructive.

### P3: Make EventBridge failures durable and retried (F3)
- WHY: cursor advances past failed rows; failures exist only in an in-memory counter.
- EVIDENCE: ping-runtime/events/event_bridge.js: cursor set to rows[rows.length-1].event_id after the loop regardless of per-row failures; errors counted in this._stats.errors only.
- MINIMUM CHANGE: advance the cursor only to the last SUCCESSFULLY bridged row; on failure, INSERT the row id + error into repository_dead_letters (reuse DeadLetterAuthority with authority='EventBridge') instead of only errors++.
- TEST: seed one canonical_events row whose emit is rejected (bad event_type), run bridge, assert cursor did not advance past it and a dead-letter row exists; second poll still sees the row.
- RESULT: bridge failures are visible, bounded, and recoverable.

### P4: Put the pipeline on /health (L2)
- WHY: /health reports healthy with the whole worker pipeline dark.
- EVIDENCE: gateway/bootstrap/gateway_runtime.js lines 726-759 register 8 checks; none covers MissionScheduler/WorkerRuntime/EventBridge/EventToMissionBridge/DeadLetterAuthority.
- MINIMUM CHANGE: registerHealthCheck('worker-pipeline', ...) returning healthy iff missionScheduler._running && workerRuntime._running && eventBridge._running && eventToMissionBridge started, plus pending-mission count and dead-letter count as detail fields.
- TEST: stop the scheduler in a test harness, assert /health flips to unhealthy.
- RESULT: FAKE-health gap closed.

### P5 (hygiene): retire or re-home the vestigial queue protocol
- WHY: /events/unprocessed|/processed|/failed + event_processing + the disabled _poll advertise a queue that has no producers and no consumers; the Python fleet that spoke it is dev-profile dormant.
- EVIDENCE: routes in gateway/routes/events.js:129-150; _poll disabled ping-runtime/workers/worker_runtime.js:49-56; compose.yaml profiles:[dev] on all six worker services; docker ps shows none running.
- MINIMUM CHANGE (propose-only): either (a) delete the three routes + _poll + Dockerfile.worker-runtime + compose worker services, or (b) document them as RESERVED in a WORKER_PROTOCOL.md with a dormant gate test like test_dormant_worker_gate.js. Do not leave them silently half-alive.
- TEST: grep CI gate asserting no live references to /events/unprocessed outside the vestigial files.
- RESULT: no future engineer re-enables a queue whose event vocabulary (CLAIM_GENERATED etc.) does not match the live schema.
