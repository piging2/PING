## 1. Mission-result flow trace

### Where a completed mission's result goes today

Writer (single live writer): `MissionScheduler._dispatch()` (ping-runtime/orchestration/mission_scheduler.js:371)
calls `MissionRuntime.complete(missionId, { worker: workerName, completed_at }, fencingToken)`.

CRITICAL: the worker's actual product — `dispatchResult` (the `{status:'ok', claim}`, `{status:'ok', recommendation}`, observation, etc. returned by `WorkerRuntime.dispatch`) — is checked for `status === 'failed'` and then DISCARDED. It never reaches `complete()`. The `result` JSONB column in `ping_missions` therefore holds only bookkeeping metadata: `{worker, completed_at, duration_ms}`. Even the human-review surface shows no worker product.

Storage: `ping_missions.result` (JSONB), `completed_at`; plus a `MISSION_COMPLETED` event in `ping_events` with payload `{missionId, result, duration_ms, attempt}`.

### Consumer classification table

| # | Consumer | What it reads | Classification |
|---|----------|---------------|----------------|
| 1 | `MissionRuntime.reconcileLostCompletions` (mission_runtime.js:336) | `result` for crash-after-accept re-emit of `MISSION_COMPLETED` | RECOVERY (infra, not product use) |
| 2 | Orca control loop `observe()` (orca_control_loop.js:165) | presence bit only (`result_recorded`) | VERIFICATION / TELEMETRY |
| 3 | `MissionRuntime.getTrace` → `GET /missions/:id/trace` | full mission row incl. `result` | HUMAN-REVIEW (but content is metadata-only) |
| 4 | `TriggerAuthority._emitTriggerProcessed` → `replayTrigger` | `mission_result` embedded in `TriggerProcessed` payload; read back only by trigger replay | RECOVERY-only |
| 5 | `MISSION_COMPLETED` event | — | DEAD-END: zero registered worker subscribers, zero `EVENT_MISSION_MAP` entries, zero `MISSION_WORKER_MAP` entries |
| 6 | Operator API surface | — | GAP: no completed-missions or result-listing endpoint (`/missions` routes have active/pending/stats/trace only) |
| 7 | `gateway/mission_authority_v2.js` completeMission | in-memory legacy map | SHELFWARE: not referenced by bootstrap/composition; legacy, Lane A territory |

No non-test, non-recovery consumer of mission results exists. The audit claim (144 completed, zero consumers) is consistent with code evidence; the live count could not be re-verified (Oracle hop down).

### First missing edge (mission loop)

TWO coupled breaks, in order:
1. **Content**: `dispatchResult` discarded at `complete()` — the stored result contains no worker product. (Fix: spread worker output into the completion payload.)
2. **Read surface**: no operator endpoint lists completed missions/results.

Neither is release-blocking for the certified candidate (no live caller depends on result content; change is additive).

### The five questions — mission-result content break
- WHY DOES THIS EXIST? `complete()` was built for lifecycle bookkeeping (fencing token, duration); the worker product was never part of the contract.
- WHO CALLS IT? Only `MissionScheduler._dispatch`.
- WHAT HAPPENS ON RETRY/RESTART? Attempt-fenced (CE-002); reconciler re-emits canonical-equivalent completion (deterministic identity, CE-001). Persisting worker output changes neither.
- WHAT TEST WOULD HAVE CAUGHT IT? A test asserting `ping_missions.result` contains the worker's returned product after a completed dispatch (nothing asserts result content today).
- WHAT CLAIM ARE WE MAKING THAT WE CANNOT PROVE? That completed missions constitute "organizational knowledge" — the stored result contains no knowledge, only metadata.

The next edge is deciding whether machine work products enter the knowledge graph at all — that determines whether the "accumulating organizational knowledge" loop includes the machine's own output.
- EXACT EVIDENCE: graphProjectionEvents list at `gateway/bootstrap/composition/core_event_spine.js:70`; `addNode(..., {status:'candidate', sourceEventId})` at :78; MISSION_COMPLETED emitted with `{missionId, result, duration_ms, attempt}` at `mission_runtime.js:236` with zero consumers (see consumer table).
- COUNTEREVIDENCE: CG-001 (decided 2026-09-19): tenant owner is the default human decision authority — approval stays human either way. Auto-projection as *candidate* does not auto-promote; the promoter still requires explicit approval. Risk: candidate-node volume/noise from machine output.
- OPTIONS: (a) Add MISSION_COMPLETED to graphProjectionEvents (machine output becomes approvable knowledge); (b) keep projection to business events only (knowledge = human/business-domain facts); (c) project only selected mission types (e.g. recommendations) — middle path.
- CONSEQUENCES: (a) closes the loop observations→promotion→retrieval for machine work; risk of graph noise. (b) keeps the graph clean but the 144 missions' products never enter organizational knowledge. (c) needs a mission-type allowlist (new policy surface).
- DEFAULT IF NOLAN DOES NOTHING: (b) — projection list stays as-is; machine results stay out of the graph.
- RECOMMENDED NEXT EXPERIMENT: After LANEB-002 lands, project MISSION_COMPLETED for ONE mission type (e.g. recommendation missions) as candidates for 7 days; measure approval/rejection rate; decide (a)/(b)/(c) on evidence.
