## 2. Object model

- **Event** — `{ id, name, data, user?, ts }`. Triggers functions by name/wildcard/CEL `if` match. One event fans out to every matching function.
- **Function** — registered code unit: id, triggers (event/cron), config (retries, concurrency, throttle, rateLimit, debounce, batch, priority, cancelOn, timeouts, idempotency CEL, onFailure). Addressed by **Composite ID** = `<app-id>-<function-id>`.
- **Run** — one execution of a function. Keyed by server-generated `run_id` (ULID, e.g. `01ABC123...`). May span many Call Requests over a long period.
- **Call Request** — server → SDK HTTP POST: `{ events[], steps{...}, ctx{run_id, attempt, disable_immediate_execution, use_api, stack, qi_id} }`. `attempt` is 0-indexed, incremented per function retry, resets after a successful step.
- **Step** — a retriable code block inside a run, reported by the SDK as a 206 response: `{ id (hashed), op (opcode), displayName?, opts? }`. Step types (opcodes): `StepRun(2)` / `StepPlanned(4)` / `StepError(3)` / `StepNotFound` / `Sleep(5)` / `WaitForEvent(6)` / `InvokeFunction(7)` / `AIGateway(8)` / `Gateway(9)` / `WaitForSignal(10)` / `RunComplete(11)` / `StepFailed(12)` / `SyncRunComplete(13)`.
- **Queue item** — the schedulable unit. `qi_id` in `ctx` identifies the current queue item so the server can reset the retry counter after a successful checkpoint (one queue item shared across many checkpointed steps).
- **History / trace** — per-run ordered record of step spans (status, timing, op, input/output) plus terminal records (`FunctionCancelled`, `function_finishes`-style rows per operator notes).

## 3. ID scheme

- **Event `id`**: producer-set string; idempotency key over a **24h window**. Duplicates are stored (visible in event history) but do not trigger functions. Must be event-type-specific.
- **Function idempotency key**: derived from a CEL expression over `event.data` (e.g. `event.data.userId + "-" + event.data.organizationId`); one execution per unique key per 24h per function.
- **`run_id`**: ULID, generated by the runner per run, stored in the State store.
- **Step `id`**: **hex-encoded SHA-1 of the developer-supplied step id**, so all SDKs/languages produce identical keys ("cross-language, cross-cloud migrations of Functions mid-Run"). Repeated ids in loops get `:n` suffix before hashing (`my-step-id`, `my-step-id:1`, `my-step-id:2`; zero-index has no suffix).
- **fn_id / app_id**: UUIDs. Composite function id = `appId-functionId`.
- **External operation keys**: explicitly NOT the attempt id — docs require stable business keys (checkout id, order+message-type) at the external service, because "a request can succeed before Inngest records the step result."

## 4. State transitions

Run status (official, `pkg/api/v2/README.md`): `QUEUED → RUNNING → {COMPLETED | FAILED | CANCELLED}`.
Function status: `ACTIVE | PAUSED | ARCHIVED | DISABLED`.

Step lifecycle (from SDK_SPEC + retries doc):
1. Discovered in Call Request → reported (206) with opcode.
2. `StepPlanned` → separate Call Request with `?stepId=<hashed-id>`; SDK memoizes prior steps and runs only that step.
3. Success → `StepRun` with JSON `data`; server memoizes under hashed id. Error → `StepError`; server records the attempt, saves error, schedules retry with backoff+jitter; per-step retry counter (default 4 retries after the initial attempt; `retries: 0` disables).
4. Retries exhausted → final `{error}` memoized; error re-thrown into developer code on next Call Request; unhandled → function retry (`attempt`+1) or terminal FAILED → `inngest/function.failed` event fires → `onFailure` handler runs.
5. `Sleep`/`WaitForEvent`/`InvokeFunction`/`AIGateway`/`Gateway` are **async opcodes**: the SDK yields, the server schedules future work (wake-up, event listener, child run) and resumes later; memoized with `null` (sleep/timeout) or the event payload.

## 5. Authority boundary

- The **Inngest Server is the high-level event-loop authority**: it decides which step runs, when retries happen, what is memoized, ordering, concurrency/fairness, and cancellation. The SDK is a **stateless reporter/memoizer**: it executes developer code, reports steps, and injects memoized results. The server never runs user code; the SDK's code runs at the developer's HTTP endpoint (or outbound WebSocket via Connect).
- Trust boundary: **signing key** (HMAC) verifies server↔SDK requests, with a documented fallback key and one-way failover; **event key** authorizes event ingestion.
- Determinism contract: "an SDK MUST maintain determinism in Call Requests when the underlying code has not changed, ensuring that two identical Call Requests will always produce the same output." Cross-SDK step-key stability is what makes this hold.

## 6. Persistence semantics

- Per-run **State store**: step results keyed by hashed step id as `{data}` or final `{error}`; server persists each step as it completes, so a run "can resume on the same machine or a different one."
- Delivery is **at-least-once** everywhere: events → functions; step retries re-run developer code. The idempotency story is layered, not absolute: event `id` (24h, producer), function `idempotency` CEL (24h, consumer), and still-required external operation keys.
- **Checkpointing** (sec. 10): optional optimization — the SDK persists sync-opcode results (`StepRun` etc.) via `POST /v1/checkpoint/{runID}/async` without yielding the HTTP response; async opcodes force a yield (206). Graceful fallback is specified: if checkpointing fails, buffered steps go in the normal 206 response — "function execution correctness does not depend on the checkpoint API being available."

## 7. Evidence / receipts

- Per-step **trace**: every step span with status, timing, opcode, and (optionally) input/output — queryable via `GET /runs/{run_id}/trace`.
- **System events**: `inngest/function.failed` (terminal failure; drives `onFailure`), `inngest/function.cancelled` (cancellation; usable for cleanup).
- Event history records even deduplicated (suppressed) events — duplicates are visible, not silently dropped.
- Run output pollable (`/v1/checkpoint/{runID}/output?token=...` JWT).

## 8. Retries / failures

- Per-`step.run()` retry counter; default **4 retries after the initial attempt** (5 total); function-level `retries` config (0–20 in TS v4).
- Backoff with jitter by default; `RetryAfterError` for provider-supplied retry times; `NonRetriableError` for permanent failures (validation, 4xx).
- `attempt` (0-indexed) delivered in `ctx`; resets after a successful step.
- Memoized `{error}` is re-thrown into developer code; if the developer swallows it or throws a new error, the SDK marks the request non-retriable (spec 5.2.2).
- `StepNotFound` handles code-changed-mid-run and non-deterministic functions (warn + continue with stack-ordered recovery, 5.4).
- Known sharp edge (operator note, joelclaw docs): worker crashes can leave stale `RUNNING` runs — the list view is not the authority; run detail/trace is.

## 9. Revocation model

- `cancelOn: [{event, if}]` — a matching later event cancels the run. **Active step execution is NOT stopped**; cancellation prevents the *next* step from starting. Fires `inngest/function.cancelled`.
- `timeouts.start` / `timeouts.finish` cancel runs that wait too long to start or run too long.
- Function-level: `PAUSED` (while paused, event idempotency is ignored — replay after unpause may skip runs), `ARCHIVED`/`DISABLED`.
- Run status `CANCELLED` is terminal.

## 10. Concurrency controls

- `concurrency: {limit, key}` — max in-flight runs per function or per CEL key (per tenant/customer) — fairness is first-class.
- `throttle: {limit, period, burst, key}` — delays starts over the limit.
- `rateLimit: {limit, period, key}` — hard cap; **excess events are skipped (dropped), not queued**. Keeps the FIRST event (opposite of debounce).
- `debounce: {period, key, timeout}` — waits for event quiet; runs with the LAST event's data; `timeout` forces a max-wait execution.
- `batch` — up to 100 events per run.
- `priority: {run: <CEL>}` — −600..600, higher runs sooner.

## 12. vs Temporal — what is DIFFERENT and SMALLER

- **No event-sourced replay of the workflow function.** Temporal replays a recorded history through deterministic workflow code; Inngest re-invokes the function once per step and injects memoized step results. There is no workflow-code determinism requirement beyond "same Call Request → same output."
- **Steps are inline closures, not separately registered activities.** A step boundary is one line (`step.run("id", fn)`); no activity definitions, no worker fleet, no long-lived process — just an HTTP endpoint (or Connect WebSocket).
- **Retry scope is function-level with per-step counters**: the whole function body re-executes each call, and anything outside a step re-runs every time. The durability burden is explicit and local: wrap side effects in steps.
- **Invocation is event-driven**, never RPC-by-ID: events fan out to matching functions (name/wildcard/CEL); producers never name consumers. Temporal routes by explicit Workflow ID.
- **What's smaller for PING:** the step protocol is ~4 primitives (hashed step key, 206 report/memoize exchange, opcode yield classification, per-step attempt counter) versus Temporal's history engine + workers + deterministic-code compiler constraints. The cost Inngest accepts (and PING must too, if adapted): memoization granularity is only as good as the developer's step discipline, and at-least-once means external effects still need stable operation keys.

## 13. SMALLEST MISSING PRIMITIVE for PING's event-kernel

**Checkpointed step boundary with deterministic step keys + per-step attempt counters + sync/async opcode classification.**

PING already has: append-only event journal, missions, WorkerRuntime dispatch, capabilities, evidence. What it does not have, and what proofs 9–14 (create mission → worker result → fallback → verification → replay) actually require *inside* a mission execution, is:

1. A **deterministic step key** (`sha256`-family hash of `mission_id ‖ step_name ‖ occurrence_index`, `:n`-suffixed for loops) under which a step's result is durably memoized — separate from the event journal.
2. A **memoize-or-execute rule**: on (re)dispatch, the worker replays memoized `{data}|{error}` for known step keys and executes only unknown ones — so a crashed worker resumes mid-mission instead of restarting it.
3. **Per-step attempt counters with backoff scheduling**, reset on step success, plus a `NonRetriable` vs `RetryAfter` error taxonomy — failure-injection missions (proof 11) need attempt counts to be first-class data.
4. A **sync/async opcode split**: sync steps checkpoint in-process; async steps (sleep, wait-for-event, invoke-child) *yield* to the scheduler instead of blocking the worker — this is what lets one worker fleet serve long waits without thread starvation.

That is the whole harvest: four rules, no new subsystem, no Inngest code. The 24h event-id dedupe window and CEL-keyed function idempotency map onto PING as: event envelope carries an idempotency key with a bounded window, and per-function CEL dedupe keys — both small additions on top of the same primitive.

## 15. License finding — FLAG FOR NOLAN

- **Inngest server + CLI: SSPL 1.0 with Delayed Open Source Publication (DOSP): Apache-2.0 begins on the 3rd anniversary of each version's release.** SSPL §13 requires anyone offering the program (or a modified version) as a service to third parties to release the defined "Service Source Code" under SSPL — that definition sweeps in management/API/automation/monitoring/storage/hosting software. **Do not copy server code into PING; do not embed or operate Inngest server as a PING service.**
- **All Inngest SDKs: Apache-2.0.** Safe to read and learn from; we still take only the protocol mechanism, no code.
- This proposal is therefore **mechanism-only ADAPT**: the harvested artifact will be original PING code implementing the four rules in §13. No license contamination path.

## 16. Proof mapping

- **9** (create one mission) — Run keying: ULID `run_id` per mission execution; queue-item ref (`qi_id`) separating scheduling from execution.
- **10** (worker returns result) — `StepRun` memoized `{data}` under the deterministic step key.

- **13** (verified only after independent verification) — deterministic memoization lets a verifier re-derive step results from the same keys without trusting the worker's claim. (Honest note: Inngest itself does not do independent verification; the primitive *enables* it.)

No proof_id → the rest (throttle/debounce/rateLimit/batch/priority/onFailure/cancelOn) is OPTIONAL. Of these, `debounce` and `rateLimit` are the cheapest future additions for the FYD loop; they are not proposed now.
