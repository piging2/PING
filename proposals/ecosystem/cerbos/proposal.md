# Harvest Proposal: Cerbos (decision authority mechanics)

## What Cerbos is
Cerbos is an open-source, language-agnostic authorization layer. The core product is the Cerbos PDP (Policy Decision Point): a stateless service that evaluates YAML policies and answers two questions: `CheckResources` ("can this principal do these actions on these resources?") and `PlanResources` ("which instances of a resource kind may this principal act on?"). Policies are managed via Git-ops (disk, git, object stores, databases) and a cloud control plane (Cerbos Hub, proprietary) versions/distributes them. The client application (your app, API gateway, Envoy sidecar) is the Policy Enforcement Point (PEP); the PDP only decides, it never enforces.

Verdict: **ADAPT** — take the decision-request shape, the decision-receipt/audit record schema, and the policy-version lineage mechanism; re-implement clean-room in piging2 TypeScript. Do NOT adopt the Go PDP service as a runtime dependency (violates zero-dependency preference and would introduce a second execution/authority boundary, conflicting with PING's single-authority doctrine).

## Object model
- **Principal**: `{id, roles[], attr{}, policyVersion?, scope?}`. The actor. Context attributes (`attr`) are free-form; CEL conditions in policies read them via `request.principal.attr.*`.
- **Resource**: `{kind, id, attr{}, policyVersion?, scope?}`. `kind` selects the resource policy; `attr` carries instance data for conditions.
- **Action**: a string name per resource kind (`view`, `approve`, `delete`, or namespaced `view:public`; wildcard `*` allowed in policies).
- **Policy (resource)**: YAML, `apiVersion: api.cerbos.dev/v1`, `resourcePolicy: {version, resource, rules[], importDerivedRoles[]?}`. A rule = `{actions[], effect: EFFECT_ALLOW|EFFECT_DENY, roles[]|derivedRoles[], condition?}`. Conditions are CEL expressions over `request.principal`, `request.resource`, and JWT-derived vars. Default-deny: no matching rule = deny.
- **Principal policy**: per-principal overrides (`principal.donald_duck.v20210210`), evaluated before resource policies.
- **Derived roles**: named, condition-gated role assignments (`owner := parentRoles:[user] if resource.attr.owner == principal.id`); resolved at evaluation, returned as `effectiveDerivedRoles`.
- **Policy module ID**: `<kind>.<name>.v<version>/<scope>` — the stable address of one compiled policy (e.g. `resource.leave_request.vdefault/acme.hr`). This is the lineage key.
- **Scope**: dot-path hierarchy (`acme.corp`, `acme.hr`); policies can nest and the response reports the `matchedScope` that was active.
- **Schema (attribute schema)**: optional JSON Schema for principal/resource attrs; violations surface as `validationErrors[]` with `source: SOURCE_PRINCIPAL|SOURCE_RESOURCE`.

## ID scheme
- `requestId`: optional, application-provided; echoed back for correlation. Application-chosen, NOT generated by the PDP.
- `cerbosCallId`: PDP-generated ULID per API call (e.g. `01HHENANTHFD5DV3HZGDKB87PJ`); written into the audit log for the request, so the response and its audit record join on it.
- Audit record `callId`: same ULID as `cerbosCallId`.
- Policy module ID: `<kind>.<name>.v<version>/<scope>` as above.
- Policy `version`: opaque string (`default`, `20210210`, `v1`, `1.0.0`); request pins via `policyVersion` on principal/resource, else server `defaultPolicyVersion` applies.
- No signatures on decisions in OSS: receipts are integrity-by-transport; Hub stores them centrally but OSS leaves signing to the log pipeline. (Noted as a gap; piging2's DecisionReceipt should be hash-bound, see primitive below.)

## State transitions (decision lifecycle)
1. **Author**: YAML policy committed (Git / disk / DB / Hub store).
2. **Compile**: `cerbos compile` validates + runs co-located `*_test.yaml` suites; failure blocks deployment (CI gate).
3. **Distribute**: PDP loads compiled bundle; disk driver watches for changes and hot-reloads; Hub pushes versioned bundles to the fleet.
4. **Request**: PEP sends `CheckResources`/`PlanResources` with principal+resources+actions+context (+ optional JWT auxData for token-derived vars).
5. **Evaluate**: engine resolves policies by (kind, version, scope), computes derived roles, evaluates rules in order, collects `outputs` (policy-defined side-channel values), enforces schemas, returns per-action `EFFECT_ALLOW|EFFECT_DENY` + `meta` (matchedPolicy, matchedScope, effectiveDerivedRoles) + `cerbosCallId`.
6. **Record**: PDP appends a `DecisionLogEntry` to the audit backend (same `callId`), subject to decision filters (`ignoreAllowAll` etc.). Hub backend streams with local disk buffer for network outages.
7. **Enforce**: PEP acts on the decision. PDP never enforces — that is the PEP's job (app middleware, Envoy ext_authz, query-plan adapter filtering).

## Authority boundary
- **PDP decides, PEP enforces.** Cerbos explicitly does not touch your data or apply its own enforcement; the app must call and must obey. Defense-in-depth pattern: coarse decision at the gateway (Envoy ext_authz -> Cerbos) + fine-grained decision in the service, both against the same policies/attribute vocabulary.
- Policy authoring/approval (PAP) lives outside the PDP (Git PR review, or Hub's review flow). The PDP only reads compiled policy; admin API mutations require a mutable store + Basic Auth and are an operational backdoor, not the normal path.
- JWTs are verified by the PDP against configured keysets (pluggable trust), so the gateway/adapter can forward raw tokens instead of reimplementing verification.
- Note for PING: Cerbos splits decision and enforcement across a network boundary. For piging2 the right adaptation is the *contract* (request shape, receipt, lineage), not the network split — PING's capability evaluation stays in-process under one authority; the receipt is what gets harvested.

## Persistence semantics
- PDP is **stateless**: no decisions, sessions, or revocations stored in the PDP. Policies are the only state, held in the external store (disk/git/DB/Hub).
- Audit logs are **append-only event records** (newline-delimited JSON, local file, or streamed to Hub). Retention is operator-owned (log rotation settings; external SIEM for long-term).
- Policy updates are hot-loaded without restart (disk watch); Hub does atomic bundle swaps to the fleet. Versioning is by the `version` string + Hub deployment versions; rollback = point at a previous bundle/store revision.
- PDP local decision logs are per-instance (no cross-instance aggregation in OSS); Hub provides the unified view. This is a known OSS limitation — piging2's event spine must not repeat it.

## Evidence / receipts
The `DecisionLogEntry` (from PR #960, verified shape):
```
{ "log": {"logger":"cerbos.audit","kind":"decision"},
  "callId": "<ULID>", "timestamp": "<RFC3339>",
  "peer": {"address":"...","userAgent":"...","forwardedFor":"...","authInfo":"..."},
  "metadata": {<grpc/http metadata map>}, "method": "CheckResources",
  "checkResources": {
    "inputs":  [{requestId, resource{kind,id,attr,scope}, principal{id,roles,attr}, actions[]}],
    "outputs": [{requestId, resourceId,
                 actions: { "<action>": {"effect":"EFFECT_ALLOW|EFFECT_DENY",
                                        "policy":"<module-id>", "scope":"<matched scope>"} },
                 effectiveDerivedRoles: [...]}] } }
```
(or `planResources: {...}` for PlanResources calls.)
Key properties: it records **both inputs and outputs** of the evaluation (full replay input), the exact policy module ID and scope that produced each per-action effect, and the request/response correlation via `callId`/`cerbosCallId`. This is the "replayable audit trail as a byproduct of deciding at every hop" doctrine. Gap: no signature/hash binding the record to the inputs in OSS.

## Retries / failures
- Hub audit streaming has a **local disk buffer** (`storagePath`) so decision logs survive network outages; the PDP does not block or drop evaluation when the audit sink is down (fail-open logging, documented behavior — decision path keeps serving).
- Decision filters (`ignoreAllowAll`, `ignoreAll`, `ignoreAlwaysAllow`) reduce log volume at write time.
- Schema enforcement can be warn or reject at request time; violations are reported in `validationErrors` rather than silently defaulting.
- `PlanResources` KIND_CONDITIONAL returns the residual condition AST so the PEP can apply it at the data layer (query-plan adapters) — partial evaluation as a failure-mode-friendly shape.

## Revocation model
- Cerbos has **no runtime revocation store**. Revocation is by policy change: disable a policy via admin API (`/admin/policy/disable?id=<module-id>`), delete it, or push a new version/bundle. Because the PDP is stateless and hot-reloads, revocation latency = store propagation time.
- Principal attributes (roles, clearance) are supplied per-request by the caller or fetched by Synapse at decision time — staleness is bounded by the caller's token/lookup freshness, not by Cerbos. There is no "revoke this decision" — decisions are instantaneous and logged; you change future decisions by changing policy/data.

## Tests
- **Policy unit tests**: `*_test.yaml` suites co-located with policies; `cerbos test` runs them; discovered automatically by `cerbos compile`; official guidance is a failing test must block deployment (CI gate before upload to Hub).
- **Compile-time validation**: `cerbos compile` checks policy syntax, references (derived-role imports, schema paths), and CEL expression parse.
- **Schema enforcement at request time**: `validationErrors[]` in the response when principal/resource attrs violate declared JSON schemas.
- The engine's per-action evaluation is deterministic given (policy set, request inputs) — same inputs + same policy version = same decision. (Determinism claim grounded in the replayable-audit doctrine and the matchedPolicy echo, not in a formal spec I read.)

## Mapping to PING capability-kernel
PING's capability-kernel already has actor/target/action/constraints/allow-deny. What Cerbos proves valuable that PING lacks:
1. **Decision-request contract** (principal+resource+actions+free-form context+JWT aux data, version-pinned policy selection, per-call correlation ID): a crisp externalizable shape for "ask the authority" — adapts cleanly to PING's capability evaluation call.
2. **Policy lineage by module ID** (`<kind>.<name>.v<version>/<scope>` echoed in `meta.matchedPolicy` and in audit outputs): every decision names the exact policy version+scope that produced it. PING should stamp capability decisions with the capability-policy version the same way.
3. **`PlanResources` residual-condition pattern**: when a decision depends on data not yet known, return the condition AST (KIND_CONDITIONAL) instead of a bare deny — directly useful for Ask FYD list filtering ("which sites may this principal see") without leaking data.
4. **Decide-at-every-hop logging** as the audit trail: the decision record IS the trail; no separate audit bolt-on.

## SMALLEST MISSING PRIMITIVE
**DecisionReceipt.** PING's capability-kernel can evaluate allow/deny, but it has no canonical, evidence-grade record of a single evaluation. The smallest primitive worth adding:
```
DecisionReceipt {
  receipt_id: ULID            # == the call/correlation id, joinable to the request and the event journal
  evaluated_at: timestamp
  evaluator: "capability-kernel" (+ code version)
  actor_id, action(s), target_ref {kind, id}
  context_digest: sha256(canonical(context attrs))   # binds the exact inputs without storing secrets twice
  policy_ref: {policy_id, policy_version, scope}     # the Cerbos module-ID lesson
  matched_rule: string                               # which rule/case produced the decision
  effects: {action: ALLOW|DENY}
  derived_roles: [string]                            # effectiveDerivedRoles lesson
}
```
Recorded append-only in the event spine per evaluation that gates a mission-critical effect (proofs 9-14: worker authorization, bad-result rejection, independent verification). Cerbos proves the shape (inputs+outputs+callId+policy lineage); PING improves it by hash-binding the receipt (context_digest, and eventually a signature) — the gap Cerbos OSS leaves open.

## Dependency analysis
- **No dependencies required for the adaptation.** The harvest is the *contract shapes* (request JSON, receipt schema, module-ID lineage), re-derived clean-room in piging2 TypeScript from documented wire formats. Wire formats are facts, not code; no Cerbos code is copied.
- Adopting the actual PDP would mean: Go runtime + binary/service deployment + gRPC/HTTP clients + SDK per language — a heavyweight runtime dependency and a second decision authority boundary. REJECTED for piging2 per zero-dependency preference and the one-authority rule.

## Open questions / caveats
- The exact current `DecisionLogEntry` proto field set may have evolved since PR #960 (2022); the wire shape above is verified from official sources, but piging2 should treat its own `DecisionReceipt` as the canonical contract and validate against a live PDP only if interop is ever needed.
- Cerbos OSS decision logs are unsigned; integrity comes from the log pipeline. PING's DecisionReceipt should add `context_digest` (and later signatures) from day one.
- PDP-local logs don't aggregate in OSS (per-instance); piging2's event spine must centralize by construction.
