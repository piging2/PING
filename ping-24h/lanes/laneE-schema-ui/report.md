## 2. Minimal sketch: BUSINESS / SERVICE / POST each driving the pipeline

One schema source per object (authored once, e.g. Zod in a shared package, serialized to canonical JSON Schema + content hash at registration). From that single source each of the five projections is mechanical.

**BUSINESS.** Fields: `name` (required text), `phone`, `address` (nested object), `hours` (array of day/open/close), `categories` (enum array), `website`, `owner_name`. Types: `z.infer` gives the `Business` TS type used by Mission Control, FYD site builder, and Ask FYD, no hand copies. Validation: same schema validates intake/agent writes at the boundary (phone regex, required name). Editor: field types map to widgets (enum -> multi-select, hours -> repeating group), a separate UI-schema layer orders sections and adds labels without touching the data schema. Eligibility: testers score the BUSINESS schema node: it is eligible for `BusinessProfile` hero component, `ContactCard`, `HoursTable`, `MapEmbed` (requires address subfields), ranked by tester priority. Capabilities: the `categories` enum projects to capability option sets (e.g. scheduling options for trades, booking for services); `hours` presence enables the hours-aware capabilities. Search/protocol: the same fields emit `LocalBusiness` JSON-LD for indexing and the canonical JSON bytes for the protocol projection.

**SERVICE.** Fields: `business_id` (relationship -> BUSINESS, relationTo-style), `name`, `description`, `price_model` (enum: fixed/hourly/quote), `price`, `duration_minutes`, `category` (enum), `is_active`. Types + validation as above; validation includes cross-field rule (price required unless price_model=quote) expressed as schema refinement evaluated by the engine, not by UI code. Editor: relationship field renders a BUSINESS picker (registry tester sees the relationship annotation), enum renders radio/dropdown, conditional price field shows/hides per `price_model` via engine-evaluated rules. Eligibility: eligible for `ServiceCard`, `ServiceList`, `QuoteForm` (requires price_model=quote), `BookingSlotPicker` (requires duration_minutes). Capabilities: `price_model` and `duration_minutes` derive booking/scheduling tool options; tool descriptions generated from field `.describe()` strings via Zod->JSON Schema (P5), authorization checked outside the schema. Search/protocol: projects to schema.org `Service` markup.

**POST.** Fields: `business_id` (relationship -> BUSINESS), `type` (enum: announcement/offer/event/update), `title`, `body` (richtext), `media` (array of image refs), `starts_at`/`ends_at` (conditional on type=event/offer), `status` (enum: draft/published), `published_at`. Types + validation as above; validation gates publish transitions (title+body required when status=published). Editor: `type` selector drives conditional `starts_at`/`ends_at` visibility through engine rules; richtext maps to the Lexical-style field widget. Eligibility: eligible for `PostFeedCard`, `AnnouncementBanner` (type=announcement), `EventCard` (type=event with dates), `OfferBadge` (type=offer); ineligible testers return NOT_APPLICABLE when required fields are absent. Capabilities: `status` transitions drive the publish/schedule capability set; tool input schema for `publish_post` generated from the POST schema subset. Search/protocol: projects to `Article`/`BlogPosting` JSON-LD; the event carries the schema version so replay resolves exact bytes.

PERSON (deferred): same mechanics, fields `name`, `role` (enum), `business_id`, `contact`; add only when a renderer or capability needs person-shaped data. Do not build a fourth schema speculatively.

## 3. Schema-registry authority rules

1. The registry is a projection of git, not a store of truth: schemas are authored as code (config-as-code, P2), reviewed in PRs, and the registry only indexes registered versions. Git HEAD is the authority; the registry is the lookup.
2. Registration is a CI gate, not a runtime convenience: every schema change computes the canonical JSON Schema bytes, content-hashes them, and runs compatibility checks (BACKWARD default per P4) against all prior versions of that subject before merge. Breaking changes fail the build.
3. Events and objects carry schema identity: every emitted event/object stamps `schema_name` + `schema_version` (or content hash). Replay resolves the exact pinned bytes from the registry; never re-interpret old data with the newest schema.
4. Canonical bytes exclude presentation: the registry stores the data schema only. UI-schema, widget hints, and eligibility testers live in separate versioned artifacts that reference schema versions; they can never alter canonical bytes (P6, P8).
5. Derived artifacts are generated, never edited: TS types, validation bindings, editor field lists, tool input schemas, JSON-LD projections are built from the registered schema bytes by deterministic generators. A hand-edited derived artifact is a defect; regeneration is the only fix path.
6. Compatibility modes are explicit per subject: BUSINESS/SERVICE/POST start at BACKWARD (add optional fields freely; new required fields, renames, and type changes are breaking and require a new major version with a migration). NONE is forbidden in production.
7. One semantic authority check on every read path: no consumer (renderer, agent, search indexer, protocol projector) may define its own field semantics. If two consumers disagree about what a field means, the schema's field description is the ruling text and the schema gets the fix, not the consumers.

## Verdicts requested by parent

Top 6 patterns with verdicts: P1 Zod-first single source (HARVEST), P2 Payload config-as-code (HARVEST), P3 JSON Forms renderer registry + tester dispatch (HARVEST), P4 Confluent-style versioned registry with compatibility gates and schema IDs on events (HARVEST), P5 Zod->JSON Schema -> agent/MCP tool surface (HARVEST), P6 separate UI-schema layer (HARVEST).

Sharpest SCHEMA GAP: there is no evidence of a canonical schema source anywhere in the current implementation driving the UI pipeline. Types, validation, editor fields, component eligibility, capability options, and tool descriptions are each hand-maintained in their own layer, which is exactly the drift the public patterns above were built to kill (nightwarden deleted 857 hand-written lines; docita made "Zod schemas are the only source of truth" its core principle). The highest-leverage first move is not a registry service or 100 schemas: it is THREE schema modules (BUSINESS, SERVICE, POST) authored once, with types inferred, validation shared, and one projection each to editor fields and component eligibility testers. Everything else (versioning gates, tool-surface generation, JSON-LD) layers on top of those three without rework.
