## What the builder lanes reuse as-is

1. Digest-bound proposals (`proposalDigest`/`verifyProposalDigest`, `sha256-canonical-json-v1`): the human approves the exact digest; the approved transition applies through the governed event path, never by the agent. Already the builder mechanism for conversational patching (contract v0.3 step 11). Nothing new to build here.
2. Checkpoint file format (`STATE.json` schema: branch, base_commit/base_tip, green_state, lanes, steps, accepted_boundaries): the current lane coordination. Crash recovery = a fresh agent reads the checkpoint and continues unfinished steps. Keep it file-based.
3. Deterministic identity + `ON CONFLICT DO NOTHING` + semantic-collision fail-closed (from `UnifiedEventRuntime.emit`): the pattern for builder run records and artifact writes. Same logical run always hashes to the same record; a hash collision with different content fails closed instead of silently overwriting.
4. Conditional state transitions (from `MissionRuntime`): any builder run-state machine should copy the rule that a transition only fires from its legal predecessor state (claim only from created, complete only from running). This is what makes re-execution after a crash safe.
5. The single-decider / single-writer law (from `WorkerRuntime.dispatch`): one canonical place decides execution; the builder already mirrors this with the single-writer rule (parallelize only across disjoint semantic units).

## What we will NOT build

- No new workflow engine. Trigger.dev and Conductor are reference patterns, not dependencies (per the directive). The harvest found the needed primitives already implemented.
- No new queue service. No BullMQ, no resurrection of `queue_port.js` / `persistent_queue_authority.js`. The mission-table-plus-poll pattern (or the file-based STATE.json equivalent) is the queue.
- No shared lease service. The TS kernel leases are in-memory and dead; the PG lease pattern is adapted only as checkpoint fields if ever needed.
- No durable browser runner. Browser jobs in this machinery are single-shot and idempotent on re-run; no resumable-playwright layer.
- No separate intent ledger. Deterministic IDs, conditional transitions, and digest-bound proposals already prevent duplicate execution; a ledger would be a second source of truth.
- No in-memory approval/effect authorities on production paths. `approval_restart_durability.test.js` documents the defect: without a storage adapter, proposed actions and effects are lost on restart. Any builder adoption of the proposal/effect pattern must use a durable store.
