## DATA FLOW DESIGN (chosen: option b — PING-side projection dump + Next.js serve)

No existing API route queries PING (the ask route reads the same static
fixtures via getSiteBundle). The PING backend holds NO FYD business records

are PING-internal ops events). So the honest chain is:

### The chain

1. **PING state (source of truth for overlays).**
   Overlay events in PING Postgres `ping_events`:
   `event_type='FYD_SITE_OVERLAY'`, namespace `fyd::site::<slug>`,
   payload = deterministic change ops (set_field / add_object /
   add_relationship / deactivate_object). Emitted through the REAL gateway
   `POST http://127.0.0.1:8080/events` with Bearer `MUSE_LEVEL_1_KEY`
   resolved at runtime from the ping-gateway container env (never stored),
   same pattern as ~/workspace/tandem/emit-observation.py. Verifiable with a
   read-only SELECT on ping_events.

2. **PING-side projection dump** (lives in PING tooling, NOT the website repo):
   `/home/nolan/ping/tools/fyd-site-projection/dump.py`
   - Base graph: mechanically extracted from the committed machine-generated
     fixture TS (strip `import`/`export const X: ObjectGraph =` wrapper, parse
     JSON). Records base sha256 + the fixture provenance header. No
     hand-authoring: the transform is byte-deterministic and recorded.
   - Overlays: read-only query of FYD_SITE_OVERLAY events for the site,
     applied in (timestamp, event_id) order. Overlay objects/relationships get
     provenance `{kind:"ping-event-derived", ref:"ping-event:<event_id>",
     derivedAt:<dump time>}`; base objects keep `website-derived`.
   - Writes canonical projection JSON to
     `/home/nolan/ping/var/fyd-projections/<slug>.json`:
     `{ meta: {siteId, dumpedAt, dumperVersion, baseDigest, overlayEventIds[],
       graphDigest, generatedAt, eventSequences}, graph: {objects, relationships} }`
     where `graphDigest = sha256(canonicalBytes(graph))`, canonicalBytes =
     recursive key-sort then JSON (same rule as the absorbed
     ~/workspace/fyd-lane/absorb/src/canonical.ts).
   - `emit-overlay.py` (same dir): emits one overlay event via the gateway.
     Usage for the proof: add a service to happy-place.

3. **Website-side source module** (NEW files, no collision with placement lane):
   - `src/fyd/data/ping-object-source.ts` (server-only): `getPingObjectGraph(siteId)`
     reads `$FYD_PROJECTION_DIR/<siteId>.json` (default
     `/home/nolan/ping/var/fyd-projections`), parses, shape-validates, FAILS
     CLOSED when: file missing, JSON invalid, graphDigest mismatch
     (recomputed via the integrated canonical.ts), or any object lacking
     provenance. Returns `{ graph, meta }`. Integrates the absorbed
     canonical.ts as the tamper-evidence check (the "verify bindings before
     render" fit for this lane: no unverified projection ever reaches the
     generator/renderer).
   - `src/app/api/fyd/projection/route.ts` (NEW): `GET /api/fyd/projection?siteId=`
     serves the same projection JSON + meta. The serving seam for future
     client-side consumers.

4. **APPLY (after rail-capture.mjs exits; pages are placement-lane-owned until then):**
   - `src/app/sites/happy-place/page.tsx` and `coppersmith-plumbing/page.tsx`
     become async: `const { graph, meta } = await getPingObjectGraph("<slug>")`,
     `generateSiteSpec(graph, { generatedAt: meta.generatedAt,
     eventSequences: meta.eventSequences })`, metadata title/description
     derived from the owner object's title (no hardcoded business name).
   - `src/fyd/media/site-bundle.ts`: `getSiteBundle` reads via
     `getPingObjectGraph` (BUNDLE_DEFS generatedAt literals deleted); the
     bundle stays a thin wrapper so /api/fyd/ask answers from the same
     PING-backed graph as the page renders. Ask FYD and the page can never
     disagree about customer facts again.
